# Open Questions Registry

## Decision

These questions are intentionally unresolved. Documentation contradictions stay in this registry because guessing would erase the boundary between documented protocol behavior and later code/runtime verification.

| ID | Category | Question / conflicting evidence | Impact | Required next step |
| --- | --- | --- | --- | --- |
| OQ-001 | conflicting documentation / security assumption | What exact metadata is hidden from non-entitled participants, sequencers, mediators and SV applications? The privacy overview claims no metadata leakage while ordering/transaction pages list recipients, sizes, timestamps, informees, policies and outcomes. | Threat models and privacy claims cannot use an absolute formulation. | Reconcile protocol specification terminology; later inspect message schemas and run traffic-observation experiments. |
| OQ-002 | unclear terminology / protocol ambiguity | Does any submitting/preparing participant reconstruct the full clear transaction tree, and under what explicit-disclosure/view conditions? The lifecycle intro says no single node sees it while Phase 1 says the submitter produces a full tree. | Determines trust/privacy of transaction preparation services. | Obtain specification-level definition; later verify preparation/runtime behavior. |
| OQ-003 | protocol ambiguity | What are the current thresholds and failure assumptions separately for orderer BFT, mediator replication, sequencer client trust, decentralized DSO-party confirmation and app-level governance voting? | “Two-thirds” can otherwise be applied to the wrong set/property. | Produce an authoritative per-network/version threshold matrix from current specifications/config. |
