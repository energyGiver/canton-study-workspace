Canton Transaction은 commit되거나 reject되기 전에 서로 구별되는 다섯 phase를 거칩니다. 각 phase에는 Participant Node, Sequencer Node, Mediator Node 등 특정 node 역할이 관여하며 encrypted sequenced message를 통해 통신합니다. 어느 단일 node도 전체 Transaction을 cleartext로 보지 못합니다.

Phase는 다음과 같습니다.

1. **Preparation**: Submitting Participant가 Command를 interpret하고 encrypted Transaction view를 구성합니다
2. **Submission**: Participant가 confirmation request batch를 Sequencer에 보냅니다
3. **Sequencing and Distribution**: Sequencer가 message의 순서를 정하고 recipient에게 deliver합니다
4. **Validation and Confirmation**: 각 Confirming Participant가 자신의 view를 validate하고 Mediator에 response를 보냅니다
5. **Aggregation and Commit**: Mediator가 response를 수집하여 verdict를 내리고 Participant가 verdict에 따라 결과를 적용하거나 폐기합니다


## Phase 1: Preparation

Lifecycle은 Submitting Participant Node가 application에서 Ledger API(gRPC)를 통해 Command를 받으면 시작됩니다. 그런 다음 Participant는 다음을 수행합니다.

- **Command interpret:** Canton engine에서 Canton smart contract code를 local로 실행합니다. Engine은 Participant의 현재 Active Contract Set(ACS)을 기준으로 Command를 evaluate하고 모든 action(create, exercise, fetch), 각 action의 결과, 관련 metadata를 담은 구조인 full Transaction tree를 생성합니다.

- **각 action node의 informee 결정:** Informee는 Canton Template에서 정의된 Signatory, Observer, Actor(Choice를 실행하는 Party)처럼 특정 action을 볼 권한이 있는 Party입니다. 각 action의 informee set에 따라 누가 Transaction의 어느 부분을 받을지 결정됩니다.

- **Transaction을 view로 분해:** Transaction tree의 각 action node가 별도 view가 됩니다. View에는 action과 그 결과, validation에 충분한 context만 담깁니다. 각 view는 informee와 그 informee를 hosting하는 Participant만 decrypt할 수 있도록 encrypt됩니다. Non-informee는 payload, Party, action의 존재 여부 등 action에 관해 아무것도 알지 못합니다.

- **Root hash 계산:** 전체 Transaction tree에 cryptographic commitment를 제공하는 root hash를 계산합니다. Root hash는 모든 view를 결합합니다. 모든 Confirming Participant는 자신이 받은 view가 다른 모든 Participant가 validate하는 동일한 Transaction에 속하는지 verify할 수 있습니다. Mediator는 root hash로 confirmation response를 correlate합니다.

Transaction이 여러 Synchronizer의 contract를 다루는 경우 Participant는 submission 전에 해당 contract를 common Synchronizer로 reassign해야 할 수 있습니다. [Reassignment Protocol](/overview/reference/reassignment-protocol)이 이를 처리합니다.

Canton은 Transaction을 view로 분할합니다. Submitting Participant는 Synchronizer의 Sequencer를 통해 need-to-know basis로 관여한 모든 Participant에게 이 view를 보냅니다. 이 section에서는 intended recipient만 Transaction 내용을 알도록 view를 encrypt, distribute, store하는 방식을 설명합니다.

Canton은 hierarchical view structure를 Merkle-like tree로 표현합니다. 이 tree에서 hash는 내용을 공개하지 않고 hidden node와 subtree의 내용에 commitment를 제공합니다. 각 recipient는 hash를 사용해 받은 view에서 자신의 Transaction projection을 올바르게 reconstruct할 수 있습니다.

Submitting Participant는 view action의 informee 또는 witness를 hosting하는 Participant에 view를 보냅니다. 따라서 Participant는 전체 Transaction이 아니라 자신이 hosting하는 witness의 data만 받아 **subtransaction privacy**가 보장됩니다. 각 Canton Participant는 view를 포함해 Sequencer에서 받은 모든 message를 persist합니다.

또한 Canton은 Synchronizer에도 Transaction 내용을 숨깁니다. 이를 위해 Submitting Participant는 다음 encryption scheme으로 view를 encrypt합니다.

1. View를 받을 Participant 집합인 distinct recipient informee group마다 short-lived symmetric **session key**를 생성합니다.

2. 각 view의 Merkle tree serialization을 해당 recipient group의 session key로 encrypt합니다.

3. 마지막으로 각 view informee를 hosting하는 Participant의 public key로 이 session key를 encrypt합니다. Caching이 활성화되면 session key와 이 key를 Participant public key로 asymmetrically encrypt하여 생성된 해당 ciphertext를 잠시 memory에 저장합니다. 그러면 이후 비슷한 view에서 session key를 asymmetrically encrypt/decrypt할 필요가 일시적으로 없어집니다. Encrypted Merkle tree와 각 informee Participant를 위해 encrypt한 session key가 Sequencer를 통해 전송되는 data를 구성합니다.

Session key는 informee를 hosting하는 Participant의 public key로 encrypt되지만 encrypted Merkle tree 자체는 witness만 hosting하는 Participant에도 전송됩니다. 후자의 Participant도 Merkle tree를 decrypt할 수 있습니다. Parent view의 tree가 direct subview hash와 encryption key를 함께 담으므로 parent view를 decrypt할 수 있는 Participant가 parent 내용에서 subview key를 얻기 때문입니다.

Sequencer가 encrypted view를 제한된 기간 persist하더라도 Synchronizer는 symmetric session key에 접근할 수 없습니다. 따라서 Informee Participant 중 하나의 private key를 알지 못하면 view를 decrypt할 수 없습니다. 그러므로 Synchronizer에 대해 Transaction 내용의 confidentiality가 유지됩니다.

## Phase 2: Submission(Confirmation Request)

Submitting Participant가 Sequencer에 **confirmation request batch**를 보냅니다. Batch에는 세 가지 message category가 있습니다.

- **Encrypted view**: Action node마다 하나씩 있습니다. 각 view는 informee를 hosting하는 Participant를 위해 encrypt됩니다. 특정 view의 Informee를 전혀 hosting하지 않는 Participant는 이를 decrypt할 수 없고 전달받지도 않습니다.

- **Root hash message**: Recipient Participant마다 하나씩 있습니다. 각 root hash message는 Transaction root hash를 전달하여 recipient가 받은 view를 하나의 Transaction과 correlate할 수 있게 합니다.

- **Informee message**: Mediator로 전송됩니다. 각 view의 informee와 confirmation policy를 나열합니다. Confirmation policy는 confirm해야 하는 Signatory와 각 Signatory에 대해 승인해야 하는 Hosting Participant의 threshold를 지정합니다. Mediator는 이 정보로 충분한 confirmation이 도착했는지 판단합니다.

Submitting Participant는 이 모든 message를 하나의 batch로 Sequencer에 보냅니다.

## Phase 3: Sequencing and Distribution

Sequencer는 confirmation request batch를 처리합니다.

1. **Timestamp 할당:** Transaction의 sequencing time입니다. Sequencer가 BFT-write를 수행하여 ordering node가 global message sequence에서 이 batch의 위치와 timestamp에 합의합니다. Timestamp는 이후 모든 deadline의 reference point가 됩니다.

2. **지정된 recipient에게만 각 message deliver:** Participant는 자신이 Informee Party를 hosting하는 encrypted view와 root hash message를 받습니다. Mediator는 Informee message를 받습니다. Transaction의 어떤 view에도 Informee를 hosting하지 않는 Participant는 아무것도 받지 않으며 Transaction에 관해 아무것도 알지 못합니다.

Mediator는 Informee message를 받으면 다음을 수행합니다.

- Confirmation request metadata(root hash, informee list, confirmation policy) 기록
- Sequencing time과 Synchronizer의 configured decision time parameter를 바탕으로 **confirmation deadline timer** 시작
- Participant의 confirmation response 대기

## Phase 4: Validation and Confirmation

View를 받은 각 Participant는 독립적으로 validate합니다. Validation check는 다음과 같습니다.

- **Conformance:** Participant가 받은 각 view action의 Canton contract logic을 다시 실행합니다. Re-execution은 view가 주장한 것과 같은 결과, 즉 created contract와 archived contract를 생성해야 합니다. 결과가 다르면 view가 malformed되었거나 submitter가 dishonest한 것입니다.

- **Authorization:** 모든 action이 올바르게 authorize되었는지 확인합니다. 각 action의 required Party(Signatory, Controller)가 authorize해야 합니다. Party-to-Participant Topology와 Canton authorization rule을 통해 authorization을 verify합니다.

- **Consistency:** View가 참조하는 모든 input contract가 local ACS에서 여전히 active한지 확인합니다. 이미 consume, 즉 archive된 contract는 다시 사용할 수 없습니다. 이 check가 단일 Synchronizer 내 double-spend를 방지합니다.

- **Time bound:** Transaction이 주장하는 ledger time이 sequencing time(record time)에 대해 acceptable bound 안에 있는지 확인합니다. Tolerance window는 Synchronizer parameter입니다.

- **Root hash:** 받은 view가 root hash message의 root hash와 consistent한지 확인합니다. 이를 통해 모든 Participant가 동일한 Transaction tree의 view를 validate하도록 보장하며 malicious submitter가 서로 다른 Participant에 서로 다른 view를 보내는 것을 방지합니다.

Validation 후 Participant가 **mediator response(MR)** message를 구성합니다.

- Participant가 받은 모든 view가 모든 check를 통과하면 **Approve**
- 어느 check라도 실패하면 rejection reason과 함께 **Reject**

Mediator response는 Sequencer로 전송되고 Sequencer가 다시 BFT-write를 수행해 message에 timestamp를 부여한 다음 Mediator에 deliver합니다. Confirming Participant는 response를 Mediator에 직접 보내지 않으며 모든 communication은 Sequencer를 거칩니다.

## Phase 5: Aggregation and Commit

Mediator는 mediator response message를 수집하고 confirmation policy에 따라 evaluate합니다.

1. **Aggregation:** 각 view의 confirmation policy가 confirm해야 하는 Signatory Party를 지정합니다. Signatory Party가 여러 Participant에서 hosting될 수 있으며 policy는 해당 Signatory가 confirmed로 인정되기 위해 승인해야 하는 Hosting Participant 수인 confirmation threshold를 정의합니다. Mediator는 view별, Signatory별 approval을 추적합니다. 여기에는 Submitting Party가 multi-hosted인 경우도 포함됩니다.

2. **Verdict 결정:** 가능한 outcome은 두 가지입니다.
   - **Approve**: Confirmation deadline 전에 모든 view의 모든 Signatory threshold가 충족됩니다. 모든 required Signatory에 대해 충분한 Hosting Participant가 승인했습니다.
   - **Reject**: Required Participant가 명시적으로 reject하거나 충분한 approval 없이 confirmation deadline이 만료됩니다. 단 하나의 Signatory라도 threshold를 충족하지 못하면 전체 Transaction이 reject됩니다.

3. **Transaction result 배포:** Mediator가 **transaction result(TR)** message를 Sequencer에 보냅니다. Sequencer가 이 verdict를 모든 Informee Participant에 deliver합니다. Participant는 Sequencer에서 verdict를 읽을 때 BFT-read를 수행하여 delivered message의 Sequencer signature를 verify하고 authenticity를 확인합니다.

4. **Local commit 또는 discard:** 각 Participant가 verdict를 처리합니다.
   - **Approve 시:** Participant가 Transaction을 commit합니다. Consumed contract를 archive하고 새 contract를 생성하며 ACS를 update합니다. Transaction과 그 effect는 Participant의 local ledger projection 일부가 됩니다.
   - **Reject 시:** Participant가 Transaction을 discard합니다. State change를 적용하지 않으며 ACS는 변경되지 않습니다.

Verdict가 sequence되고 deliver되면 Transaction result는 **final**입니다. Fork, reorganization, rollback은 없습니다. Commit된 Transaction은 commit 상태로, reject된 Transaction은 reject 상태로 유지됩니다.

## Message 요약

다음 표는 protocol에서 교환하는 message와 sender, recipient, 내용을 요약합니다.

| Message | Sender | Recipient | 내용 |
|---------|--------|-----------|------|
| **Command** | Application | Submitting Participant | Ledger API를 통한 Canton Command(create, exercise) |
| **Encrypted view** | Submitting Participant | Sequencer, 이후 Informee Participant | Action node마다 하나, Informee별로 encrypt |
| **Root hash message** | Submitting Participant | Sequencer, 이후 각 Recipient Participant | Full Transaction tree의 root hash |
| **Informee message** | Submitting Participant | Sequencer, 이후 Mediator | View별 informee list와 confirmation policy |
| **Mediator response(MR)** | Confirming Participant | Sequencer, 이후 Mediator | Approve 또는 reason을 포함한 reject |
| **Transaction result(TR)** | Mediator | Sequencer, 이후 모든 Informee Participant | Final verdict: approve 또는 reject |

## Timing과 Deadline

두 time parameter가 protocol liveness를 제어합니다.

- **Sequencing time:** Confirmation request batch가 order될 때 Sequencer가 할당합니다. Transaction reference timestamp입니다.
- **Decision time:** Sequencing time에 Synchronizer의 `decisionTimeout` parameter를 더해 계산합니다. Decision time까지 Mediator가 충분한 confirmation을 받지 못하면 timeout으로 Transaction을 reject합니다.

Participant도 **participant response deadline**을 enforce합니다. Sequencing time에서 도출되는 configured cutoff 전에 mediator response를 보내야 합니다. 제때 response하지 못한 Participant는 해당 Transaction에서 non-confirming으로 처리됩니다.

## Failure Mode

Transaction은 lifecycle의 여러 지점에서 실패할 수 있습니다.

- **Preparation failure:** Canton engine이 Command를 reject합니다. 예를 들어 contract not found, authorization failure, assertion violation이 있습니다. Message를 보내기 전에 Command가 synchronously reject되며 다른 node는 관여하지 않습니다.

- **Validation rejection:** Confirming Participant가 conformance, authorization, consistency 또는 time-bound violation을 발견하여 reject MR을 보냅니다. Confirmation policy에 따라 단일 rejection만으로 전체 Transaction이 reject될 수 있습니다.

- **Timeout:** Decision time 전에 충분한 Participant가 response하지 않아 Mediator가 Transaction을 reject합니다. Participant가 offline, overloaded 또는 unreachable한 경우 발생할 수 있습니다.

- **Equivocation detection:** Submitter가 서로 다른 Participant에 inconsistent view, 즉 root hash와 일치하지 않는 view를 보내면 honest Participant가 root hash validation 중 inconsistency를 detect하고 reject합니다.

모든 failure case에서 state는 변경되지 않습니다. 모든 Participant의 ACS는 Transaction submission 전 상태로 유지됩니다.
