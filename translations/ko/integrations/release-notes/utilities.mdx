## 0.12.1

### Synchronizer ID Migration

`utility.yaml`을 2.0.0에서 2.1.0으로 업데이트하면서 utility endpoint에 `synchronizerId`를 도입했습니다. 이 새 field는 기존 `domainId`와 동일한 값을 사용합니다. `domainId`는 이제 deprecated 상태이지만 backwards compatibility를 위해 계속 사용할 수 있습니다. 모든 사용자는 `synchronizerId`로 전환하는 것이 좋습니다.

### Documentation

documentation의 기존 How-To Tutorial을 version 0.12.x에 맞게 업데이트했습니다.

### Independent Transaction Validation

participant가 UpdateID 및 Transfer Object를 제출해 Registry asset의 asset transfer 결과를 독립적으로 확인할 수 있는 새로운 verification API를 도입했습니다. 이 service는 표준화된 Success, Failure, Pending status 또는 invalid input을 제공합니다.

### Historical Transfer Verification

prune된 transaction의 proof data를 조회하도록 Transfer Proof API를 개선했습니다. 이를 통해 Ledger data가 archive된 이후에도 과거 transfer를 검증할 수 있습니다.

### 새로운 Registry App 기능

#### Batched Featured App Marker

Registry Daml workflow는 더 이상 featured app activity marker를 생성하지 않습니다. 이제 Digital Asset이 운영하는 batched app marker automation을 통해 marker가 생성됩니다.

이 automation은 최신 tokenomics guideline에 따라 Asset Issuer(Registry Provider)에 최적의 app marker 수가 적용되도록 보장합니다.

featured party의 marker 생성을 DA operator에게 위임하려면 이 service를 opt-in해야 합니다. Registry Onboarding tab의 UI에서 Delegate Marker Creation을 클릭하면 `DelegatedBatchedMarkersProxy` instance가 생성됩니다.

backwards-compatible Registry workflow(version 0.10 및 0.11)를 계속 사용하는 경우 Utility Operator Backend API가 activity marker 생성에 필요한 context를 더 이상 제공하지 않는다는 점에 유의하세요. 이는 최신 Tokenomics guideline을 준수하기 위한 조치입니다.

또한 이 변경은 Registry transaction submitter에게 발생하는 transaction cost를 줄이는 데 중요한 역할을 합니다. 자세한 내용은 아래와 같습니다.

추가 Transaction Cost 절감

input holding 수가 늘어날수록 비례 cost 절감 효과가 더욱 커집니다. 예를 들어 여러 UTXO를 merge하는 cost가 이전보다 크게 낮아졌습니다.

#### ExecutedTransfer 및 기타 Result Contract

- **Batch Archival:** `ExecutedTransfer` 및 `RejectedTransfer` contract를 더 cost-efficient하게 batch archive할 수 있도록 `RegistrarService`에 choice를 추가했습니다.
- **Observer Removal:** `ExecutedTransfer`, `RejectedTransfer` 및 기타 모든 Executed\*/Rejected\* contract를 포함한 모든 result contract에서 operator를 observer에서 제거했습니다.

#### Allocation 및 TransferRule

이제 allocation 실행은 새로 도입된 `TransferRule_ExecuteAllocation` choice를 통해 `TransferRule`을 활용합니다. 따라서 실행에 성공하려면 token admin 또는 registrar의 TransferRule instance가 있어야 합니다.

또한 rule이 호출되는 역할을 더 명확히 구분할 수 있도록 TransferRule에 전용 choice를 추가했습니다.

- `TransferRule_TwoStepTransfer`
- `TransferRule_DirectTransfer`

이는 향후 계획된 TransferRule validation logic 개선의 prerequisite입니다.

### UX 개선

- self-issuing credential UX를 개선했습니다. 일반적으로 Registry allowlist에 사용되는 기능입니다.
- deprecated 상태인 `HolderService`는 더 이상 UI에 표시되지 않습니다. `ProviderServiceConfiguration`의 `holderCredentialRequirements` field는 비어 있으면 숨겨지고 configuration이 수정될 때마다 0으로 설정됩니다.

### 기타 변경 사항

Splice dependency를 splice-amulet-0.1.16으로 업그레이드했습니다.

### Deprecation 및 지원 Version

이 DA Apps version에서는 0.9.x release line 지원이 제거되었습니다. 모든 사용자는 적어도 0.10.x release line과 함께 제공된 Daml model을 실행해야 합니다.

`HolderService`는 version 0.8.0부터 deprecated 상태입니다. 활성 `HolderService` instance가 있는 Provider는 해당 instance를 archive하고 `RegistrarConfiguration`에서 대응하는 holder requirement를 0으로 설정하는 것이 좋습니다. UI를 통해 빠르게 처리할 수 있습니다. 다음 release에서는 ensure false clause를 통해 Daml에서 HolderService를 완전히 비활성화할 계획입니다.

기존 3-step mint/burn flow는 Daml에서 비활성화되었습니다.

### Integration Guide 및 Backwards Compatibility

#### Tokenizer

- batched app marker 생성을 위해 featured provider는 새로 도입된 `DelegatedBatchedMarkersProxy` template을 통해 가능한 한 빨리 app marker 생성을 operator에게 위임해야 합니다. UI에서 Registry Onboarding tab으로 이동하고 Delegate Marker Creation button을 클릭하세요. 이 작업은 operator가 해당 release를 활성화하는 package를 deploy한 이후에 수행할 수 있습니다. 이 설정이 완료될 때까지 marker 생성이 중단되지 않도록 임시 방안으로 operator의 featured app right를 사용합니다.
- 또한 Tokenizer는 Canton Foundation의 Validator release schedule을 따르고, marker 생성이 중단되지 않도록 최신 Splice version을 사용해야 합니다.
- allocation 실행을 성공시키려면 token administrator 또는 registrar가 token에 대응하는 `TransferRule` instance가 있는지 확인해야 합니다. 없으면 transaction이 실패합니다.

#### Wallet Provider

Utility asset을 지원하는 Wallet Provider는 transaction history를 표시할 수 있도록 transfer를 성공적으로 parse할 수 있어야 합니다. 2-step transfer는 `TransferRule_DirectTransfer` choice 사용에서 새로 도입된 전용 `TransferRule_TwoStepTransfer` choice 사용으로 전환되었습니다.

#### Third-Party Application

그 밖의 모든 third-party application, 예를 들어 Token Standard Allocation workflow를 통해 Utility와 compose하는 exchange는 최신 Daml package를 upload하고 vet해야 합니다. 추가 단계는 필요하지 않습니다.
