Canton Network Validator와 application developer가 자주 묻는 질문에 대한 답변입니다. 이 FAQ는 실제 support interaction을 바탕으로 작성되었으며 가장 흔히 혼동하는 사항을 다룹니다.

## 시작하기

<AccordionGroup>

<Accordion title="Canton Quickstart 실행을 위한 prerequisite는 무엇인가요?">
**Hardware requirement:**
- 최소 8GB RAM, 16GB 권장
- 최소 4개 CPU core
- 50GB의 여유 disk space

**Software requirement:**
- Docker 27.0.0 이상 및 Docker Compose 2.27.0 이상이 포함된 Docker Desktop
- Java 17 또는 21, Java 22 이상은 지원되지 않음
- Node.js 18.x 이상
- Git

**Colima를 사용하는 Mac user:**
```bash
colima start --memory 8 --cpu 4
```

<Warning>
Prerequisite documentation에는 모든 dependency의 구체적인 version requirement가 나와 있지 않을 수 있습니다. Error가 발생하면 먼저 Docker Compose version을 확인하세요. Quickstart failure의 가장 흔한 원인입니다.
</Warning>
</Accordion>

<Accordion title="LocalNet, DevNet, TestNet, MainNet의 차이는 무엇인가요?">
| Environment | 목적 | Access | 실제 가치 |
|-------------|---------|--------|------------|
| **LocalNet** | Local machine에서 development | Access 불필요 | 없음 |
| **DevNet** | Integration testing | VPN + SV sponsorship | 없음 |
| **TestNet** | Staging/pre-production | IP whitelist 필요 | 없음 |
| **MainNet** | Production | IP whitelist + onboarding | 있음, Canton Coin |

**LocalNet**은 local Synchronizer와 함께 전적으로 local machine에서 실행됩니다. 초기 development와 unit testing에 사용합니다.

**DevNet**은 public development environment에 연결됩니다. VPN access와 Super Validator sponsorship이 필요합니다. 승인을 받는 데 2~4주가 걸릴 수 있습니다.

**TestNet**은 production 전 staging deployment에 사용합니다. DevNet보다 안정적이며 IP whitelisting이 필요합니다.

**MainNet**, 즉 Global Synchronizer는 production입니다. 실제 가치가 있는 Canton Coin을 사용하며 완전한 Validator onboarding process가 필요합니다.
</Accordion>

<Accordion title="DevNet access는 어떻게 얻나요?">
1. [canton.foundation](https://canton.foundation)에 나열된 Super Validator sponsor에게 문의합니다.
2. Sponsor는 다음을 수행합니다.
   - VPN credential 제공
   - Validator IP whitelist 등록
   - Sponsorship 정보 제출

승인 process에 **2~4주가 걸릴 수 있습니다.**

<Info>
DevNet은 integration testing을 위해 설계되었으며 Super Validator sponsor와의 active relationship이 필요합니다.
</Info>
</Accordion>

</AccordionGroup>

## Validator 운영

<AccordionGroup>

<Accordion title="Public explorer에 잘못된 Validator version이 표시되면 어떻게 수정하나요?">
Helm upgrade에 성공했지만 ccview.io 또는 CantonLoop Lighthouse 같은 explorer에 이전 version이 표시된다면 `--reuse-values` flag를 사용한 것이 원인일 가능성이 큽니다.

**해결 방법:**
`--reuse-values` 없이 upgrade합니다.

```bash
helm upgrade validator splice-validator/splice-validator \
  --version 0.5.4 \
  -f validator-values.yaml \
  --namespace validator
```

**확인:**
```bash
kubectl -n validator get deploy validator-app \
  -o "jsonpath={.spec.template.spec.containers[0].image}"
```

`--reuse-values` flag를 사용하면 새 chart version으로 upgrade해도 이전 version configuration이 유지될 수 있습니다.
</Accordion>

<Accordion title="SV URL과 Scan URL의 차이는 무엇인가요?">
두 URL은 목적이 다르므로 혼동해서는 **안 됩니다.**

**SV URL**, 즉 Super Validator URL:
- 용도: Validator onboarding 및 sponsorship
- 형식: `https://sv.sv-2.global.canton.network.digitalasset.com`
- Configuration 위치: `svSponsorAddress`

**Scan URL**:
- 용도: Network data 확인 및 Transaction 탐색
- 형식: `https://scan.sv-2.global.canton.network.digitalasset.com`
- 사용 주체: Block explorer와 public-facing tool

<Warning>
`svSponsorAddress`에 Scan URL을 사용하면 "Gave up getting app version" 같은 error와 함께 onboarding이 실패합니다.
</Warning>
</Accordion>

<Accordion title="Validator에서 pruning을 활성화하려면 어떻게 하나요?">
`validator-values.yaml`에 pruning configuration을 추가합니다.

```yaml
participantPruningSchedule:
  cron: "0 */10 * * * ?"   # Every 10 minutes
  maxDuration: 30m          # Max time per pruning run
  retention: 90d            # Keep 90 days of history
```

**MainNet에서 처음 pruning하는 경우:**
History가 많으면 `maxDuration`을 늘리거나 더 큰 `retention` 값으로 시작합니다.

```yaml
participantPruningSchedule:
  cron: "0 */10 * * * ?"
  maxDuration: 60m          # Longer for initial pruning
  retention: 180d           # Start high, reduce later
```

**진행 상황 monitoring:**

<CANTON_DOCS_CN_FAQ_0 />


`/v2/state/latest-pruned-offsets` endpoint를 확인하여 pruning이 실행 중인지 검증합니다.
</Accordion>

<Accordion title="Validator가 정상인지 어떻게 확인하나요?">
**HTTP endpoint 사용:**
```bash
# Validator health
curl http://localhost/api/validator/readyz

# Participant health  
curl http://localhost:5003/health
```

**Canton Console 사용:**

<CANTON_DOCS_CN_FAQ_1 />


**Kubernetes 사용:**
```bash
kubectl get pods -n validator
kubectl logs -n validator deployment/validator-app --tail=100
```

**정상적인 Validator의 표시:**
- 모든 pod가 Running state
- Health endpoint가 200 반환
- Synchronizer에 연결됨
- 지속적인 error log가 없음
- Activity Reward를 수신함, MainNet
</Accordion>

<Accordion title="Network upgrade 중에는 어떤 일이 발생하며 무엇을 해야 하나요?">
Network upgrade는 조정된 schedule에 따라 진행됩니다. Upgrade가 있을 때는 다음을 수행합니다.

1. [canton.foundation/sv-network-status](https://canton.foundation/sv-network-status/)에서 **target version을 확인합니다.**

2. Breaking change와 migration requirement에 관한 **release note를 검토합니다.**

3. 예를 들어 0.4.x에서 0.5.x로 가는 **version upgrade의 경우:**
   - Upgrade 전에 backup/snapshot 생성
   - 필요한 경우 database name update:
     ```yaml
     persistence:
       databaseName: participant_4
     ```

4. Network version에 맞게 **Helm chart** 또는 Docker image를 upgrade합니다.

5. Validator가 network에 다시 참여하고 operation을 재개하는지 **확인합니다.**

<Warning>
Intermediate version을 거치며 점진적으로 upgrade하지 마세요. 현재 network version으로 바로 upgrade하세요.
</Warning>
</Accordion>

</AccordionGroup>

## Authentication 및 보안

<AccordionGroup>

<Accordion title="OIDC authentication을 어떻게 구성하나요? Auth0/Keycloak">
1. Auth0, Keycloak 등의 **OIDC provider를 설정합니다.**

2. `.env` file에 **환경 변수를 구성합니다.**
   ```bash
   AUTH_URL="https://your-tenant.auth0.com"
   AUTH_JWKS_URL="https://your-tenant.auth0.com/.well-known/jwks.json"
   AUTH_WELLKNOWN_URL="https://your-tenant.auth0.com/.well-known/openid-configuration"
   LEDGER_API_AUTH_AUDIENCE="https://ledger_api.your-domain.com"
   VALIDATOR_ADMIN_USER="auth0|123456789"
   WALLET_ADMIN_USER="auth0|123456789"
   ```

3. **Authentication과 함께 Validator를 시작합니다.**
   ```bash
   ./start.sh -a
   ```

**Authentication을 사용하지 않는 구성에서 사용하는 구성으로 migration:**
- Validator 중지: `./stop.sh`
- `-a` flag로 restart: `./start.sh -a`
- Validator operator user가 자동으로 migrated됩니다.

<Info>
OIDC provider는 요청받았을 때 `daml_ledger_api` scope가 있는 JWT를 발행해야 합니다.
</Info>
</Accordion>

<Accordion title="ACCESS_TOKEN_EXPIRED error가 계속 발생하면 어떻게 수정하나요?">
일반적으로 token lifetime이 너무 짧을 때 발생합니다. 최신 Splice version은 더 긴 token lifetime을 요구할 수 있습니다.

**해결 방법:**
OIDC provider에서 access token timeout을 늘립니다.

**Auth0:**
1. Applications → Your App → Settings
2. Advanced Settings → Access Token Lifetime
3. 900초, 15분 이상으로 설정

**Keycloak:**
1. Realm Settings → Tokens
2. Access Token Lifespan → 900, 15분

그런 다음 Validator를 restart합니다.
</Accordion>

<Accordion title="Validator authentication에 권장되는 token lifetime은 얼마인가요?">
**권장 setting:**
- Access Token: 15~30분
- Refresh Token: 24시간

일부 OIDC provider가 사용하는 default 5분 token lifetime은 Canton Validator에 충분하지 않은 경우가 많으며, 특히 activity가 많거나 network latency가 있을 때 그렇습니다.
</Accordion>

</AccordionGroup>

## Transaction 및 error

<AccordionGroup>

<Accordion title="MEDIATOR_SAYS_TX_TIMED_OUT은 무엇을 의미하나요?">
이 error는 timeout period 이내에 Mediator가 모든 필수 Party로부터 충분한 confirmation을 받지 못했음을 나타냅니다.

**일반적인 원인:**
1. **Canton Coin 부족**: Party에 traffic top-up을 위한 CC가 충분하지 않음
2. **Validator offline**: 관련 Validator 중 하나가 down되었거나 연결할 수 없음
3. **Network latency**: 일시적인 network 문제

**해결 방법:**
1. 관련된 모든 Party의 Canton Coin balance 확인
2. 모든 Validator가 정상인지 검증
3. 필요한 경우 CC top-up:
   ```bash
   curl -X POST "http://localhost/api/validator/v0/wallet/buy-traffic-requests" \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
       "receiving_validator_party_id": "<validator-party-id>",
       "domain_id": "<synchronizer-id>",
       "traffic_amount": 100000,
       "tracking_id": "<unique-tracking-id>",
       "expires_at": <expiry-unix-timestamp-micros>
     }'
   ```
   전체 request/response schema는 [Traffic 구매](/sdks-tools/api-reference/splice-validator-api#buying-traffic)을 참조하세요.

Error message의 `unresponsiveParties`는 응답하지 않은 Party를 알려줍니다.
</Accordion>

<Accordion title="Command 제출 시 503 timeout error가 발생하는 이유는 무엇인가요?">
503 error는 일반적으로 Participant가 overloaded되었음을 나타냅니다. 다음을 확인하세요.

**Database queue overflow:**
```bash
grep "DB_STORAGE_DEGRADATION" participant.log
grep "queued tasks = 2000" participant.log
```

**해결 방법:**
1. Database size를 줄이도록 **pruning 활성화**
2. IOPS, memory 등 **database resource 증설**
3. Read-heavy workload에는 **PQS 고려**
4. Exponential backoff를 사용하는 **retry logic 구현**

많은 Transaction을 제출한다면 batch 처리 또는 rate limiting을 고려하세요.
</Accordion>

<Accordion title="ContentionOnSharedResources는 무엇을 의미하나요?">
이 error는 여러 Transaction이 같은 locked Contract 또는 resource를 두고 경쟁할 때 발생합니다.

**해결 방법:**
Exponential backoff를 사용하는 retry logic을 구현합니다.

```typescript
async function submitWithRetry(command, maxRetries = 5) {
  for (let i = 0; i < maxRetries; i++) {
    try {
      return await submit(command);
    } catch (e) {
      if (e.code === 'ABORTED' && i < maxRetries - 1) {
        await sleep(Math.pow(2, i) * 100);
        continue;
      }
      throw e;
    }
  }
}
```

Concurrent environment에서는 이 error가 **예상되며** retry strategy가 올바른 해결 방법입니다.
</Accordion>

<Accordion title="Transaction이 rejected되었을 때 어떻게 debug하나요?">
**Debug 단계:**

1. Error response에서 **trace ID를 가져옵니다.**

2. Trace ID를 **log에서 검색합니다.**
   ```bash
   grep "trace-id\":\"YOUR_TRACE_ID" participant.log validator.log
   ```

3. **일반적인 원인을 확인합니다.**
   - Authorization failure, Party가 authorized되지 않음
   - Package가 vetted되지 않음
   - Traffic 부족, Canton Coin
   - Contract가 이미 archived됨
   - Timeout 문제

4. 더 깊은 조사를 위해 **Canton Console을 사용합니다.**

</Accordion>

## Quickstart 문제

<AccordionGroup>

<Accordion title="Splice container가 계속 crash하면 어떻게 해야 하나요?">
**진단 단계:**

1. **Log 확인:**
   ```bash
   docker logs splice-validator-participant-1
   ```

2. **Resource 확인:**
   - Docker memory 8GB 이상
   - Docker CPU 4 core 이상

3. `.env` file의 **configuration error 확인**

**일반적인 해결 방법:**

Colima user:
```bash
colima stop
colima start --memory 8 --cpu 4
```

Docker Desktop:
- Settings → Resources → Memory → 8GB+
- Apply & Restart

그런 다음 clean start합니다.
```bash
make clean
make setup && make build
make start
```
</Accordion>

<Accordion title="make build가 env_file type error와 함께 실패하는 이유는 무엇인가요?">
**Error:**
```
'env_file[1]' expected type 'string', got unconvertible type 'map[string]interface {}'
```

**원인:** Docker Compose version이 2.27.0 미만입니다.

**해결 방법:**
```bash
# Check version
docker compose version

# Upgrade (Mac with Homebrew)
brew install docker-compose

# Or update Docker Desktop
```

Canton Quickstart에는 Docker Compose 2.27.0 이상이 필요합니다.
</Accordion>

<Accordion title="Quickstart가 시작되는 데 얼마나 걸리나요?">
충분한 hardware, 8GB RAM과 4개 CPU core를 사용하는 경우:

- **첫 실행:** 10~15분, image download 및 build
- **이후 실행:** 2~5분

Startup이 20분을 넘으면 다음을 확인하세요.
- 사용 가능한 system resource
- Error가 있는지 Docker log 확인
- Image download를 위한 network connectivity
</Accordion>

</AccordionGroup>

## Backup 및 recovery

<AccordionGroup>

<Accordion title="Validator identity를 어떻게 backup하나요?">
**Node ID dump export:**

<CANTON_DOCS_CN_FAQ_3 />


이 명령은 다음을 포함하는 JSON file을 생성합니다.
- Participant ID
- Cryptographic key pair, namespace/signing/encryption
- Authorized Store snapshot
- Version

이 backup을 **안전하게 보관하세요.** Validator identity를 recovery할 수 있습니다.

<Warning>
Node ID dump에는 Private Key가 포함됩니다. 조직의 Key Management policy에 따라 암호화하고 안전하게 보관하세요.
</Warning>
</Accordion>

<Accordion title="이전 version의 Node ID backup을 여전히 restore할 수 있나요?">
가능하지만 JSON file의 Key name을 update해야 할 수 있습니다.

**이전 형식, 0.4.x 이전:**
```json
{
  "keys": [
    { "name": "participant-namespace", ... },
    { "name": "participant-signing", ... },
    { "name": "participant-encryption", ... }
  ]
}
```

**현재 형식:**
```json
{
  "keys": [
    { "name": "namespace", ... },
    { "name": "signing", ... },
    { "name": "encryption", ... }
  ]
}
```

Restore 전에 Key name과 version field를 update하세요.
</Accordion>

<Accordion title="Upgrade 전에 무엇을 backup해야 하나요?">
**모든 upgrade 전에:**

1. **Database snapshot**, PostgreSQL dump
   ```bash
   pg_dump -h localhost -U cnadmin cantonnet_participant > backup.sql
   ```

2. **Persistent Volume snapshot**, Kubernetes
   - Validator PV
   - Participant PV

3. **Node ID dump**

<CANTON_DOCS_CN_FAQ_4 />


4. **Configuration file**
   - `validator-values.yaml`
   - `.env` file
   - Custom configuration

5. **현재 state 기록**
   - 현재 version
   - Migration ID
   - Database name
</Accordion>

## Performance 및 scaling

<AccordionGroup>

<Accordion title="Ledger API performance를 어떻게 개선하나요?">
**Performance 개선 option:**

1. ACS size를 줄이도록 **pruning 활성화:**
   ```yaml
   participantPruningSchedule:
     cron: "0 */10 * * * ?"
     maxDuration: 30m
     retention: 90d
   ```

2. Read-heavy workload에는 **PQS**, Participant Query Store를 사용하여 query를 main Participant에서 분리

3. **Database resource 증설:**
   - Storage upgrade, AWS의 gp2에서 gp3
   - IOPS 증설
   - Memory/CPU 추가

4. **Connection pool 조정:**

<CANTON_DOCS_CN_FAQ_CONNECTION_ALLOCATION_HOCON_0 />

5. **Client-side batching** 및 rate limiting 구현
</Accordion>

<Accordion title="Database가 350GB 이상으로 매우 큰 것이 정상인가요?">
Pruning 없이 오랫동안 실행된 MainNet Validator에서는 큰 database가 흔합니다.

**해결 방법:**

1. **Pruning 활성화**, 위 pruning FAQ 참조

2. 초기 pruning volume을 줄이도록 **보수적인 retention으로 시작:**
   ```yaml
   retention: 180d  # Start high
   maxDuration: 60m # Allow longer pruning runs
   ```

3. **Database growth를 monitoring**하고 필요에 따라 retention 조정

4. **Database maintenance 고려:**
   - PostgreSQL에서 VACUUM ANALYZE
   - Index optimization
</Accordion>

</AccordionGroup>

## Wallet 및 Canton Coin

<AccordionGroup>

<Accordion title="Traffic을 위해 Canton Coin을 어떻게 top-up하나요?">
**Wallet UI 사용:**
Wallet interface로 이동하여 top-up 기능을 사용합니다.

**API 사용:**
```bash
curl -X POST "http://localhost/api/validator/v0/wallet/buy-traffic-requests" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "receiving_validator_party_id": "<validator-party-id>",
    "domain_id": "<synchronizer-id>",
    "traffic_amount": 100000,
    "tracking_id": "<unique-tracking-id>",
    "expires_at": <expiry-unix-timestamp-micros>
  }'
```
이 호출은 request만 생성합니다. `/v0/wallet/buy-traffic-requests/{tracking_id}/status` endpoint에서 status를 확인하세요. 전체 request/response schema는 [Traffic 구매](/sdks-tools/api-reference/splice-validator-api#buying-traffic)을 참조하세요.

**자동 top-up:**
Validator configuration에서 automatic traffic purchase를 구성합니다.
<DamlAppdevTroubleshootingGuideOperationalIssuesL34 />
</Accordion>

<Accordion title="DevNet/TestNet에서 CC를 어떻게 tap하나요?">
**DevNet/TestNet은 test Canton Coin을 얻을 수 있는 faucet 기능을 제공합니다.**

1. Wallet UI에 access합니다.
2. "Tap" 또는 faucet 기능을 사용합니다.
3. Test CC가 Wallet에 적립됩니다.

<Info>
Test CC는 실제 가치가 없으며 DevNet과 TestNet의 testing 목적으로만 사용합니다.
</Info>
</Accordion>

<Accordion title="Upgrade 후 Wallet balance가 0이면 CC를 잃은 것인가요?">
아닙니다. CC가 손실되지 않았을 가능성이 큽니다. 일반적으로 sync 문제를 나타냅니다.

**단계:**
1. Validator가 완전히 resync될 때까지 기다립니다. Protocol upgrade 후에는 몇 시간이 걸릴 수 있습니다.
2. Log에서 error를 확인합니다.
   ```bash
   grep "503\|UNAVAILABLE" logs-validator.log
   ```
3. 모든 component가 정상인지 검증합니다.
4. 24시간 후에도 문제가 지속되면 log와 함께 support에 문의합니다.

올바른 balance를 표시하려면 Validator가 모든 historical event를 처리해야 합니다.
</Accordion>

<Accordion title="DevNet에서 TestNet을 거쳐 MainNet으로 어떻게 이동하나요?">
**DevNet → TestNet:**
1. TestNet IP whitelisting 요청
2. Configuration update:
   - Synchronizer URL 변경
   - SV sponsor address update
3. 새로 deploy하거나 use case에 따라 migrate

**TestNet → MainNet:**
1. MainNet Validator onboarding 완료
2. MainNet IP whitelisting 요청
3. [MainNet onboarding documentation](/global-synchronizer/deployment/onboarding-process) 준수
4. Production configuration으로 deploy

<Warning>
DevNet과 TestNet data는 MainNet으로 migrate할 수 없습니다. 새 deployment를 계획하세요.
</Warning>
</Accordion>
