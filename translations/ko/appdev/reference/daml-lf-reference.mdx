# Ledger API 개요

## Ledger API란 무엇인가

**Ledger API**는 모든 Participant Node가 제공하는 API입니다. 사용자는 Ledger API를 통해 ledger state에 접근하고 이를 조작합니다. Ledger API에는 gRPC와 JSON이라는 두 protocol이 있습니다. 핵심 service는 [gRPC]()와 [Protobuf]()로 구현됩니다. 모든 Ledger API service를 JSON Ledger API로도 제공하는 변환 계층이 추가로 존재합니다.

service에 대한 상위 수준의 소개는 `ledger-api-services`를 참고하세요.

각 service가 protobuf message를 통해 정의되는 방식을 설명하는 API protobuf documentation도 참고할 수 있습니다.

## Ledger API 접근 방법

Java binding을 통해 gRPC Ledger API에 접근할 수 있습니다.

JVM을 대상으로 하는 언어를 사용하지 않는다면 gRPC를 사용해 `proto` standard를 지원하는 여러 programming language용 Ledger API 접근 code를 생성할 수 있습니다.

gRPC API를 사용하지 않으려면 JSON Ledger API를 사용할 수도 있습니다. 이 API는 openapi 및 asyncapi description으로 정식 정의됩니다. OpenAPI standard를 지원하는 언어라면 OpenAPI [Generator]()를 사용해 client를 생성할 수 있습니다.

## Daml-LF

Daml source를 .dar file로 compile하면 내부 format은 Daml-LF입니다. Daml-LF는 Daml과 비슷하지만 핵심 기능 집합만 남긴 형태입니다. 표면 Daml syntax와 Daml-LF의 관계는 대략 Java와 JVM bytecode의 관계와 유사합니다.

사용자가 Daml-LF와 직접 상호작용할 필요는 없습니다. 다만 내부적으로 다음 용도에 사용됩니다.

- Ledger에서 Daml code 실행
- Ledger API를 통한 값 송수신
- Daml model과 상호작용할 다른 언어의 code 생성, 흔히 “codegen”이라고 부름

Daml assistant는 DAML-LF를 Java 또는 Typescript에서 자연스러운 Daml 표현으로 변환하는 두 code generator를 제공합니다.

### Daml-LF를 알아야 하는 경우

Daml-LF는 ledger로 보내거나 ledger에서 받는 object를 다룰 때만 실제로 관련됩니다. 제공되는 code generator를 사용한다면 Daml-LF를 알 필요가 없습니다.

그렇지 않다면 Daml code의 type이 Daml-LF 수준에서 어떤 모습인지 이해하는 것이 유용합니다. 이를 통해 Ledger API에서 어떤 값을 예상해야 하는지 알 수 있습니다.

예를 들어 Daml contract를 생성하는 application을 작성한다면 contract parameter로 전달할 값을 구성해야 합니다. 이 값은 해당 contract template의 Daml-LF type에 따라 결정됩니다. 따라서 Daml-LF type과 원래 Daml model의 type이 어떻게 대응하는지 이해해야 합니다.

대부분의 Daml type은 예상 가능한 방식으로 Daml-LF로 변환됩니다. 이 페이지에서는 모든 경우를 자세히 설명합니다.

# Daml-LF JSON encoding

JSON Ledger API에서 Daml-LF 값은 JSON 값으로 표현됩니다. 이 표현은 `CreateCommand` component의 `createArguments` field처럼 `JSON Ledger API`가 `Daml` record 또는 값을 요구할 때 사용됩니다. `JSON Ledger API`가 값을 반환할 때도 Daml 값이 JSON으로 변환됩니다. `Daml` type에 관한 자세한 내용은 `daml-ref-built-in-types`를 참고하세요.

| Daml-LF type | JSON type | 예시 |
| --- | --- | --- |
| `Int` | `string` 권장, number도 입력으로 허용. 범위: `[-9223372036854775808, 9223372036854775807]`. | `1234567890` |
| `Decimal` | `string` 권장, number도 입력으로 허용. 범위: `[-(10^38 - 1) / 10^10, (10^38 - 1) / 10^10]`. 형식: `-?[0-9]{1,28}(\.[0-9]{1,10})?`. | `"1234.56"` |
| `Timestamp` | `string` ISO 8601 timestamp. | `"2023-04-06T04:30:23.1234569Z"` |
| `Date` | `string` ISO 8601 date. | `"2023-04-06"` |
| `Unit` | 빈 JSON object. | `{}` |
| `Text` | `string` | `"my text value"` |
| `Bool` | `boolean` | `false` |
| `ContractId` | `string` | `"1234:56:7890"` |
| `Party` | `string` | `"Alice:1234567890"` |
| `Record` | record field마다 하나의 property를 갖는 JSON object. | `{"field1Label": "value of field1", "field2Label": "value of field2"}` |
| `List` | JSON array. | `[1, 7, 3, 4, 5]` |
| `TextMap` | text 값을 key로 사용하는 JSON object. | `{"key1": "value1", "key2": "value2"}` |
| `Variant` | `tag` 및 `value` property를 갖는 JSON object. | `{"tag": "InAccount", "value": {"number": "CH-1234567890", "bank": {}}}` |
| `Optional` | 값이 있으면 JSON 값, 비어 있으면 `null`. | `null` |
| `Enum` | `string` enum value name. | Daml `data Color = Red | Green | Blue`의 경우 `"Red"` |

<Note>
많은 언어, 특히 JavaScript가 JSON number에 IEEE double을 사용해 모든 Daml-LF 값을 정확히 표현할 수 없으므로 `Int` 및 `Decimal` 값에는 string을 권장합니다. 편의를 위해 parser는 JSON number와 string을 모두 허용합니다.
</Note>

<Note>
Timestamp parsing은 유연하며 `yyyy-mm-ddThh:mm:ss(.s+)?Z`를 허용합니다. microsecond를 넘는 sub-second 정밀도는 버립니다. local time을 실수로 전달할 위험을 줄이려면 UTC timezone designator를 반드시 포함해야 합니다.
</Note>

# Daml type이 Daml-LF로 변환되는 방식

이 페이지는 Daml type이 Daml-LF로 변환되는 방식을 보여줍니다. 생성되는 client interface를 이해하고 예측하는 데 도움이 되며, Ledger API 또는 다른 언어의 client binding을 사용하는 Daml 기반 application을 구축할 때 유용합니다.

## Primitive type

Daml built-in data type은 Daml-LF에 직접적으로 대응합니다.

이 section에서는 client application이 생성된 Daml-LF를 통해 상호작용할 수 있는 serializable type만 다룹니다. Serializable type은 그 값이 ledger에 존재할 수 있는 type입니다. function type, `Update` 및 `Scenario` type과 이들로 구성된 type은 제외되며 그 밖에도 여러 제약이 있습니다.

대부분의 built-in type은 Daml과 Daml-LF에서 이름이 같습니다. 정확한 대응은 다음과 같습니다.

| Daml primitive type | Daml-LF primitive type |
|---------------------|------------------------|
| `Int`               | `Int64`                |
| `Time`              | `Timestamp`            |
| `()`                | `Unit`                 |
| `[]`                | `List`                 |
| `Decimal`           | `Decimal`              |
| `Text`              | `Text`                 |
| `Date`              | `Date`                 |
| `Party`             | `Party`                |
| `Optional`          | `Optional`             |
| `ContractId`        | `ContractId`           |

Prelude module이 export하는 Daml primitive type만 위 Daml-LF primitive type에 대응한다는 점에 유의하세요. 따라서 `Party`라는 자체 type을 정의해도 Daml-LF primitive `Party`로 변환되지 않습니다.

## Tuple type

Daml tuple type constructor는 `T1, T2, …, TN` type을 받아 `(T1, T2, …, TN)` type을 만듭니다. Daml 표면 언어에서는 Prelude module을 통해 제공됩니다.

각 N에 대응하는 Daml-LF type constructor는 `daml-prim:DA.Types:TupleN`이며, N의 범위는 2 \<= N \<= 20입니다. 이 qualified name은 package name(`ghc-prim`)과 module name(`GHC.Tuple`)을 나타냅니다.

예를 들어 Daml pair type `(Int, Text)`는 `daml-prim:DA.Types:Tuple2 Int64 Text`로 변환됩니다.

## Data type

Daml-LF에는 세 종류의 data declaration이 있습니다.

- data 집합을 정의하는 **Record** type
- 여러 대안을 정의하는 **Variant** 또는 **sum** type
- type parameter나 argument가 없는 단순화된 **sum** type을 정의하는 **Enum**

Daml의 data type declaration은 `data` keyword로 시작하며 record, variant 또는 enum type으로 변환됩니다. 어떤 형태로 변환되는지 명확하지 않은 경우가 있으므로 이 section에서는 Daml data type과 Daml-LF 변환 결과의 여러 예를 제시합니다.

### Record declaration

이 section에서는 중괄호를 사용하는 Daml record syntax를 사용합니다.

| Daml declaration                           | Daml-LF 변환 결과                           |
|--------------------------------------------|--------------------------------------------|
| `data Foo = Foo { foo1: Int; foo2: Text }` | `record Foo ↦ { foo1: Int64; foo2: Text }` |
| `data Foo = Bar { bar1: Int; bar2: Text }` | `record Foo ↦ { bar1: Int64; bar2: Text }` |
| `data Foo = Foo { foo: Int }`              | `record Foo ↦ { foo: Int64 }`              |
| `data Foo = Bar { foo: Int }`              | `record Foo ↦ { foo: Int64 }`              |
| `data Foo = Foo {}`                        | `record Foo ↦ {}`                          |
| `data Foo = Bar {}`                        | `record Foo ↦ {}`                          |

### Variant declaration

| Daml declaration                                                               | Daml-LF 변환 결과                                                                                                                            |
|--------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| `data Foo = Bar Int \| Baz Text`                                                | `variant Foo ↦ Bar Int64 \| Baz Text`                                                                                                        |
| `data Foo a = Bar a \| Baz Text`                                                | `variant Foo a ↦ Bar a \| Baz Text`                                                                                                          |
| `data Foo = Bar Unit \| Baz Text`                                               | `variant Foo ↦ Bar Unit \| Baz Text`                                                                                                         |
| `data Foo = Bar Unit \| Baz`                                                    | `variant Foo ↦ Bar Unit \| Baz Unit`                                                                                                         |
| `data Foo a = Bar \| Baz`                                                       | `variant Foo a ↦ Bar Unit \| Baz Unit`                                                                                                       |
| `data Foo = Foo Int`                                                           | `variant Foo ↦ Foo Int64`                                                                                                                   |
| `data Foo = Bar Int`                                                           | `variant Foo ↦ Bar Int64`                                                                                                                   |
| `data Foo = Foo ()`                                                            | `variant Foo ↦ Foo Unit`                                                                                                                    |
| `data Foo = Bar ()`                                                            | `variant Foo ↦ Bar Unit`                                                                                                                    |
| `data Foo = Bar { bar: Int } \| Baz Text`                                       | `variant Foo ↦ Bar Foo.Bar \| Baz Text`, `record Foo.Bar ↦ { bar: Int64 }`                                                                   |
| `data Foo = Foo { foo: Int } \| Baz Text`                                       | `variant Foo ↦ Foo Foo.Foo \| Baz Text`, `record Foo.Foo ↦ { foo: Int64 }`                                                                   |
| `data Foo = Bar { bar1: Int; bar2: Decimal } \| Baz Text`                       | `variant Foo ↦ Bar Foo.Bar \| Baz Text`, `record Foo.Bar ↦ { bar1: Int64; bar2: Decimal }`                                                   |
| `data Foo = Bar { bar1: Int; bar2: Decimal } \| Baz { baz1: Text; baz2: Date }` | `variant Foo ↦ Bar Foo.Bar \| Baz Foo.Baz`, `record Foo.Bar ↦ { bar1: Int64; bar2: Decimal }`, `record Foo.Baz ↦ { baz1: Text; baz2: Date }` |

### Enum declaration

| Daml declaration                  | Daml-LF declaration               |
|-----------------------------------|-----------------------------------|
| `data Foo = Bar \| Baz`            | `enum Foo ↦ Bar \| Baz`            |
| `data Color = Red \| Green \| Blue` | `enum Color ↦ Red \| Green \| Blue` |

### 금지되는 declaration

Daml에서는 가능할 것으로 예상하지만 Daml-LF 때문에 허용되지 않는 두 가지 주의 사항이 있습니다.

첫째, constructor가 하나뿐인 data type은 record인지 variant type인지 명확해야 합니다. 구체적으로 `data Foo = Foo` data type declaration은 record와 variant 중 무엇을 선언하는지 불명확하므로 compile-time error를 발생시킵니다.

이를 해결하려면 구분을 명시해야 합니다. field가 없는 record type은 `data Foo = Foo {}`로 선언하고, unit argument를 받는 단일 constructor variant는 `data Foo = Foo ()`로 선언합니다.

둘째, data type declaration의 constructor는 label이 없는 argument type을 최대 하나만 가질 수 있습니다. 이 제약은 여러 client language에서 Daml-LF type을 직접적으로 encoding할 수 있게 합니다.

| 금지되는 declaration            | 대안                                                                                                        |
|---------------------------------|-------------------------------------------------------------------------------------------------------------|
| `data Foo = Foo`                | `record Foo ↦ {}`를 만들려면 `data Foo = Foo {}`, `variant Foo ↦ Foo Unit`을 만들려면 `data Foo = Foo ()` |
| `data Foo = Bar`                | `record Foo ↦ {}`를 만들려면 `data Foo = Bar {}`, `variant Foo ↦ Bar Unit`을 만들려면 `data Foo = Bar ()` |
| `data Foo = Foo Int Text`       | record declaration으로 constructor argument에 이름을 지정합니다. 예: `data Foo = Foo { x: Int; y: Text }` |
| `data Foo = Bar Int Text`       | record declaration으로 constructor argument에 이름을 지정합니다. 예: `data Foo = Bar { x: Int; y: Text }` |
| `data Foo = Bar \| Baz Int Text` | Baz constructor argument에 이름을 지정합니다. 예: `data Foo = Bar \| Baz { x: Int; y: Text }`             |

### Upgrade 제약

datatype의 Daml-LF 표현 형태는 Smart Contract Upgrade 방식에 제약을 줍니다. record만 field를 추가할 수 있고 variant와 enum만 새 constructor를 추가할 수 있습니다. 한번 선택한 datatype 형태는 변경할 수 없습니다.

따라서 어떤 datatype 형태가 적합한지는 계획한 upgrade 동작에 크게 좌우됩니다. 예를 들어 다음 datatype은

``` 
data Foo = Foo { foo: Int }
```

Daml-LF에서 record로 변환됩니다.

``` 
record Foo ↦ { foo: Int64 }
```

field를 추가해도 형태가 바뀌지 않으므로 upgrade 시 field를 추가할 수 있습니다.

``` 
-- Add a field to Foo in version 2 of its package
data Foo = Foo { foo: Int, newField: Int }
```

``` 
// Still a record
record Foo ↦ { foo: Int64, newField: Int }
```

하지만 새 constructor를 추가하면 record에서 variant로 형태가 바뀌므로 허용되지 않습니다.

``` 
-- Add a constructor to Foo in version 2 of its package
data Foo
  = Foo { foo: Int }
  | NewConstructor
```

``` 
// Flavour changed from a record to a variant
variant Foo ↦ Foo Foo.Foo | NewConstructor
```

위와 같이 field가 있는 variant는 하나의 variant와 각 constructor에 대응하는 record로 desugar됩니다.

``` 
-- Add a constructor to Foo in version
data Foo
  = Bar { bar1: Int; bar2: Decimal }
  | Baz { baz1: Text; baz2: Date }
```

``` 
// Desugars to a variant datatype and two record datatypes, one for each
// of the variant's constructors
variant Foo ↦ Bar Foo.Bar | Baz Foo.Baz
record Foo.Bar ↦ { bar1: Int64; bar2: Decimal }
record Foo.Baz ↦ { baz1: Text; baz2: Date }
```

따라서 이 datatype에서는 constructor field를 upgrade하면서 동시에 새 constructor를 추가할 수 있습니다. 두 변경 모두 기반 Daml-LF definition에 대해 유효한 upgrade이기 때문입니다.

예를 들어 `bar3` field와 `Bat` constructor를 추가하면 다음과 같습니다.

``` 
data Foo
  = Bar { bar1: Int; bar2: Decimal, bar3: Text } -- Add a bar3 field
  | Baz { baz1: Text; baz2: Date }
  | Bat { bat1: Int } -- Add a Bat constructor
```

``` 
variant Foo ↦ Bar Foo.Bar | Baz Foo.Baz | Bat Foo.Bat // Variant adds a constructor - allowed under upgrades
record Foo.Bar ↦ { bar1: Int64; bar2: Decimal; bar3: Text } // Record adds a variant - allowed under upgrades
record Foo.Baz ↦ { baz1: Text; baz2: Date }
record Foo.Bat ↦ { bat1: Int64 } // New variant constructor's underlying datatype
```

요약하면 시간이 지나면서 constructor를 추가할 계획이면 datatype을 variant로 정의해야 합니다. field를 추가할 계획이면 record로 정의해야 합니다. 둘 다 필요하다면 field를 가진 variant로 정의해야 합니다.

Smart Contract Upgrade가 datatype 형태별로 부과하는 제약은 Limitations in Upgrading Variants에서 더 자세히 설명합니다.

이 declaration은 모두 template가 정의된 module의 최상위 수준에 위치합니다.

## 특수 문자가 포함된 이름

Daml의 type, template, choice, field 및 variant data constructor 이름은 더 엄격한 Daml-LF 규칙에 맞게 변환됩니다. ASCII 문자, 숫자 및 `_` underscore는 Daml-LF에서도 바뀌지 않으며 그 밖의 문자는 다음과 같이 변형해야 합니다.

- `$`는 `$$`로 바뀝니다.
- 65536 미만의 Unicode codepoint는 `$uABCD`로 변환됩니다. `ABCD`는 해당 codepoint를 소문자 `a-f`만 사용한 정확히 네 자리의 zero-padded hexadecimal digit로 표현한 값입니다.
- 그보다 큰 Unicode codepoint는 `$UABCD1234`로 변환됩니다. `ABCD1234`는 동일한 `a-f` 규칙을 적용한 정확히 여덟 자리의 zero-padded hexadecimal digit입니다.

| Daml name | Daml-LF identifier       |
|-----------|--------------------------|
| `Foo_bar` | `Foo_bar`                |
| `baz'`    | `baz$u0027`              |
| `:+:`     | `$u003a$u002b$u003a`     |
| `naïveté` | `na$u00efvet$u00e9`      |
| `:🙂:`    | `$u003a$U0001f642$u003a` |

# Daml package 및 archive(.dar) file

Daml package를 compile하면 DAR(`.dar`) file이라는 최종 artifact로 묶입니다. DAR file은 다른 file 없이 package의 template를 실행하는 데 필요한 모든 code와 logic을 담습니다.

예를 들어 `dep` dependency 하나를 갖는 단순한 `mypkg` package를 가정합니다.

```yaml
name: mypkg
version: 1.0.0
source: daml
...
dependencies:
- daml-prim
- daml-stdlib
data-dependencies:
- /path/to/dep-1.0.0.dar
```

`dpm build` command는 package를 compile하고 마지막 줄에 생성된 DAR path를 출력합니다.

``` sh
> dpm build

Running single package build of mypkg as no multi-package.yaml was found.
...
Compiling mypkg to a DAR.
...
Created .daml/dist/mypkg-1.0.0.dar
```

이 DAR에는 package의 전체 code와 모든 dependency code가 포함됩니다.

## Archive file 구조

DAR는 실제로 여러 file을 포함하는 zip file입니다. 이 file들은 함께 작동해 compile된 code를 실행하는 데 ledger가 알아야 할 모든 정보를 제공합니다.

``` sh
> unzip -Z1 .daml/dist/mypkg-1.0.0.dar

META-INF/MANIFEST.MF
...
mypkg-1.0.0-<mypkg-package-id>/dep-1.0.0-<dep-package-id>.dalf
mypkg-1.0.0-<mypkg-package-id>/Main.daml
mypkg-1.0.0-<mypkg-package-id>/Main.hi
mypkg-1.0.0-<mypkg-package-id>/Main.hie
mypkg-1.0.0-<mypkg-package-id>/mypkg-1.0.0-<mypkg-package-id>.dalf
```

DAR에 포함된 file 대부분은 DALF file(`.dalf`)입니다. 각 `.dalf` file에는 특정 package의 compile된 전체 code가 들어 있습니다.

DALF file 중 하나는 DAR의 compile 대상인 "main" 또는 "primary" package입니다. 이 DALF에는 DAR을 만들 때 사용한 Daml code의 template, interface, datatype 및 function definition이 포함됩니다. 이 예시에서는 위의 `mypkg-1.0.0-<mypkg-package-id>.dalf` file입니다.

나머지 DALF file은 "main" package 실행에 필요한 dependency package입니다. 여기에는 `dep-1.0.0-<dep-package-id>.dalf`와 `daml-prim` 및 `daml-stdlib` library의 여러 DALF file이 포함됩니다.

이 밖에 다음 file이 포함됩니다.

- DAR에 있는 나머지 artifact의 metadata를 담은 `MANIFEST.MF` file
  - DAR로 compile된 "main" package name
  - main package의 모든 dependency 목록
  - package에 관한 추가 metadata
- primary package의 source code(`.daml`). DAR consumer는 이를 사용해 실행 중인 DALF가 내부 code와 대응하는지 확인할 수 있습니다. 다른 project가 DAR을 dependency로 포함할 때 Daml Studio가 jump-to-definition 같은 code intelligence를 제공하는 데도 사용합니다.
- primary package의 interface file(`.hi`, `.hie`, `.conf`). Daml Studio가 jump-to-definition을 제공하는 데도 사용합니다.

source code와 interface file은 Daml Studio 외 다른 tool에는 필요하지 않습니다. participant runner 같은 consumer는 이를 DAR에서 안전하게 제거할 수 있습니다.

## DALF file과 Daml file의 차이

DAR file이 모든 package source code를 직접 담지 않고 DALF file을 포함하는 이유는 자주 묻는 질문입니다.

그 이유를 이해하려면 Daml file과 DALF file의 차이를 알아야 합니다.

- Daml file에는 Daml developer가 작성한 Daml source code가 들어 있습니다. Daml source code는 사람이 작성하고 읽을 수 있으며 general-purpose programming language처럼 읽을 수 있습니다.
- 반면 DALF file에는 Daml-LF의 compact한 binary encoding 표현이 들어 있습니다. Daml-LF는 제약이 많고 비교적 단순한 computer-executable programming language입니다. 사람이 읽거나 작성하기 위한 것이 아니라 deterministic하고 빠르고 안전하게 실행되도록 설계됐습니다.

DAR file은 실행하고 전달하기 위한 artifact이므로 직접 실행할 수 있는 Daml-LF를 주로 포함합니다. compile 원본인 Daml code를 저장할 필요는 없습니다.

## Dependency로 사용하는 DAR

새 project가 다른 package에 의존해야 하면 해당 package를 compile한 DAR을 새 project의 `daml.yaml`에 data-dependency로 제공합니다.

예를 들어 `mypkg` package를 dependency로 사용하는 새 `next-project` package를 가정합니다.

```yaml
name: next-project
version: 1.0.0
source: daml
dependencies:
- daml-prim
- daml-stdlib
data-dependencies:
- ../mypkg/.daml/dist/mypkg-1.0.0.dar
```

이 경우 compile process는 `mypkg-1.0.0` DAR을 풀고 primary package를 찾아 `next-project` 내부 code의 dependency로 제공합니다. `next-project`를 compile하면 `mypkg` package의 dependency를 포함해 `mypkg` DAR 내부의 모든 DALF file이 유지됩니다.

일반적으로 추가 DAR dependency가 있는 package를 DAR로 compile하면 해당 dependency DAR을 풀고 모든 DALF file을 새 output DAR로 복사합니다. 하지만 DALF file과 달리 dependency DAR의 manifest, source code 및 interface file은 복사하지 않습니다. DAR에는 해당 DAR primary package의 source code와 interface file만 포함될 수 있습니다.

DAR 및 DALF file을 열고 검사하는 방법은 Daml archive file parsing documentation을 참고하세요.

# Daml archive file parsing 방법

Daml project를 compile하면 Daml Archive의 약자인 DAR(`.dar` extension)이 생성됩니다. Daml compiler는 이 archive를 검사하는 command를 제공합니다.

## DAR file 검사

`dpm damlc inspect-dar /path/to/your.dar`을 실행하면 내부 file 목록과 package 및 package id 목록을 사람이 읽을 수 있는 형태로 확인할 수 있습니다. 방금 build한 project의 package id를 찾을 때 유용합니다.

예를 들어 `dep` package에 의존하는 `mypkg` package를 살펴보겠습니다.

```yaml
name: mypkg
version: 1.0.0
source: daml/Main.daml
...
data-dependencies:
- ../dep/.daml/dist/dep-1.0.0.dar
```

```yaml
name: dep
version: 1.0.0
source: daml/Dep.daml
...
```

`mypkg-1.0.0`을 DAR로 compile한 뒤 이를 검사해 `mypkg` package와 dependency인 `dep`이 모두 포함됐는지 확인할 수 있습니다.

``` sh
> dpm build
...
Created .daml/dist/mypkg-1.0.0.dar

> dpm damlc inspect-dar .daml/dist/mypkg-1.0.0.dar

...

mypkg-1.0.0-<mypkg-package-id>/mypkg-1.0.0-<mypkg-package-id>.dalf
mypkg-1.0.0-<mypkg-package-id>/MyPkg.daml
mypkg-1.0.0-<mypkg-package-id>/MyPkg.hi
mypkg-1.0.0-<mypkg-package-id>/MyPkg.hie
META-INF/MANIFEST.MF

...

```

첫 section은 DAR의 모든 file을 보여주고, 두 번째 section은 archive에 있는 각 DALF의 package name과 package ID를 보여줍니다.

## DAR 및 DALF file parsing

Scala code에서 DAR 또는 DALF file을 parse하려면 Maven의 `com-daml:daml-lf-archive-reader` library가 여러 decoder를 포함한 Scala package object `com.digitalasset.daml.lf.archive`를 제공합니다. 아래에서는 decoder의 일반적인 input/output type과 원하는 input/output에 따른 decoder 선택 방법을 설명합니다. 자세한 input, output 및 decoder 정보는 Maven에서 관련 library source code를 참고하세요.

### Output type

package를 decode할 때 decoder는 필요에 따라 여러 output 중 하나를 반환할 수 있습니다.

- package 전체 code가 필요하면 tuple `(PackageId, Package)`를 반환하는 decoder를 선택합니다.

  여기서 `PackageId`는 Maven의 `com.daml:daml-lf-data` library에 있는 `com.digitalasset.daml.lf.language.Ref`의 string과 유사한 type입니다. `Package`는 package 전체 구조를 나타내며 Maven의 `com.daml:daml-lf-language` library에 있는 `com.digitalasset.daml.lf.language.Ast`에서 제공합니다.

  package를 완전히 decode하면 다음 두 방식보다 처리 시간이 오래 걸리므로 package 전체 code가 필요할 때만 사용합니다.

  예를 들어 Maven의 `com-daml:daml-lf-api-type-signature` library에 있는 `com.digitalasset.daml.lf.typesig.reader.SignatureReader` class는 `(PackageId, Package)` pair를 받아 `com.digitalasset.daml.lf.typesig.PackageSignature`를 생성합니다. 이 type 역시 `api-type-signature` package에서 제공하며 package의 모든 template, datatype 및 interface를 지정합니다.

- package protobuf의 가장 단순한 표현만 필요하면 Maven의 `com-daml:daml-lf-archive` library에 있는 `com.digitalasset.daml.lf.ArchivePayload`를 반환하는 decoder를 선택합니다. package의 내부 protobuf 표현을 다룰 때만 필요합니다.

- package의 byte 표현과 hash만 필요하면 Maven의 `com-daml:daml-lf-archive-proto` library에 있는 `Archive`를 반환하는 decoder를 사용합니다. 이 경우 decoder는 metadata나 code 같은 실제 package content를 decode하지 않습니다.

### Input type

decoder는 DALF file, DAR file 또는 두 형식을 모두 입력으로 받을 수 있습니다.

- DALF file을 받는 decoder는 해당 DALF의 단일 package를 위 세 output type 중 하나로 parse합니다.
- DAR file을 받는 decoder는 DAR의 여러 package를 `Dar[X]` struct로 parse합니다. 이는 DAR을 두 public field `main: X`와 `dependencies: List[X]`로 encoding하는 case class입니다.
- 두 형식을 모두 받는 decoder는 항상 `Dar[X]`를 생성합니다. DAR을 받으면 일반 DAR decoder처럼 작동합니다. DALF를 받으면 이를 단일 package로 decode하고 `main` package와 빈 dependency 목록을 갖는 `Dar[X]`를 반환합니다.

### Decoder

DALF를 읽는 decoder는 `readArchiveFromFile(file: java.io.File): Either[Error, X]` method를 제공하는 `GenReader[X]` instance입니다.

- `val ArchiveReader: GenReader[ArchivePayload]`

  `ArchiveReader.readArchiveFromFile(new java.io.File("<path-to-dalf>"))`를 실행해 dalf file의 `ArchivePayload`를 parse합니다.

- `val ArchiveDecoder: GenReader[(PackageId, Ast.Package)]`

  `ArchiveDecoder.readArchiveFromFile(new java.io.File("<path-to-dalf>"))`를 실행해 dalf file의 `(Ref.PackageId, Ast.Package)`를 parse합니다.

- `val ArchiveParser: GenReader[DamlLf.Archive]`

  `ArchiveParser.readArchiveFromFile(new java.io.File("<path-to-dalf>"))`를 실행해 dalf file의 `DamlLf.Archive`를 parse합니다.

DAR을 읽는 decoder는 `readArchiveFromFile(file: java.io.File): Either[Error, Dar[X]]` method를 제공하는 `GenDarReader` instance입니다.

- `val DarReader: GenDarReader[ArchivePayload]`

  `DarReader.readArchiveFromFile(new java.io.File("<path-to-dar>"))`를 실행해 dar file의 `Dar[ArchivePayload]`를 parse합니다.

- `val DarDecoder: GenDarReader[(PackageId, Ast.Package)]`

  `DarDecoder.readArchiveFromFile(new java.io.File("<path-to-dar>"))`를 실행해 dar file의 `Dar[(Ref.PackageId, Ast.Package)]`를 parse합니다.

- `val DarParser: GenDarReader[DamlLf.Archive]`

  `DarParser.readArchiveFromFile(new java.io.File("<path-to-dar>"))`를 실행해 dar file의 `Dar[DamlLf.Archive]`를 parse합니다.

DAR을 읽는 universal decoder는 `readFile(file: java.io.File): Either[Error, Dar[X]]` method를 제공하는 `GenUniversalArchiveReader` instance입니다.

- `val UniversalArchiveReader: GenUniversalArchiveReader[ArchivePayload]`

  `UniversalArchiveReader.readFile(new java.io.File("<path-to-dar-or-dalf>"))`를 실행해 dar file의 `Dar[ArchivePayload]`를 parse합니다.

- `val UniversalArchiveDecoder: GenUniversalArchiveReader[(PackageId, Ast.Package)]`

  `UniversalArchiveDecoder.readFile(new java.io.File("<path-to-dar-or-dalf>"))`를 실행해 dar file의 `Dar[(Ref.PackageId, Ast.Package)]`를 parse합니다.

### 예시

`daml-lf-archive-reader` library와 함께 Scala REPL을 실행해 `mypkg` DAR을 대화형으로 parse할 수 있습니다.

```scala
scala> // Start a REPL
scala> val darEither = DarDecoder.readArchiveFromFile(".daml/dist/mypkg-1.0.0.dar")
val dar: Either[Error, Dar[(Ref.PackageId, Ast.Package)]]
Right(Dar((..., GenPackage(Map(Main -> ...
...

scala> // Extract the resulting value
scala> val dar = darEither.toOption.get

scala> :t dar.main
(Ref.PackageId, Ast.Package)

scala> :t dar.dependencies
List[(Ref.PackageId, Ast.Package)]
```

Dar datatype에는 main package와 dependency를 하나의 list로 반환하는 `.all` method도 있습니다. 여기에 `_1`을 mapping하면 DAR의 모든 package ID를 얻습니다.

```scala
scala> dar.all.map(_._1)
val res1: List[Ref.PackageId] = List(224..., 54f..., ...)
```

`Ast.Package` datatype의 `.metadata.name` field를 사용해 DAR의 모든 dependency package name을 얻습니다.

```scala
scala> dar.dependencies.map(_._2.metadata.name)
val res2: List[com.digitalasset.daml.lf.data.Ref.PackageName] = List(daml-prim, daml-prim-DA-Exception-ArithmeticError, ...
```
