Daml application과 Ledger의 상호 작용은 본질적으로 비동기식입니다. Application이 Ledger에 command를 보내면 일정 시간이 지난 후에야 Ledger에서 해당 command의 효과를 확인합니다. 이 시간 동안 여러 문제가 발생할 수 있습니다.

- Application이 crash할 수 있습니다.
- Participant Node가 crash할 수 있습니다.
- Network에서 message가 손실될 수 있습니다.
- 높은 load로 인해 Ledger 응답이 느려질 수 있습니다.

의도한 Ledger 변경이 두 번 실행되지 않도록 하려면 application이 모든 failure scenario를 견고하게 처리해야 합니다. 이 guide에서는 다음 주제를 다룹니다.

- Command Deduplication의 작동 방식
- Application에서 Command Deduplication을 효과적으로 사용하는 방법

## Command Deduplication의 작동 방식

Command submission의 다음 field가 Command Deduplication에 사용됩니다. 처음 세 field는 의도한 Ledger 변경을 식별하는 change ID를 구성합니다.

- act_as는 제출 Party를 정의합니다.
- User ID는 command를 제출하는 user를 식별합니다.
- Command ID는 의도한 Ledger 변경을 식별하도록 user가 선택합니다.
- Deduplication period는 같은 change ID의 이전 submission이 Command Completion Service의 completion event에 나타난 대로 accepted되지 않았어야 하는 기간을 지정합니다. 해당 기간에 그런 변경이 accepted되었다면 현재 submission은 rejected됩니다. 이 기간은 deduplication duration 또는 deduplication offset(inclusive)으로 지정합니다.
- Submission ID는 특정 submission을 식별하도록 application이 선택합니다. Application이 특정 submission을 특정 completion과 연결할 수 있도록 대응하는 completion event에 포함됩니다. Application은 Submission ID를 절대로 재사용해서는 안 됩니다.

Ledger는 submission에 지정된 deduplication period를 임의로 연장할 수 있습니다.

<Note>
Maximum deduplication duration은 Participant가 지원한다고 보장하는 deduplication period의 길이입니다.
</Note>

Ledger가 선택한 deduplication period를 *effective deduplication period*라고 합니다. Ledger는 요청된 deduplication duration을 effective deduplication offset으로 변환하거나 그 반대로 변환할 수도 있습니다. Effective deduplication period는 command completion event의 deduplication duration 또는 deduplication offset field에 보고됩니다.

다음 중 하나 이상에 해당하면 command submission을 **duplicate submission**으로 간주합니다.

- 제출 Participant의 Completion Service에 *effective* deduplication period 이내의 같은 change ID에 대한 successful completion event가 있습니다.
- Participant 또는 Daml Ledger가 Command Deduplication을 수행할 때 같은 change ID의 다른 command submission이 in-flight 상태임을 알고 있습니다.

Command Deduplication 결과는 다음과 같이 전달됩니다.

- Command Service를 통한 command submission은 [gRPC deadline](https://grpc.io/blog/deadlines/)을 초과하지 않은 경우 동기 gRPC response로 Command Deduplication 결과를 나타냅니다. 참고로 결과가 Command Completion Service의 completion event로 추가로 나타날 수도 있지만, Command Service를 사용하는 application은 일반적으로 completion event를 처리할 필요가 없습니다.

- Command Submission Service를 통한 command submission은 결과를 동기 gRPC response로 나타내거나 Command Completion Service를 통해 비동기식으로 나타낼 수 있습니다. 특히 Command Submission Service가 gRPC status code `OK`로 submission을 acknowledge하더라도 duplicate일 수 있습니다.

결과 전달 방식과 관계없이 Command Deduplication은 command submission에 대해 다음 결과를 생성합니다.

- Daml Ledger 또는 in-flight 상태에 같은 change ID의 conflicting submission이 없으면 completion event와 경우에 따라 response가 submission 결과(success 또는 gRPC error)를 전달합니다. `error_codes`는 error 전달 방식을 설명합니다.

- gRPC status code `ALREADY_EXISTS`와 error code ID DUPLICATE_COMMAND는 effective deduplication period 이내에 같은 change ID의 이전 command completion이 있음을 나타냅니다.

- gRPC status code `ABORTED`와 error code id SUBMISSION_ALREADY_IN_FLIGHT는 이 submission을 처리할 때 같은 change ID의 다른 submission이 in-flight 상태였음을 나타냅니다.

- gRPC status code `FAILED_PRECONDITION`과 error code id INVALID_DEDUPLICATION_PERIOD는 지정한 deduplication period가 지원되지 않음을 나타냅니다. Metadata의 `longest_duration` 또는 `earliest_offset` field는 현재 Ledger API endpoint에서 지원하는 가장 긴 duration 또는 가장 이른 offset을 지정합니다. 두 field 중 하나 이상이 존재합니다.

  구성된 maximum deduplication duration 이하의 deduplication duration과 해당 duration 이내에 publish된 deduplication offset은 모두 이 error를 일으키지 않아야 합니다. Participant는 재량에 따라 더 긴 기간을 허용할 수 있습니다.

- Offset으로 표현된 deduplication period를 지정할 때 gRPC status code `FAILED_PRECONDITION`과 error code id PARTICIPANT_PRUNED_DATA_ACCESSED가 나타나면 지정한 deduplication offset이 pruned되었음을 뜻합니다. Metadata의 `earliest_offset` field는 마지막으로 pruned된 offset을 지정합니다.

Deduplication이 의도대로 작동하려면 같은 Ledger 변경에 대한 모든 submission을 같은 Participant를 통해 제출해야 합니다. Submission이 duplicate인지 여부는 completion event로 결정되며, 기본적으로 Participant는 바로 그 Participant를 통해 요청된 submission의 completion event만 출력합니다.

## Command Deduplication 사용 방법

Ledger 변경을 정확히 한 번 수행하려면 이전 submission이 손실되었을 때 application이 command를 다시 제출해야 합니다. 하지만 application은 일반적으로 손실된 submission과 Ledger의 느린 submission 처리를 구분할 수 없습니다. Command Deduplication을 사용하면 application은 command가 실행될 때까지 다시 제출하고 이후 모든 duplicate submission을 reject할 수 있습니다.

일부 Ledger 변경은 최대 한 번만 실행될 수 있으므로 Command Deduplication이 필요하지 않습니다. 예를 들어 제출된 command가 특정 Contract ID에서 consuming Choice를 exercise한다면 모든 Contract는 최대 한 번만 archived될 수 있으므로 이 command도 최대 한 번만 accepted될 수 있습니다. 이와 같은 변경의 모든 duplicate submission은 CONTRACT_NOT_ACTIVE로 rejected됩니다.

반면 Create command는 Ledger에 도달하는 submission마다 지정한 Template의 새로운 Contract instance를 생성합니다. 단, Template precondition이나 Contract Key uniqueness 같은 다른 constraint를 위반하지 않아야 합니다. 마찬가지로 non-consuming Choice에 대한 Exercise command 또는 Exercise-By-Key command는 여러 번 제출되면 여러 번 실행될 수 있습니다. Command Deduplication을 사용하면 application이 이전 submission이 손실되었다고 판단해 다시 제출하거나 crash 중에 이미 제출했다는 사실을 잊더라도 이러한 의도한 Ledger 변경이 deduplication period 이내에 한 번만 실행되도록 보장할 수 있습니다.

### Processing time bound를 아는 경우

이 전략을 사용하려면 application clock을 기준으로 Daml Ledger의 processing time과 forward clock drift에 대한 bound `B`를 추정해야 합니다. 모든 retry에 걸쳐 측정한 processing time이 추정치 `B`보다 길면 Ledger 변경이 여러 번 적용될 수 있습니다. 이 caveat 아래에서는 Command Service 또는 Command Submission Service와 Command Completion Service를 사용하는 application에 다음 전략을 적용할 수 있습니다.

<Note>
Bound `B`는 구성된 maximum deduplication duration 이하여야 합니다. 그렇지 않으면 Ledger가 더 긴 deduplication duration을 허용한다는 데 의존하게 됩니다. 이러한 의존은 application을 다른 Daml Ledger로 port하기 어렵게 만들고, Ledger가 자체 재량으로 그러한 연장 duration의 허용을 중단할 수 있어 취약합니다.
</Note>

1.  같은 Ledger 변경에는 항상 같은 Command ID가 할당되도록 Command ID를 선택합니다. Command ID를 deterministic하게 결정하거나, 예를 들어 Contract payload에 globally unique identifier가 있으면 이를 Command ID로 사용할 수 있습니다. 또는 Command ID를 무작위로 선택하고 Ledger 변경과 함께 persist하여 application이 crash 후 restart하고 다시 제출할 때 같은 Command ID를 사용할 수 있게 합니다. 참고로 같은 Ledger 변경의 모든 command 재제출에는 같은 Command ID를 할당해야 합니다. 이는 application crash/restart 후 recovery procedure에 유용합니다. Crash 후 application은 일반적으로 crash 전에 command set을 제출했는지 알 수 없습니다. 확실하지 않으면 같은 Command ID를 사용하여 command를 다시 제출합니다. Crash 전에 command가 제출되었다면 Ledger의 Command Deduplication이 재제출을 reject합니다.

2.  Command Submission Service를 사용할 때는 State Service에서 최근 offset `OFF1`을 가져옵니다. 예를 들면 현재 Ledger end를 사용합니다.

3.  다음 parameter로 command를 제출합니다.

    - Command ID를 1단계에서 선택한 Command ID로 설정합니다.

    - Deduplication duration을 bound `B`로 설정합니다. 참고로 Ledger configuration update가 maximum deduplication duration을 줄이는 경우에 대비하여 deduplication duration을 원하는 bound `B`로 명시적으로 설정하는 것이 좋습니다. Bound `B`를 사용하면 Ledger가 더 이상 길이 `B`의 deduplication duration을 지원하지 않을 때 INVALID_DEDUPLICATION_PERIOD error로 문제를 알 수 있습니다. Deduplication period를 생략하면 현재 유효한 maximum deduplication duration이 사용됩니다. 이 경우 Ledger configuration update가 deduplication period를 조용히 줄여 deduplication analysis를 무효화할 수 있습니다.

    - Submission ID를 임의의 UUID 같은 새로운 값으로 설정합니다.

    - Timeout(gRPC deadline)을 예상 submission processing time(Command Service) 또는 submission hand-off time(Command Submission Service)으로 설정합니다.

      **Submission processing time**은 application이 Command Service에 submission을 보낸 시점부터 acceptance 또는 rejection을 받을 때까지의 시간입니다. Timeout이 발생하지 않으면 동기식으로 받습니다. **Submission hand-off time**은 application이 Command Submission Service에 submission을 보낸 시점부터 이 gRPC call의 동기 response를 받을 때까지의 시간입니다. RPC timeout 후 application은 submission이 손실된 것으로 간주하고 retry loop로 들어갑니다. 이 timeout은 일반적으로 deduplication duration보다 훨씬 짧습니다.

4.  RPC call이 response를 반환할 때까지 기다립니다.

    - `OK` 이외의 status code는 error handling에 따라 처리해야 합니다.

    - Command Service를 사용할 때 response의 status code가 `OK`이면 Ledger 변경이 적용된 것입니다. Success를 보고할 수 있습니다.

    - Command Submission Service를 사용할 때는 3단계에서 선택한 change ID와 Submission ID의 completion event가 보일 때까지 `actAs`에 대한 completion을 `OFF1`(exclusive)부터 Command Completion Service로 subscribe합니다. Completion status가 `OK`이면 Ledger 변경이 적용된 것이므로 success를 보고할 수 있습니다. 그 밖의 status code는 error handling에 따라 처리해야 합니다.

      Command Submission Service는 system의 관련 부분이 영구적으로 unavailable해지는 경우를 제외하면 결국 completion event가 생성될 submission만 acknowledge하므로 이 단계에는 timeout이 필요하지 않습니다.

#### Error Handling

Command submission RPC call 또는 completion event의 status code가 `OK`가 아닐 때는 error handling이 필요합니다. 다음 표에는 status code(`STATUS_CODE`로 표기)와 error code(link가 있는 대문자로 표기)에 따른 적절한 반응이 나와 있습니다. Error metadata의 field는 소문자 `field`로 표기합니다.

| Error condition | 대응 |
|-----------------|----------|
| `DEADLINE_EXCEEDED` | Submission이 손실된 것으로 간주합니다.<br/><br/>`Step 2 <dedup-bounded-step-offset>`부터 retry하여 completion offset `OFF1`을 가져오고 필요한 경우 timeout을 늘립니다. |
| Application이 crash함 | `Step 2 <dedup-bounded-step-offset>`부터 retry하여 completion offset `OFF1`을 가져옵니다. |
| `ALREADY_EXISTS` / `DUPLICATE_COMMAND <error_code_DUPLICATE_COMMAND>` | 보고된 deduplication period 이내에 change ID가 이미 Ledger에서 accepted되었습니다. Optional field `completion_offset`에는 정확한 offset이 포함됩니다. Optional field `existing_submission_id`에는 successful submission의 Submission ID가 포함됩니다. Ledger 변경의 success를 보고합니다. |
| `FAILED_PRECONDITION` / `PARTICIPANT_PRUNED_DATA_ACCESSED <error_code_PARTICIPANT_PRUNED_DATA_ACCESSED>` | 지정된 deduplication offset이 Participant에서 pruned되었습니다. `earliest_offset`에는 마지막으로 pruned된 offset이 포함됩니다.<br/><br/>`Command Completion Service <command-completion-service>`를 사용하여 `completions <com.daml.ledger.api.v2.CompletionStreamRequest>`를 요청합니다. `offset <com.daml.ledger.api.v2.CompletionStreamRequest.begin_exclusive>`을 `earliest_offset` 값으로 설정하여 마지막으로 pruned된 offset에서 시작하고, 처음 수신한 `completion offset <com.daml.ledger.api.v2.Completion.offset>` 또는 `checkpoint offset <com.daml.ledger.api.v2.OffsetCheckpoint.offset>`을 deduplication offset으로 사용합니다. |
| `ABORTED` / 그 밖의 error code | 잠시 기다린 후 `Step 2 <dedup-bounded-step-offset>`부터 retry하여 completion offset `OFF1`을 가져옵니다. |
| 그 밖의 error condition | Business workflow와 현재 Ledger state에 관한 배경 지식을 사용하여 이전 submission이 여전히 accepted될 수 있는지 판단합니다.<br/><br/>더 이상 accepted될 수 없다고 결론 내리면 retry를 중단하고 Ledger 변경이 failed했음을 보고합니다.<br/>그렇지 않으면 `Step 2 <dedup-bounded-step-offset>`부터 retry하여 completion offset `OFF1`을 가져오거나, Ledger 변경이 일어나지 않을 것임을 확실히 알지 못한 채 중단합니다.<br/><br/>예를 들어 Ledger 변경이 Template의 Contract instance만 생성한다면 outstanding submission이 여전히 Ledger에서 accepted될 수 있으므로 결코 확신할 수 없습니다. 특히 `SUBMISSION_ALREADY_IN_FLIGHT <error_code_SUBMISSION_ALREADY_IN_FLIGHT>` error를 받지 않았다는 사실로 결론을 내려서는 안 됩니다. Outstanding submission이 어딘가에 queued되어 있고 나중에야 관련 processing point에 도달할 수 있기 때문입니다. |

Processing time bound를 아는 경우의 Command Deduplication error handling

#### Failure Scenario

위 전략은 다음 scenario에서 실패할 수 있습니다.

1.  Bound `B`가 너무 낮습니다. Command가 여러 번 실행될 수 있습니다.

    가능한 원인은 다음과 같습니다.

    - Deduplication duration보다 오랫동안 retry했지만 의미 있는 응답을 받지 못했습니다. 예를 들어 timeout(gRPC deadline)이 너무 짧을 수 있습니다. Command Service를 사용할 때 장시간 실행되는 Daml interpretation 때문에 이런 일이 발생할 수 있습니다.
    - Application clock이 Participant 또는 Ledger clock과 크게 어긋납니다.
    - 예기치 않은 network delay가 있습니다.
    - Submission이 Participant 또는 Daml Ledger 내부에서 retry되며, 해당 retry가 `B`가 끝나기 전에 멈추지 않습니다. 자세한 내용은 해당 Ledger의 documentation을 참조하세요.

2.  허용할 수 없는 변경으로 인해 무한 retry가 발생합니다.

    더 이상 retry가 의미 없는 시점을 판단하려면 business workflow 지식이 필요합니다. 물론 언제든 retry를 중단하고 결과를 확실히 알 수 없음을 받아들일 수 있습니다.

### Processing time bound를 모르는 경우

Processing time에 적합한 bound `B`를 찾기는 어렵고, 예측하지 못한 상황으로 처리가 선택한 bound `B`보다 지연될 수도 있습니다. Duration 대신 deduplication offset을 사용하면 이러한 문제를 피할 수 있습니다. Offset은 Ledger history의 한 지점을 정의하므로 clock skew와 network delay의 영향을 받지 않습니다. Offset은 상대적으로 직관성이 떨어지며 application developer에게 더 많은 노력을 요구합니다. Deduplication offset에는 다음 전략을 권장합니다.

1.  Ledger 변경과 `actAs` Party를 위한 새로운 Command ID를 선택합니다. 이들은 application ID와 함께 change ID를 결정합니다. Application crash 후에도 Command ID를 기억합니다. 위 1단계와 유사합니다.

2.  Completion stream에서 최근 offset `OFF0`을 가져오고, 선택한 Command ID에 `OFF0`을 사용한다는 사실을 crash 후에도 기억합니다. 방법은 여러 가지입니다.

- State Service에서 현재 Ledger end를 요청합니다.

  <Note>
    일부 Ledger implementation은 제출 Party에 보이는 command completion을 식별하지 않는 deduplication offset을
    error code id <code> INVALID_DEDUPLICATION_PERIOD</code>로 reject합니다. 일반적으로 Ledger end는 제출 Party에
    보이는 command completion을 식별하지 않아도 됩니다. 이러한 Ledger에서 실행할 때는 다음에 설명하는
    Command Service 방식을 사용합니다.
  </Note>

- Command Service를 사용하여 최근 offset을 가져옵니다. 예를 들어 single-signatory Template에서 Archive Choice를 사용하는 Create-And-Exercise command 같은 dummy command를 successful response가 올 때까지 반복해서 제출합니다. Response에는 completion offset이 포함됩니다.

3.  Command Completion Service를 사용할 때는 다음과 같이 합니다.

    - 이 단계를 처음 실행한다면 `OFF1 = OFF0`으로 설정합니다.
    - Error handling의 일부로 3단계부터 retry하여 completion offset `OFF1`을 가져오며 이 단계를 실행한다면 completion stream에서 최근 offset `OFF1`을 가져옵니다. 예를 들어 현재 end를 사용합니다. 위 2단계와 유사합니다.

4.  다음 parameter로 command를 제출합니다. Deduplication period 부분을 제외하면 위 3단계와 유사합니다.

    - Command ID를 1단계에서 선택한 Command ID로 설정합니다.
    - Deduplication offset을 `OFF0`으로 설정합니다.
    - Submission ID를 임의의 UUID 같은 새로운 값으로 설정합니다.
    - Timeout(gRPC deadline)을 예상 submission processing time(Command Service) 또는 submission hand-off time(Command Submission Service)으로 설정합니다.

5.  RPC call이 response를 반환할 때까지 기다립니다.

    - `OK` 이외의 status code는 error handling에 따라 처리해야 합니다.
    - Command Service를 사용할 때 response의 status code가 `OK`이면 Ledger 변경이 적용된 것입니다. Success를 보고할 수 있습니다. Response에는 이후 submission의 2단계에서 사용할 수 있는 completion offset이 포함됩니다.
    - Command Submission Service를 사용할 때는 3단계에서 선택한 change ID와 Submission ID의 completion event가 보일 때까지 `actAs`에 대한 completion을 `OFF1`(exclusive)부터 Command Completion Service로 subscribe합니다. Completion status가 `OK`이면 Ledger 변경이 적용된 것이므로 success를 보고할 수 있습니다. 그 밖의 status code는 error handling에 따라 처리해야 합니다.

#### Error Handling

알려진 bound의 경우와 같지만, 기존의 2단계부터 retry하는 대신 3단계부터 retry합니다.

#### Failure Scenario

위 전략은 다음 scenario에서 실패할 수 있습니다.

1.  지원되는 deduplication period 이내에 success가 없음

    Application이 INVALID_DEDUPLICATION_PERIOD error를 받으면 원래 의도한 deduplication period 내에서 exactly-once execution을 더 이상 달성할 수 없습니다.

2.  허용할 수 없는 변경으로 인해 무한 retry가 발생함

    더 이상 retry가 의미 없는 시점을 판단하려면 business workflow 지식이 필요합니다. 물론 언제든 retry를 중단하고 결과를 확실히 알 수 없음을 받아들일 수 있습니다.
