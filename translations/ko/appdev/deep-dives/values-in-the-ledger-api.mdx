Command와 query는 수신한 value에 완화된 validation rule을 적용합니다. 반환되는 value에는 normalization이 적용됩니다.

### Command의 Value Validation

다음 example에서 command의 *target template*는 dynamic package resolution 이후 command의 `template_id` field로 식별되는 template 또는 interface입니다.

Command에 포함된 value(예: `create_arguments`)가 target template의 type signature를 충족하기 위해 `T`에 대해 type-check되어야 한다면 해당 value의 *expected type*은 `T`입니다. 이 definition은 필연적으로 sub-value에도 확장된다는 점에 유의하세요.

`Constructor { field1 = v1, ..., fieldn = vn }` 형식의 record value에서 `vi`는 모든 `n >= j >= i`에 대해 `vj = None`이면 *trailing None*입니다.

Command 제출 시 value validation rule은 다음과 같이 완화됩니다.

> - Value의 `record_id`, `variant_id`, `enum_id` field가 있는 경우 해당 value의 expected type에 있는 module 및 type 이름에 대해서만 검사합니다. 이 field의 package ID component는 무시됩니다.
> - 모든 field 이름이 제공된 record value에서는 value가 None인 *어떤* field든 생략할 수 있습니다.
> - 일부 field 이름이 제공되지 않은 record value에서는 record type definition과 같은 순서로 field를 제공해야 하며 trailing None은 생략할 수 있습니다.

이 rule은 모든 sub-value에 적용됩니다.

**Example 1**

`example1-1.0.0`이라는 package가 `T`라는 template를 `Main`이라는 module에 정의한다고 가정합니다.

```haskell
module Main where

template T
  with
    p : Party
  where
    signatory p
```

`other-1.0.0`이라는 다른 package가 역시 `T`라는 서로 다른 template를 `Main`이라는 module에 정의한다고 가정합니다.

```haskell
module Main where

template T
  with
    s : Party
    i : Int
  where
    signatory s
```

그러면 Ledger API는 `example1-1.0.0:Main.T`의 Create command에서 create argument에 `other-1.0.0:T:Main.T` type annotation이 있어도 accept합니다. Type annotation이 잘못되었지만 다음 console command가 성공합니다.

```scala
@ val createCmd = Command(
    command = Command.Command.Create(
      value = CreateCommand(
        templateId = Some(
          value = Identifier(packageId = packageIdExample1, moduleName = "Main", entityName = "T")),
        createArguments = Some(
          value = Record(
            recordId = Some(
              Identifier(
                packageId = packageIdOther,
                moduleName = "Main",
                entityName = "T"
              )
            ),
            fields = Seq(
              RecordField(
                label = "p",
                value = Some(
                  value = Value(sum = Value.Sum.Party(value = sandbox.adminParty.toLf))
                )
              )
            )
          )
        )
      )
    )
  )

@ sandbox.ledger_api.commands.submit(Seq(sandbox.adminParty), Seq(createCmd))
```

이는 type annotation의 module과 type 이름인 `Main`과 `T`가 expected type인 `example1-1.0.0:Main.T`의 이름과 일치하기 때문입니다.

### Ledger API response의 Value normalization

Ledger API value(예: `create_arguments` in a `CreatedEvent`) 자체를 포함한 어떤 sub-value에도 trailing None이 없으면 normal form이라고 합니다.

Daml 3.3.0부터 Ledger API의 non-verbose response에 있는 value에는 normalization이 적용됩니다. Normalization은 모든 sub-value로 확장됩니다.

**Example**

`example1-1.0.0`이라는 package가 template `T`와 record `Record`를 `Main`이라는 module에 정의한다고 가정합니다.

```haskell
module Main where

data Record = Record { ri : Optional Int, rj : Int, rk : Optional Int }
  deriving (Eq, Show)

template T
  with
    p : Party
    i : Optional Int
    r : Record
    j : Optional Int
  where
    signatory p
```

또한 type `T`의 contract를 포함하는 ledger가 있으며, 이 contract는 `example1-1.0.0`이 작성했고 모든 optional field는 `None`으로 설정되어 있다고 가정합니다.

```scala
val createCmd = ledger_api_utils.create(
  packageIdExample1,
  "Main",
  "T",
  Map(
    "p" -> sandbox.adminParty,
    "i" -> None,
    "r" -> Map("ri" -> None, "rj" -> 1, "rk" -> None),
    "j" -> None))

sandbox.ledger_api.commands.submit(Seq(sandbox.adminParty), Seq(createCmd))
```

그러면 non-verbose mode에서 ledger의 Active Contract Set을 query할 때 다음 결과가 반환됩니다.


Response에서 세 번째 template argument(원래 `j`)뿐 아니라 nested record의 세 번째 field(원래 `rk`)도 생략되었습니다. 또한 value가 `None`인 optional field인데도 두 번째 template argument(원래 `i`)와 첫 번째 nested record field(원래 `ri`)는 trailing position에 있지 않으므로 response에 존재한다는 점에 유의하세요.
