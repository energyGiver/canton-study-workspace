# Scaling and Performance

## Network Scaling

Canton 기반 system의 scaling/performance 특성은 여러 요인이 결정합니다. 가장 단순한 방식은 Canton을 monolith로 배포하고 compute resource에 CPU, memory 등을 추가해 vertical scaling하는 것입니다. 그러나 일반적인 Canton deployment는 여러 조직의 서로 다른 data center에서 실행되는 distributed micro-service architecture이며 throughput을 점진적으로 높일 수 있는 기회가 많습니다.

Canton ledger state는 global하게 존재하지 않으므로 모든 contract를 host하는 단일 node가 없습니다. 대신 participant node는 strict need-to-know basis, 즉 data minimization 원칙에 따라 ledger state를 다루는 transaction에 참여하며 주어진 input contract의 coordination point인 synchronizer에서 encrypted information만 교환합니다. 예를 들어 participant Alice와 Bank가 synchronizer A에서 IOU contract를 transact해도 다른 participant Bob이나 synchronizer B는 해당 transaction과 관련된 bit를 하나도 받지 않습니다. 모든 node가 transaction의 직접 영향 여부와 무관하게 각 block을 처리해야 하는 blockchain과 다르며 horizontal scaling이 가능한 micro-service 방식에 적합합니다.

Canton micro-service deployment에는 participant node set, 이하 participant, synchronizer와 Topology Manager 같은 synchronizer internal service가 포함됩니다. 일반적으로 각 Canton micro-service는 자체 local database를 두는 best practice를 따라 throughput을 높입니다. Service를 자체 compute server에 배포하면 추가 CPU/disk capacity로 throughput이 증가합니다. 단일 service가 bottleneck이면 vertical scaling을 적용할 수 있고 다음에서 설명하는 horizontal scaling도 선택할 수 있습니다.

Initial Canton deployment는 서로 누적되는 여러 방식으로 scale할 수 있습니다. 단일 participant node에 party가 많다면 party를 새 participant node로 migrate해 throughput을 높일 수 있으며 현재 manual early access feature로 지원됩니다. 예를 들어 100개 party가 multi-lateral transaction을 수행한다면 party를 각 10개씩 host하는 participant 10개 또는 각 1개씩 host하는 participant 100개로 재배치할 수 있습니다. 대부분의 computation은 participant에서 발생하므로 synchronizer는 여러 participant의 큰 load를 처리할 수 있습니다. Synchronizer가 bottleneck이면 sequencer, topology manager, mediator를 각각 자체 compute server에서 실행해 synchronizer throughput을 높일 수 있습니다. 따라서 필요할 때 추가 Canton node가 있는 새 compute server를 network에 추가해 전체 system을 horizontally scale할 수 있습니다.

더 높은 throughput이 필요하면 Canton multi-synchronizer feature를 활용할 수 있습니다. 크고 active한 network에서 synchronizer가 capacity limit에 도달하면 추가 synchronizer를 rollout해 available synchronizer에 workflow를 shard할 수 있으며 early access입니다. Client application이 sharding으로 load balancing하는 표준 기법입니다.

단일 party가 bottleneck이면 서로 다른 participant에 host된 여러 party로 workflow를 shard해 throughput을 높일 수 있습니다. Workflow에 exchange 같은 large operator가 포함되면 operator party 두 개를 만들고 workflow를 두 operator에 균등 분배해 operator를 shard할 수 있습니다. 최종적으로 서로 다른 participant에 host하고 두 shard를 넘나드는 일부 workflow에는 intermediate step을 추가합니다.

최대 scaling을 위해 일부 anti-pattern을 피해야 합니다. 거의 모든 party를 단일 participant에 두면 해당 participant가 bottleneck이 되므로 피해야 합니다. Daml model design도 sharding 가능 범위에 큰 영향을 줍니다. 예를 들어 모든 transaction이 validation을 거쳐야 하는 synchronization party를 도입한 Daml application은 bottleneck을 만들므로 피해야 합니다.

결론적으로 command가 소수 participant와 synchronizer만 포함하면 Canton system은 horizontally scale out할 수 있습니다.


## Node Scaling

Canton은 다음 node scaling을 지원합니다.

- Database-backed driver인 Postgres와 Oracle은 multiple writer/reader process를 지원하는 parallel processing active-active setup으로 실행할 수 있으므로 horizontally scale할 수 있습니다.
- Canton process는 여러 CPU를 사용하고 available CPU 수를 자동 감지합니다. Transaction 간 conflict detection은 sequential하게 실행해야 하지만 각 transaction interpretation은 parallel하게 실행할 수 있습니다. JVM property `scala.concurrent.context.numThreads`를 원하는 값으로 설정해 parallel thread 수를 제어할 수 있습니다.

현재 Canton node performance는 일반적으로 storage I/O bound입니다. 따라서 performance는 database 또는 일부 driver의 distributed ledger인 underlying storage layer의 scaling behavior/throughput에 depend합니다. 필요한 performance를 얻으려면 database sizing이 핵심입니다.

Daml interpretation은 side effect가 없는 pure operation입니다. 따라서 각 transaction interpretation은 parallel하게 실행할 수 있고 transaction 간 conflict detection만 sequential하게 실행해야 합니다.

## Performance and Sizing

Daml workflow는 많은 computation 또는 contract fetch를 수행해 계산 복잡도가 임의로 높을 수 있으며 party, participant, synchronizer 수가 서로 다릅니다. Canton node는 전체 data와 추가 index를 storage layer인 database에 저장합니다. Workflow와 topology가 모두 다르므로 sizing requirement는 실행할 Daml application과 storage layer resource requirement에 depend합니다. Sizing estimate를 얻으려면 use case를 대표하는 topology/setup에서 dominant workflow의 resource usage를 측정해야 합니다.

## Batching

모든 transaction에는 signature, symmetric encryption key, serialization, transport message wrapping, HTTP header 등의 overhead가 있으므로 command를 submit하는 application이 작은 request를 단일 transaction으로 batch하도록 design할 것을 권장합니다.

Optimal batch size는 workflow와 topology에 depend하며 experiment로 결정해야 합니다.

## Asynchronous Submissions

최고 performance를 위해 asynchronous command submission을 권장합니다. 다만 async submission은 initial command interpretation과 transaction building을 포함하지만 transaction validation/result finalization은 포함하지 않아 부분적으로만 asynchronous합니다. Command size/complexity에 따라 50~1000ms가 걸립니다. 단일 thread가 transaction을 submit하는 극단적 경우에는 초당 command 하나의 rate만 얻을 수 있습니다.

Synchronous command submission을 사용하면 system이 전체 transaction 완료를 기다리므로 더 많은 thread가 필요합니다. Synchronous command submission의 default upper limit는 in-flight command 256개이며 다음 설정으로 변경할 수 있습니다.

## Storage Estimation

Canton installation의 사전 storage estimation은 어렵습니다. Storage usage는 topology, payload, 사용한 Daml model, 설정한 storage layer type에 depend합니다. 다음 예시는 use case의 storage usage를 이해하는 데 도움이 됩니다.

먼저 gRPC Ledger API로 submit한 command는 serialized gRPC request로 participant에 전송됩니다.

이 command를 먼저 interpret해 Daml-LF transaction으로 변환합니다. 이어서 interpreted transaction을 전체 transaction tree structure의 privacy-preserving representation인 Canton transaction view-decomposition으로 변환합니다. Transaction은 일반적으로 여러 transaction view로 구성되며 최악의 경우 transaction tree의 모든 action node가 별도 view가 됩니다. 각 view는 input contract의 contract argument를 포함해 해당 view에 필요한 전체 argument set을 담으므로 data representation이 크게 증가할 수 있습니다. Concrete example 없이는 결과 size를 estimate할 수 없습니다. 단순한 사례로 participant가 일반적인 "Iou" contract의 "Transfer" choice를 exercise해 다른 contract argument를 보존하면서 new owner에게 이전한다고 가정합니다. IOU의 old/new owner는 같은 participant에 host되고 issuer는 두 번째 participant에 host된다고 가정합니다.

결과 Canton transaction은 Transfer choice의 **Exercise** node와 transferred IOU의 **Create** node에 해당하는 두 view로 구성됩니다. 두 view에는 package/template identifier, contract key, stakeholder, involved participant 같은 metadata가 포함됩니다. **Exercise** node view에는 size `Y`인 input IOU contract argument가 있고 **Create** node view에는 역시 size `Y`인 created contract의 updated argument가 있습니다. Command size `X`와 input contract size `Y` 사이에는 fixed relation이 없습니다. 일반적으로 `X`는 transfer receiver만 포함하고 ledger에 저장된 contract argument는 포함하지 않습니다.

이에 따라 다음 storage usage가 발생합니다.

- Sequencer store에는 각각 payload `Y`인 encrypted envelope 두 개, view별 seed 하나, informee group별 symmetric key 하나, participant별 root hash 두 개, recipient인 participant ID와 mediator용 informee tree, sequencer database index가 있습니다. Informee tree에는 informee와 transaction metadata가 있지만 payload는 없습니다.
- 각 participant가 data를 받으므로 participant별 event table에는 각각 payload `Y`인 encrypted envelope 두 개와 view symmetric key가 있습니다.
- Private contract store에는 size `Y`인 decrypted new resulting contract가 있고 sync service active contract journal에는 contract status information이 있습니다.
- Sync service linear event log에는 created contract용 size `Y` payload가 있는 full decrypted transaction이 있습니다. Input contract argument는 포함하지 않습니다.
- Indexer event table에는 input contract를 제외하고 newly divulged input contract를 포함한 `Y` 크기의 full decrypted transaction이 있습니다.

Payload가 storage requirement의 대부분이라고 가정하면 view decomposition으로 인한 payload multiplication이 storage requirement를 결정합니다. 이 예시에서 transaction은 각 participant에 `5\*Y`, sequencer에 `2\*Y` storage가 필요합니다. Participant 두 개와 sequencer를 합치면 총 `12\*Y`입니다.

Contract와 event를 효율적으로 serve하려면 database가 추가 index를 build해야 합니다. Database layer별 index size usage의 정확한 estimation은 이 문서 scope 밖입니다.

<Note>
Sync service와 indexer 사이의 storage duplication을 제거할 계획이 있습니다. 이상적으로 이 예시의 participant storage를 `5\*Y`에서 \`3\*Y\`로 줄일 수 있습니다. Unencrypted created contract에 한 번, encrypted transaction view 두 개에 각각 한 번입니다.
</Note>

일반적으로 used storage를 회수하려면 participant와 synchronizer를 prune할 수 있습니다. Console command set으로 pruning을 수행하며 timestamp를 기준으로 past event와 archived contract를 제거할 수 있습니다. Obsolete data를 지속적으로 제거하면 Canton deployment의 storage usage를 일정하게 유지할 수 있습니다. Bilateral commitment로 unpruned history의 non-repudiation/auditability를 보존합니다.

## Set Up Canton to Get the Best Performance

이 section은 Canton application의 optimal performance 달성을 돕기 위해 internal performance test 결과를 설명합니다.

### System Design / Architecture

Optimal performance를 위해 latest supported Canton release 실행을 권장합니다.

Daml party를 independent block으로 partition할 수 있도록 topology를 설계합니다. 대부분의 Daml command가 단일 block의 party만 포함하도록 해야 합니다. 여러 block 또는 전체 block의 party가 포함되는 command도 매우 드물다면 괜찮습니다. 모든 command에 관여하는 single master party는 system bottleneck이 되므로 특히 피해야 합니다.

Participant가 bottleneck이 되면 participant node를 추가하고 각 block을 자체 participant에서 실행합니다. Synchronizer가 bottleneck이 되면 synchronizer node를 추가하고 모든 synchronizer에 load를 균등 분배합니다.

작은 command를 많이 보내기보다 여러 action, 즉 create/exercise를 포함한 큰 command를 우선합니다. gRPC Ledger API로 불필요한 command를 보내지 말고 command payload를 최소화합니다.

자세한 내용은 Section `scaling_and_performance`에서 확인할 수 있습니다.

### Hardware and Database

Production 또는 performance test에서 Canton node를 in-memory storage나 H2 storage로 실행하지 마세요. 처음에는 performance가 좋아 보일 수 있지만 data store가 차면 크게 저하될 수 있습니다.

Memory usage, CPU usage, disk throughput을 측정하고 필요에 따라 hardware를 개선합니다. 단순하게 single machine에서 시작하고 resource가 bottleneck이 되면 node와 database를 서로 다른 machine에 분산합니다.

Canton node와 database 사이 latency를 매우 낮게, 이상적으로 microsecond 수준으로 유지합니다. Canton node 간 latency는 node와 database 간 latency보다 throughput에 미치는 영향이 훨씬 작습니다.

Tuning instruction은 Postgres persistence section을 확인하세요.

<div id="tuning_resource_limits">

**Canton protocol level resource limit tuning.** Resource limit은 ledger application이 과도한 rate로 command를 보내 Canton을 overload하는 것을 방지합니다. Production에서 denial-of-service attack으로부터 system을 보호하는 데 필요하지만 maximum throughput 달성을 방해할 수 있습니다. Canton protocol level resource limit은 Canton console에서 다음과 같이 설정합니다.

</div>

``` none
participant1.resources.set_resource_limits(
  ResourceLimits(
    // Allow for submitting at most 200 commands per second
    maxSubmissionRate = Some(200),

    // Limit the number of in-flight requests to 500.
    // A "request" includes every transaction that needs to be validated by participant1:
    // - transactions originating from commands submitted to participant1
    // - transaction originating from commands submitted to different participants.
    // The chosen configuration allows for processing up to 100 requests per second
    // with an average latency of 5 seconds.
    maxInflightValidationRequests = Some(500),

    // Allow submission bursts of up to `factor * maxSubmissionRate`
    maxSubmissionBurstFactor = 0.5,
  )
)
```

일반적으로 `maxDirtyRequests`는 `throughput * latency`보다 약간 크게 설정합니다.

- `throughput`은 Canton이 처리해야 하는 초당 request 수입니다.
- `latency`는 Canton이 `throughput` rate로 request를 받는 동안 단일 request를 처리하는 시간입니다.

Performance test로 `throughput`과 `latency`가 현실적인지 확인해야 합니다. 그렇지 않으면 application이 Canton 처리량보다 많은 request를 submit해 overload할 수 있습니다.

`maxRate` parameter는 예상 maximum `throughput`보다 약간 높게 설정합니다.

Command burst를 지원해야 한다면 `maxBurstFactor`를 맞게 설정합니다. 그러면 initial burst `maxBurstFactor * maxRate`를 받은 뒤부터 `maxRate` limit이 적용됩니다.

Optimal resource limit을 찾으려면 performance test가 필요합니다. Request가 constant rate로 도착하면 `maxDirtyRequest`가 Canton overload를 방지하고 variable rate라면 `maxRate`가 추가 보호를 제공합니다.

높은 resource limit은 throughput을 높일 수 있지만 latency도 높아질 위험이 있습니다. 극단적으로 latency가 커져 command timeout이 발생하면 일부 command가 ledger에 commit되지 않으면서 processing resource만 소비합니다.

낮은 resource limit은 latency를 낮출 수 있지만 throughput이 감소하고 command가 error code `PARTICIPANT_BACKPRESSURE`로 거부될 수 있습니다.

<div id="tuning_ledger_api_limits">

**gRPC Ledger API level resource limit tuning.** Resource limit은 gRPC Ledger API level에도 적용할 수 있습니다. Ledger application에 더 가까운 곳에 적용되므로 전체 Canton system보다 individual participant resource를 보호하는 데 사용할 수 있습니다.

</div>

다음 configuration option을 수정할 수 있습니다.

``` 
canton.participants.<participant-name>.ledger-api.rate-limit {
  max-streams = 333
  max-api-services-queue-size = 444
  max-api-services-index-db-queue-size = 555
  max-used-heap-space-percentage = 66
  min-free-heap-space-bytes = 7777777
}
```

`max-streams` parameter로 동시에 open할 수 있는 gRPC Ledger API stream 수를 제한합니다. 동시에 열린 transaction, transaction-tree, completion, ACS stream이 maximum에 도달하면 추가 get stream request를 받지 않고 `MAXIMUM_NUMBER_OF_STREAMS` error code를 return합니다.

`max-api-services-queue-size`와 `max-api-services-index-db-queue-size`로 각각 Ledger API와 index database read request를 serve하는 thread pool의 pending item 수를 제한합니다. CPU worker thread pool 또는 database communication thread pool이 overload되면 server는 `THREADPOOL_OVERLOADED` error code로 response합니다.

`max-used-heap-space-percentage` parameter로 사용 memory heap 비율을 제한합니다. `tenured` memory pool garbage collection 후에도 이 비율을 초과하면 추가 space가 확보될 때까지 system을 rate-limit합니다.

`min-free-heap-space-bytes` parameter로 absolute minimum heap space도 설정할 수 있습니다. `tenured` memory pool garbage collection 후 free space가 이 값보다 작으면 추가 space가 확보될 때까지 rate-limit합니다. Maximum memory threshold를 초과하면 server가 gRPC Ledger API request에 `HEAP_MEMORY_OVER_LIMIT` error code로 response합니다.

다음은 default configuration value입니다.

``` 
max-streams = 1000
max-api-services-queue-size = 10000
max-api-services-index-db-queue-size = 1000
max-used-heap-space-percentage = 100
min-free-heap-space-bytes = 0
```

Memory 관련 설정인 `max-used-heap-space-percentage` 100과 `min-free-heap-space-bytes` 0은 사실상 inactive 상태이며 의도된 것입니다. Operating environment에 매우 민감하므로 memory profiling에서 완화해야 할 usage spike가 확인된 경우에만 설정해야 합니다.

gRPC Ledger API level rate limiting을 끌 수도 있습니다.

``` 
canton.participants.<participant-name>.ledger-api {
  rate-limit = null
}
```

<div id="tuning_stream_api_limits">

**Open Stream 수**: Ledger API와 마찬가지로 Admin API와 Sequencer API의 open stream 수를 configuration의 `limits.active` section에서 설정할 수 있습니다.

</div>

``` none
canton.sequencers.sequencer.public-api.limits.active = {
  "com.digitalasset.canton.sequencer.api.v30.SequencerService/DownloadTopologyStateForInit" : 10,
  "com.digitalasset.canton.sequencer.api.v30.SequencerService/Subscribe" : 1000,
}
```

<div id="size_of_connection_pools">

**Connection pool size.** 모든 node가 connection pool로 database와 통신하도록 합니다. Database query마다 새 connection을 만드는 추가 cost를 피할 수 있습니다. Canton은 적합한 connection pool을 기본 선택하지만 performance-sensitive application은 optimize할 수 있습니다. Database가 fully loaded되지만 overloaded되지 않도록 maximum connection 수를 설정합니다. Connection이 너무 많으면 resource waste, context switching, database contention이 발생해 전체 system이 느려지고 Canton이 report하는 query latency가 올라갑니다. Troubleshooting guide를 참고하세요.

</div>

이 문제의 자세한 처리 방법은 `max_connection_settings`에서 확인할 수 있습니다.

**Database task queue size.** Canton이 database를 query할 때 `RejectedExecutionExceptions`가 자주 발생하면 `database_task_queue_full` 설명에 따라 task queue size를 늘립니다. 이 rejection 자체는 harmless하며 database overload를 나타냅니다.

**Database latency.** Database latency를 낮게 유지합니다. Latency가 높을수록 actual bandwidth와 system throughput이 낮아집니다.

**SequencerClient throttling configuration.** `SequencerClient`는 Canton network member, 즉 participant, mediator, topology manager와 synchronizer의 connection을 관리합니다. 각 synchronizer에는 여러 sequencer가 있을 수 있고 `SequencerClient`는 그중 하나에 연결합니다. `SequencerClient`가 incoming message를 따라가지 못할 정도로 overload될 수 있으므로 `maximum-in-flight-event-batches` configuration parameter를 제공합니다.

<ExternalCantonMainCommunityAppSrcTestResourcesDocumentationSnippetsSequencerClientThrottling />

`maximum-in-flight-event-batches`로 system이 concurrently 처리하는 maximum event batch 수를 제어합니다. Overload를 방지하고 workload를 효과적으로 처리하는 데 도움이 됩니다.

`maximum-in-flight-event-batches` 값은 `SequencerClient` performance에 여러 영향을 줍니다. 높은 값은 `SequencerClient`가 더 많은 event를 동시에 처리해 throughput을 높일 수 있게 하지만 memory consumption과 batch별 processing time도 증가합니다.

낮은 `maximum-in-flight-event-batches` 값은 concurrently 처리할 event가 줄어 throughput을 제한할 수 있지만 `SequencerClient` behavior가 더 stable하고 predictable해질 수 있습니다.

`SequencerClient` performance와 desired limit 내 operation을 monitor하려면 metric `sequencer-client.handler.actual-in-flight-event-batches`를 관찰합니다. Current in-flight event batch 수와 configured limit에 얼마나 가까운지 보여줍니다. Metric `sequencer-client.handler.max-in-flight-event-batches`로 configured maximum value도 확인할 수 있습니다.

이 metric을 monitor하면 actual workload와 specified limit 접근 여부를 파악해 optimal `SequencerClient` performance를 유지하고 potential bottleneck/overload를 방지할 수 있습니다.

**High-Throughput Sequencer 활성화.** Database sequencer에는 tuning 가능한 parameter가 있으며 low-latency와 high-throughput 사이 trade-off가 있습니다. Low-latency setting은 submission을 즉시 single item으로 처리하고 high-throughput setting은 event를 몇 개 모아 한 번에 write합니다. 추가 latency는 수 ms뿐이지만 Daml application 개발/test에는 차이가 있으므로 default는 `low-latency`입니다. Throughput demand가 높은 production deployment는 `high-throughput`을 설정해야 합니다.

``` none
// example setting for synchronizers nodes. database sequencer nodes have the exact same settings.
canton.sequencers.sequencer1.sequencer {
    type = BFT
    block {
        writer = {
            // choose between high-throughput or low-latency
            type = high-throughput
        }
    }
}
```

이론적으로 fine-tune할 수 있는 parameter가 더 있지만 default를 유지하고 high-throughput 또는 low-latency를 사용할 것을 권장합니다. 경험상 high-throughput sequencer는 초당 수천 submission을 처리할 수 있습니다.

**JVM heap size.** `OutOfMemoryErrors` 또는 높은 garbage collection overhead가 관찰되면 Section `jvm_arguments` 설명에 따라 JVM heap size를 늘립니다. VisualVM 같은 JVM provider tool로 garbage collector를 monitor해 heap size가 부족한지 확인합니다.

**Thread pool size.** 모든 Canton process에는 internal task 실행용 thread pool이 있습니다. 기본 size는 underlying physical machine의 virtual core 수입니다. Machine이 database 같은 다른 process를 실행하거나 Canton이 container에서 실행되면 thread pool이 너무 커 excessive context switching이 발생할 수 있습니다. 다음처럼 size를 명시적으로 설정합니다.

``` none
"bin/canton -Dscala.concurrent.context.numThreads=12 --config examples/01-simple-topology/simple-topology.conf"
```

그러면 Canton은 다음 line을 log합니다.

``` none
"INFO  c.d.canton.environment.Environment - Deriving 12 as number of threads from '-Dscala.concurrent.context.numThreads'."
```

**Asynchronous commit.** Postgres database를 사용한다면 다음 line을 Canton configuration에 넣어 Participant Ledger API server가 database transaction을 asynchronously commit하도록 설정합니다.

``` none
canton.participants.participant1.ledger-api.postgres-data-source.synchronous-commit = off
```

**Logging setting.** Canton이 INFO 이상 level의 log message만 출력하도록 하고 `--log-immediate-flush=false` command line flag로 immediate log flushing을 끕니다. Host system crash 시 log entry를 잃을 위험이 있습니다.

**Replication.** Participant, sequencer, mediator에 single node를 사용하는 경우에만 respective configuration에서 `replication.enabled = false`로 replication을 끌 수 있습니다.

<Warning>
Performance 개선을 위해 replication을 끌 수 있지만 HA용 multiple node를 실행할 때는 **비활성화하면 안 됩니다**.
</Warning>

<div id="caching_configuration">

**Caching configuration.** 상황에 따라 caching configuration을 줄이거나 늘릴 수 있습니다. Default cache는 high-throughput, high-memory, small transaction size에 맞춰져 있으므로 큰 Canton memory footprint를 줄여야 할 때도 유용합니다.

</div>

Size 관점에서 중요한 cache는 보통 contract cache와 in-memory fan-out event buffer입니다. 다음 configuration으로 tune할 수 있으며 표시된 값은 smaller memory footprint에 권장되므로 out-of-memory 문제에도 도움이 됩니다.

## Model Tuning

Daml model 작성 방식은 system performance에 큰 영향을 줍니다. 좋은 model은 single participant node에서 초당 3000 ledger event를 처리한 사례가 있지만 bad model은 그 일부에 그칩니다. Model과 performance implication의 관계를 이해해야 하며 이 section은 몇 가지 guideline을 제공합니다.

### Reduce the Number of Views

Canton의 핵심 performance driver는 model에서 만들어지는 transaction structure입니다. Daml command는 transaction structure를 계산하는 "program"이며 Canton은 이를 "transaction view"로 분해합니다. View는 encrypt되어 participant로 전송되고 participant가 각각 confirm합니다. 각 view에는 cryptography가 필요하고 처리/validate할 additional payload가 생깁니다.

따라서 system performance는 transaction이 생성하는 view 수에 직접 depend합니다. Transaction view 수는 participant 측 DEBUG log message에 기록됩니다.

``` 
Computed transaction tree with total=27 for #root-nodes=8
```

여러 Daml command를 포함할 수 있는 Ledger API command를 submit하면 각 Daml command가 root-node 하나를 만들며 `CreateAndExercise` command는 두 개를 만듭니다. Root node마다 view 하나를 생성합니다.

모든 Daml command를 single batch command에 넣기만 해서는 많은 view가 계속 생성될 수 있어 도움이 되지 않습니다.

현재 action node의 **informee를 host하는 participant가 parent view informee participant의 subset이 아니면** Canton은 transaction tree의 각 action node마다 view를 생성합니다. View informee participant는 해당 view 정보를 받아야 하는 모든 participant입니다. View 수를 줄이려면 informee set 증가 횟수를 줄이거나 대부분 action이 같은 participant pool을 공유하도록 해야 합니다. 또는 root에 가까운 action node에 choice observer 등을 통해 informee를 추가해 child node가 initial view에 aggregate되도록 할 수 있습니다. Child node는 이 participant의 subset만 target합니다.

Daml model의 view 수를 줄이는 구체적 방법은 batch command를 작성하고 informee participant를 기준으로 ledger operation을 group화하는 것입니다. Single choice를 만들고 같은 informee participant group을 공유하는 operation을 모두 batch할 수 있습니다.

Daml model을 만들 때 node child의 parent-child view 수도 줄일 수 있습니다. 아래 예시처럼 exercise command `Foo` 20개를 batch로 보내는 대신 exercise informee participant를 cover하는 stakeholder set별로 contract를 group화하고, stakeholder group마다 Foo choice를 exercise할 contract list를 가진 generator contract에서 exercise command 하나를 보냅니다. 여러 view 대신 single view에서 operation을 수행할 수 있습니다.

아래 `doUpdate`가 `owner` party에게만 visible한 choice에서 호출되면 `efficient` flag 설정 여부가 생성 view 수에 큰 영향을 줍니다. `Example` contract의 choice `Foo`에서 informed participant가 contract informee participant의 subset이어도 choice를 매번 독립 호출하면 single view로 merge되지 않고 각자 view를 갖는 multiple root action이 생성됩니다. `Run` choice observer를 template contract와 align한다는 것은 각 경우 choice observer가 같거나 new observer가 contract informee participant 중 하나에 host된다는 뜻입니다.

```haskell
doUpdate : Bool -> Party -> Party -> [ContractId Example] -> Update ()

doUpdate efficient owner obs batch = do
  if efficient then do
    batcher <- create BatchFoo with owner
    -- This only works out if obs is the same observer on all the exercised Example contracts
    batcher `exercise` Run with batch = batch; obs = obs
  else do
    -- Canton will create one view per exercise
    forA_ batch (`exercise` Foo)
  pure ()

template Example with
    owner : Party
    obs: Party
  where
    signatory owner
    observer obs

    choice Foo : ()
      controller owner
      do
        return ()

template BatchFoo with
    owner : Party
  where
    signatory owner

    choice Run : () with
        batch : [ContractId Example]
        obs : Party
      -- The observer here is a choice observer. Therefore, Canton will
      -- ship a single view with the top node of this choice if the observer of the
      -- choice aligns with the observer of the contract.
      observer obs
      controller owner
      do
        forA_ batch (`exercise` Foo)
```

원칙적으로 view 수는 command 하나에서 parallel 처리하는 "batch" 수가 아니라 batch choice의 informee participant group 수에 depend해야 합니다. Informee participant group은 각 stakeholder를 host하는 participant를 aggregate한 set, 즉 특정 view를 봐야 하는 participant set입니다.

Transaction tree node type별 informee는 다음과 같습니다. `da-model-projections`도 참고하세요.
- Create: signatory, observer
- Consuming exercise: signatory, observer, choice stakeholder, 즉 controller와 choice observer
- Nonconsuming exercise: signatory와 choice stakeholder, 즉 controller와 choice observer. Contract observer는 제외
- Fetch: signatory와 fetch actor. Fetch가 실행된 authorization context에 있는 모든 stakeholder
- LookupByKey: key maintainer만 포함

### Reduce Ledger Events

최고 optimization은 불필요한 작업을 하지 않는 것입니다. Ledger는 relevant data를 저장하고 party 간 coordination을 수행합니다. Ledger를 processing queue로 사용하면 intermediate step에도 각 transaction view를 cryptographically secure하고 privacy/integrity를 위해 광범위하게 처리하므로 performance 문제가 발생합니다. Party가 submit한 transaction output을 같은 party가 즉시 consume한다면 ledger를 processing queue로 쓰는 것입니다. 두 step을 하나로 합치도록 command를 재구성하세요.

각 `create`는 contract를 생성하고 ledger에 data를 write합니다. 각 `fetch`는 interpreter가 interpretation을 중단하고 ledger에 contract를 요청하게 하며 최악에는 database lookup이 필요합니다. Interpretation은 sequential하게 일어나므로 contract를 하나씩 lookup해 load와 latency를 만듭니다. Data fetch는 중요한 기능이지만 database와 같은 원칙을 적용해야 합니다. Database lookup은 비싸므로 필요한 경우에만 수행하고 반복 계산 결과는 가능하면 cache합니다.

예를 들어 high-throughput process가 항상 chain `A -\> B -\> C -\> D`, 즉 fetch 네 번으로 data를 resolve한다면 single cache contract `ABCD`를 사용하도록 model을 바꿉니다. 해당 contract만 fetch하고 original contract 중 하나가 변경될 때마다 `ABCD`를 update하는 process를 둡니다.

Additional view를 만들 수 있는 불필요한 transient contract도 피합니다. `createAndExercise`는 single command가 아니라 create 하나와 exercise 하나로 변환됩니다. 대신 `nonconsuming` choice를 사용하고 audit 목적으로 ledger에 trace가 필요하면 choice observer를 추가할 수 있습니다.

일반적으로 `lookupKey` 사용도 권장하지 않습니다. On-ledger deduplication에 `lookupByKey`를 사용하면 대부분 `None`으로 resolve되면서도 database lookup이 필요합니다. 대신 Ledger API command deduplication을 사용합니다. 또한 current `lookupByKey` semantic은 single-synchronizer deployment에서만 동작하고 multi-synchronizer에 1:1로 변환할 수 없어 multi-synchronizer deployment에서는 지원되지 않습니다.

# Managing Latency and Throughput

## Problem Definition

Latency는 business transaction 완료에 걸리는 시간을 측정합니다. Throughput은 bottleneck을 나타낼 수 있는 lower/upper bound를 고려해 초당 가능한 business transaction 수를 평균적으로 측정합니다. Daml application design 단계에서 latency/throughput 문제 대응을 포함할 수 있습니다.

먼저 Daml application의 potential bottleneck을 식별해야 하며 sync-domain-specific transaction을 분석할 수 있습니다.

각 Daml business transaction은 Ledger API client가 participant에 command `create` 또는 `exercise`를 보내면서 시작합니다.

<Warning>
- Ledger transaction과 business transaction은 같은 개념이 아닙니다.
- Complete business transaction은 여러 workflow step과 여러 ledger transaction에 걸치는 경우가 많습니다.
- Batching으로 single ledger transaction에서 여러 business transaction을 처리할 수 있습니다.
- 예상 ledger transaction latency는 database sequencer에서 0.5~1초, blockchain sequencer에서 수 초 수준입니다.
</Warning>

Canton ledger가 처리하는 ledger transaction은 [Daml execution model](/appdev/modules/m3-design-patterns#daml’s-execution-model)을 참고하세요. 아래 table은 각 step의 potential resource-intensive activity를 보여줍니다.

| Step | Participant | 사용 resource | 가능한 bottleneck driver |
|------|-------------|----------------|-----------------------------|
| Interpretation | Submitting participant node | CPU<br/>Memory<br/>DB read access | Calculation complexity<br/>Size and number of variables<br/>Number of contract fetches |
| Blinding | Submitting participant node | CPU/memory | Number and size of views |
| Submission | Submitting participant node<br/>Sequencer | CPU<br/>Memory | Serialization/deserialization<br/>Transaction size/number of views |
| Sequencing | Sequencer | Backend storage<br/>Network bandwidth | Transaction size<br/>Transaction size/number of views |
| Validation | Receiving participant nodes | Network bandwidth<br/>CPU<br/>Memory<br/>DB read throughput | Transaction size -> download, deserialization, storage costs<br/>Computation complexity<br/>Number of contract fetch reads<br/>Number and size of variables |
| Confirmation | Validating participant nodes<br/>Sequencer | Network bandwidth<br/>Sequencer network<br/>Backend write throughput | Number of confirming parties |
| Mediation | Mediator nodes | Network throughput<br/>CPU<br/>Memory | Number of confirming parties |
| Commit | Mediator nodes<br/>Sequencer | CPU<br/>Memory<br/>DB<br/>Network bandwidth | Number of confirming parties |

### Possible Throughput Bottlenecks in Order of Likelihood

1.  큰 transaction size로 participant node의 serialization/deserialization과 encryption/decryption cost 증가
2.  큰 transaction size로 특히 blockchain의 sequencer backend overload 발생
3.  Calculation complexity 또는 memory usage로 interpretation/validation cost 증가
4.  많은 involved node와 sequencer network bandwidth 증가

위 요인은 latency에도 영향을 줍니다. 다만 baseline latency는 보통 Daml modeling 문제보다 DB/blockchain latency 같은 system setup 문제와 더 관련됩니다.

### Solutions

1.  **Transaction size 최소화**

다음 Daml action은 대상 contract payload를 포함한 node를 transaction에 추가합니다. 이런 operation이 많거나 large contract에서 실행되면 가장 흔한 performance bottleneck 원인이 됩니다.

> - `create`
> - `fetch`
> - `fetchByKey`
> - `lookupByKey`
> - `exercise`
> - `exerciseByKey`
> - `archive`

위 action은 제한적으로 사용합니다. Contract가 transaction 안에서 intermediary state를 갖는다면 end state만 write해 생략할 수 있습니다.

```haskell
template Incrementor
with
p : Party
n : Int
where
signatory p

choice Increment : ContractId Incrementor
    controller p
    do create this with n = n+1

-- This adds all m-1 intermediary versions of
-- the contract to the transaction tree
choice BadIncrementMany : ContractId Incrementor
    with m : Int
    controller p
    do foldlA (\self' _ -> exercise self' Increment) self [1..m]

-- This only adds the end result to the transaction
choice GoodIncrementMany : ContractId Incrementor
    with m : Int
    controller p
    do create this with n = n+m
```

Contract를 read하거나 single contract에 여러 방식으로 action해야 하면 operation을 single action으로 bundle할 수 있습니다.

```haskell
template Asset
with
issuer : Party
owner : Party
quantity : Decimal
where
signatory [issuer, owner]

-- BadMerge acts on each of the otherCids three times:
-- Once for validation
-- Once to extract the quantities
-- Once to archive
choice BadMerge : ContractId Asset
 with otherCids : [ContractId Asset]
 controller owner
 do
   -- validate the cids.
   forA_ otherCids (\cid -> do
     other <- fetch cid
     assert (other.issuer == issuer && other.owner == owner))

   -- extract the quantities
   quantities <- forA otherCids (\cid -> do
     other <- fetch cid
     return other.quantity)

   -- archive the others
   forA_ otherCids archive

   create this with quantity = quantity + sum quantities

-- Allow us to do a fetch and an archive in one action
choice ConsumingFetch : Asset
 controller owner
 do return this

-- GoodMerge only acts on each of the other assets once.
choice GoodMerge : ContractId Asset
 with otherCids : [ContractId Asset]
 controller owner
 do
   -- Get and archive the others
   others <- forA otherCids (`exercise` ConsumingFetch)

   -- validate
   forA_ others (\other -> do
     assert (other.issuer == issuer && other.owner == owner))

   -- extract the quantities
   let quantities = map (.quantity) others

   create this with quantity = quantity + sum quantities
```

드물게 변경되고 최소 access만 필요한 large payload template을 거의 모든 action에서 변경되는 field template과 분리합니다. 여러 business transaction의 resource consumption을 optimize할 수 있습니다.

이 batching 방식은 update마다 별도 transaction을 요구하지 않고 one transaction submission에서 update합니다. Latency가 조금 증가하고 command failure 가능성이 커질 수 있지만 회피할 수 있습니다.

```haskell
template T
with
p : Party
where
signatory p

choice Foo : ()
    controller p
    do return ()

batching : Script ()
batching = do
p <- allocateParty "p"

-- without batching we have 10 ledger
-- transactions.
cid1 <- submit p do createCmd T with ..
cid2 <- submit p do createCmd T with ..
cid3 <- submit p do createCmd T with ..
cid4 <- submit p do createCmd T with ..
cid5 <- submit p do createCmd T with ..

submit p do exerciseCmd cid1 Foo
submit p do exerciseCmd cid2 Foo
submit p do exerciseCmd cid3 Foo
submit p do exerciseCmd cid4 Foo
submit p do exerciseCmd cid5 Foo

-- With batching, there are only two ledger transactions.
cids <- submit p do
replicateA 5 $ createCmd T with ..
submit p do
forA_ cids (`exerciseCmd` Foo)
```

2.  CPU/memory 문제: Daml profiler로 Daml code execution을 분석합니다.
3.  Interpretation이 bottleneck이 아니라면 machine을 scale up합니다.

<Tip>
JVM을 profile하고 database를 monitor해 bottleneck 발생 위치를 확인합니다.
</Tip>

# Managing Active Contract Set (ACS) Size

## Problem Definition

Active Contract Set(ACS) size는 특정 시점 system의 active contract 수와 관련된 load를 구성하며 생성되었지만 아직 archive되지 않은 모든 contract입니다. ACS size는 의도적인 Daml workflow design에서 생길 수 있지만 supporting/auxiliary contract lifetime을 충분히 관리하지 않으면 예상과 다르게 커질 수 있습니다.

<Tip>
자세한 내용은 Daml contract documentation을 참고하세요.
</Tip>

ACS size가 수백 GB 또는 TB 수준이면 local database access performance가 저하될 수 있습니다. Large ACS의 potential issue와 solution을 살펴봅니다.

## Relational Databases

Large ACS는 relational database system performance의 여러 측면에 악영향을 줍니다. 다음은 PostgreSQL을 underlying database로 가정하며 Oracle은 detail이 다르지만 결과는 유사합니다.

- Large ACS는 memory 또는 application database에 맞지 않을 수 있는 large dataset을 다루는 Ledger API client application의 resource consumption/performance에 직접 영향을 줍니다.
- ACS size는 StateService로 Ledger API server에서 ACS를 전송하는 speed에 직접 영향을 줍니다. 극단적으로 gRPC channel capacity와 storage query speed limit 때문에 complete set 전송에 수 시간이 걸릴 수 있습니다.
- Large ACS는 corresponding index도 크게 만들어 shared-buffer space에 맞지 않게 되며 database engine query result 시간이 늘어납니다. Command submission 중 contract lookup, transaction tree streaming, pointwise transaction lookup에 영향을 줍니다.
- Large ACS는 participant database가 new transaction을 ingest하는 speed에 영향을 줄 수 있습니다. 일반적으로 update가 들어오면 write-ahead log가 table/index change를 즉시 commit하며 full-page write 또는 differential write 형태입니다. Volume이 크면 full-page write가 많아집니다.
- 많은 dirty page는 checkpointing 중 길고 비싼 disk flush로 이어집니다.

### Solutions

- Contract lifetime을 관리하고 supporting/auxiliary contract가 ACS를 채우지 않도록 가능한 즉시 archive합니다.

- Frequent pruning schedule을 설정합니다. Pruning 가능한 archived contract가 있어야 효과적이며 모든 contract가 active면 제한적입니다. [Pruning documentation](/overview/reference/pruning)을 참고하세요.

- Ledger client application에 ODS를 구현해 ACS read access dependency를 줄입니다. ACS에서 application initialize 시간이 허용 수준을 넘으면 적용합니다.

- Database performance를 monitor합니다.
  - Disk read/write activity와 operation pattern의 sudden change를 확인합니다. Disk read가 갑자기 증가하면 index가 shared buffer에 맞지 않는 신호일 수 있습니다.
  - Database query performance를 관찰합니다. 도움이 되는 query [metric](/global-synchronizer/reference/canton-metrics#daml-sequencer-db-storage-write-executor-waittime)은 [monitoring documentation](/global-synchronizer/extension-synchronizers/synchronizer-monitoring)을 확인하세요. PostgreSQL configuration에 [log_min_duration_statement parameter](https://www.postgresql.org/docs/current/runtime-config-logging.html#GUC-LOG-MIN-DURATION-STATEMENT)를 설정할 수도 있습니다.

- PostgreSQL database에 [autovacuum](https://www.postgresql.org/docs/current/routine-vacuuming.html#AUTOVACUUM)을 설정합니다. Pruning 후 많은 dead tuple을 제거해야 합니다.

# Avoid Contention Issues

Business application performance 측정에는 underlying blockchain과 Distributed Ledger Technology(DLT)의 TPS/transaction latency 외에도 여러 요소가 포함됩니다. Blockchain은 distributed system이므로 최고 performance blockchain도 traditional database보다 transaction latency가 상당히 높습니다. 이런 요인은 contention을 쉽게 만들며 적절히 처리하지 않으면 application performance를 제한합니다.

High-performance blockchain에서도 low-performance application을 설계하기 쉽고 처음에는 잘 동작하던 application이 pressure에서 실패할 수 있습니다. 나중에 문제를 고치기보다 application design에서 contention을 계획하는 편이 좋습니다. Blockchain transaction에 extra business logic을 포함하는 marginal cost는 보통 작습니다.

Distributed system에서 contention은 예상되는 현상입니다. 모든 cost를 감수해 제거하기보다 acceptable level로 줄이고 graceful하게 처리하는 것이 목표입니다. 드물게만 발생한다면 advanced avoidance technique을 구현하는 것보다 occasional allocation failure를 허용하고 retry하는 편이 performance/complexity 측면에서 저렴할 수 있습니다.

Strategic business logic을 신중하게 bundle/batch하면 contention을 줄이는 동시에 blockchain transaction throughput을 훨씬 넘는 business transaction throughput을 얻을 수 있습니다.

## Contention in Daml

Daml은 unspent transaction output(UTXO) ledger model을 사용합니다. UTXO model은 parallel transaction을 지원해 higher performance를 제공하므로 다른 transaction processing 중에도 new transaction을 보낼 수 있습니다. 반면 conflict하는 earlier transaction이 pending인 동안 second transaction이 도착하면 contention이 발생할 수 있습니다.

Daml은 contract마다 consuming choice 하나만 exercise할 수 있도록 보장합니다. 같은 contract를 consume하는 transaction 두 개를 commit하려 하면 write-write contention이 발생합니다.

Incomplete/stale knowledge에서도 contention이 생깁니다. Contract가 archive되었지만 latency 때문에 client가 아직 notification을 받지 못했거나 privacy model상 영원히 알 수 없을 수 있습니다. 같은 contract에서 하나는 read하고 다른 하나는 input을 consume하는 transaction 두 개를 commit하면 read-write contention 위험이 있습니다.

Output consume 여부를 모르면 contract를 pending으로 봅니다. Transaction은 성공한다고 가정하고 pending contract는 이미 consume되었을 가능성이 높다고 취급하는 편이 좋습니다. Pending contract에 대한 action도 실패한다고 가정해야 합니다.

Consuming input request가 input을 consume했는지 confirm하려면 sequencer의 transaction processing을 기다려야 합니다. 같은 contract에 second transaction을 submit하기 전에 first transaction confirmation을 받지 못하면 sequence를 보장하지 않습니다. 이 conflict를 피하려면 두 transaction sequence를 직접 제어해야 합니다.

Daml Execution Model에서 ledger state는 다음 위치에서 read됩니다.

1.  Client가 shared ledger state의 latest view를 기반으로 command를 submit합니다. Client가 active라고 믿는 `ContractIds` reference가 포함될 수 있습니다.
2.  Interpretation 중 ledger state로 active contract를 lookup합니다.
3.  Validation 중 ledger state로 contract를 다시 lookup하고 transaction을 reinterpret해 validate합니다.

Contention은 \#1과 \#2 사이, \#2와 \#3 사이 모두에서 발생할 수 있습니다.

- Client가 \#1에서 active라고 믿는 contract를 기반으로 command를 구성하지만 participant가 \#2 interpretation을 수행할 때는 해당 contract를 consume한 다른 transaction commit을 이미 처리했을 수 있습니다. Participant node가 contention으로 command를 거부합니다.
- Participant가 \#2에서 active라고 믿는 contract를 기반으로 transaction을 성공적으로 구성하지만 \#3 validation 시점에는 같은 contract를 consume하는 다른 transaction이 이미 sequence되었을 수 있습니다. Validating participant가 contention으로 command를 거부합니다.

Transaction 시점의 complete/relevant ledger state는 \#2와 \#3 사이 sequencing 후에만 알 수 있습니다. Double spend protection을 위해 해당 ledger state가 우선합니다.

Contention은 performance를 크게 낮춥니다. 완전히 피할 수는 없지만 logic을 설계해 최소화할 수 있으며 모든 UTXO ledger에 같은 고려사항이 적용됩니다.

# Reduce Contention

모든 action이 asynchronous인 Daml 같은 distributed system에서 contention은 자연스럽고 예상되는 현상입니다. 다양한 cause를 이해하고 error 발생 시 root cause를 diagnose하며 contract를 적절히 설계해 contention을 피할 수 있어야 합니다.

여러 technique으로 contention을 관리하고 throughput 증가/latency 감소를 통해 performance를 개선할 수 있습니다.

- Retry logic 추가
- Causality가 있는 transaction을 series로 실행
- Business logic을 bundle/batch해 business transaction throughput 증가
- Shard 간 contention이 없도록 보장하면서 sharding 등으로 parallelism 최대화
- Natural boundary를 따라 contract를 분할해 single high-contention contract 감소
- Contract의 write-write/write-read contention을 피합니다. 한 requester가 contract의 consuming exercise transaction을 submit하고 다른 requester가 같은 contract의 exercise 또는 fetch를 submit할 때 발생합니다. Client command submission과 다른 client의 committed transaction 인지 사이에는 항상 latency가 있어 완전히 제거할 수 없습니다. 다음 조치로 collision을 줄일 수 있습니다.
  - Data를 shard합니다. Ledger에 user directory를 저장하며 core type이 `[(Text, Party)]`이고 `Text`는 display name, `Party`는 associated Party라고 가정합니다. 전체 list를 single contract에 저장하면 두 user가 동시에 display name을 update할 때 collision이 발생합니다. 각 `(Text, Party)`를 별도 contract에 두면 write operation이 서로 independent해집니다.

    Data structure를 설계할 때 template이 table을 정의하고 contract가 row라고 생각하면 도움이 됩니다. Contract에 large data를 두는 것은 database row에 big blob을 저장하는 것과 같으며 여러 action이 blob을 바꿀 수 있으면 write conflict가 생깁니다.

  - 가능한 경우 collision이 없는 non-consuming choice를 사용합니다. 발생한 event를 model할 수 있으므로 reference할 data를 보유하는 short-lived contract 대신 non-consuming choice를 사용해 ledger event로 기록할 수 있습니다.

  - 여러 party가 같은 contract에서 consuming choice를 동시에 exercise하도록 유도하는 workflow를 피합니다. Field `highestBid : (Party, Decimal)`을 가진 auction contract에서 Alice가 \$100, Bob이 \$90을 동시에 bid하면 Alice bid가 더 높아도 sequencer는 first transaction과 write collision이 있는 second transaction을 거부합니다. Independently update할 수 있는 별도 Bid contract에 기록하는 편이 좋습니다. Race condition data loss를 피하는 relational database structure를 생각해 보세요.

  - `ContractIds` 저장을 신중히 고려합니다. 위 첫 bullet처럼 sharded user directory를 만들고 각 user가 display name/party를 저장하는 `User` contract를 갖는다고 가정합니다. Chat application의 각 `Message` contract가 sender를 `ContractId` User로 reference한다고 가정합니다.

    User가 display name을 바꾸면 reference가 stale해집니다. User가 보낸 모든 message를 수정하거나 Daml에서 sender contract를 사용할 수 없게 됩니다.

    Contract key로 Daml 내부 link를 만들 수 있습니다. `Party`와 `User`를 link할 곳이 user interface뿐이라면 Daml에 contract reference를 전혀 저장하지 않는 편이 좋을 수 있습니다.

# Contention 감소 기법을 적용한 예제 Application

아래 예제 application은 blockchain과 business application 성능의 관계, 그리고 설계 선택이 미치는 영향을 보여줍니다. Trading, settlement 및 관련 system은 blockchain 기술의 핵심 use case이므로, 이 예제에서는 UTXO ledger model 안에서 이러한 system을 설계하는 여러 방법과 각 설계 선택이 application 성능에 미치는 영향을 설명합니다.

## 예제 Minimal Settlement System

이 절에서는 예제 application이 충족해야 할 요구 사항, 성능 측정 방법, contention이 발생할 수 있는 지점을 정의합니다. Party에 asset을 발행하는 초기 process는 이미 준비되어 있다고 가정합니다. 예제의 모든 구체적인 수치는 현실적인 자릿수 규모를 나타내지만 설명만을 위한 값입니다.

### 예제 application의 기본 기능 요구 사항

Trading system은 party들이 asset을 교환할 수 있게 하는 system입니다. 이 예제에서 party는 Alice와 Bob이고 asset은 주식과 달러입니다. 기본 settlement workflow는 다음과 같습니다.

1.  **Proposal**: Alice가 Bob에게 주식 1주와 \$1을 교환하자고 제안합니다.
2.  **Acceptance**: Bob이 교환에 동의합니다.
3.  **Settlement**: 교환이 atomic하게 settlement됩니다. 즉 Alice가 Bob에게 \$1을 이전하는 동시에 Bob은 Alice에게 주식 1주를 이전합니다.

### 예제 application의 실무 및 security 요구 사항

다음 목록은 예제 minimal trading system의 개략적인 기능 요구 사항을 완성하기 위한 실무 조건을 추가합니다.

- Party는 자신이 control하는 여러 asset type의 *asset position*을 보유할 수 있습니다.
  - Asset position은 asset의 type, owner, quantity로 구성됩니다.
  - Asset type은 일반적으로 on-ledger issuer와 symbol의 조합입니다. 예를 들면 currency, CUSIP, ISIN이 있습니다.
- Party는 asset position 전체 또는 일부를 다른 party에게 이전할 수 있습니다.
- Party들은 한 position을 다른 position과 교환하는 settlement에 합의할 수 있습니다.
- Settlement는 atomic하게 수행됩니다.
- Double spend가 없어야 합니다.
- Owner의 *total asset position*이 음수가 되지 않도록 제한할 수 있어야 합니다. 즉 settlement에 필요한 자금이 있음을 보장할 수 있어야 합니다. Total asset position은 해당 owner가 보유한 특정 type의 모든 asset quantity 합계입니다.

### 예제 application의 성능 측정

예제의 성능은 latency와 throughput, 구체적으로 settlement latency와 settlement throughput으로 측정할 수 있습니다. Ledger transaction latency도 중요한 성능 측정 요소입니다.

- **Settlement latency**: 한 party가 settlement를 원한 시점, 즉 proposal 단계 직전부터 settlement가 commit되었다는 최종 확인을 받는 시점, 즉 settlement 단계 이후까지 걸리는 시간입니다. 이 예제에서는 최적 경로로 진행되고 party의 의사 결정에는 시간이 들지 않는다고 가정합니다.

- **Settlement throughput**: system 전체가 장기간 처리할 수 있는 초당 최대 settlement 수입니다.

- **Transaction latency**: client application이 ledger에 command 또는 transaction을 제출한 시점부터 commit 확인을 받는 시점까지 걸리는 시간입니다. 소요 시간은 command에 따라 달라집니다. 100개 settlement batch를 처리하는 transaction은 단일 교환을 처리하는 transaction보다 오래 걸립니다. 이 예제에서는 transaction latency가 고정 비용 `fixed_tx`와 settlement 수에 가변 처리 비용 `var_tx`를 곱한 값으로 구성된다고 가정합니다.

  `transaction latency = fixed_tx + (var_tx * #settlements)`

- 이 예제 application은 settlement proposal과 acceptance에 latency 비용을 부여하지 않습니다.

- 예제 application에서는 다음을 가정합니다.

  - `fixed_tx = 250ms`
  - `var_tx = 10ms`

예제 application의 기준 성능을 설정하기 위해 proposal transaction 하나와 바로 이어지는 settlement transaction 하나로 구성된 가장 단순한 settlement workflow를 살펴봅니다. 이 단순 workflow의 settlement latency는 다음 공식으로 근사할 수 있습니다.

> `(2 * fixed_tx) + var_tx`

`=` `(2 * 250ms) + 10ms`

`=` `510ms`

Settlement를 순차 실행할 때 가능한 초당 settlement 수를 구하면 throughput은 다음 공식으로 계산됩니다. 1초는 1,000ms입니다.

> `1000ms / (fixed_tx + var_tx) settlements per second`

`=` `1000ms / (250ms + 10ms)`

`=` `1000 / 260`

`=` `3.85 or ≈ 4 settlements per second`

이 계산은 고성능 system의 최적 기준선을 설정합니다.

다음 목표는 latency를 크게 늘리지 않으면서 throughput을 높이는 것입니다. 기반 DLT에는 전체 throughput과 transaction size 한도가 있다고 가정합니다. DLT system의 최소 throughput 단위를 나타내는 `dlt_min_tx`라는 단위를 사용하는 단순 cost model을 적용합니다. 빈 transaction의 고정 비용 `dlt_fixed_tx`는 다음과 같습니다.

> `dlt_fixed_tx = 1 dlt_min_tx`

Settlement의 한계 throughput 비용과 transaction throughput 비용의 비율이 앞서 본 한계 latency와 transaction latency의 비율과 대략 같다고 가정합니다. 그러면 settlement 한 건의 한계 throughput 비용 `dlt_var_tx`는 다음 계산으로 구할 수 있습니다.

> `dlt_var_tx = ratio * dlt_fixed_tx`

`=` `dlt_var_tx = (var_tx / fixed_tx) * dlt_fixed_tx`

`=` `dlt_var_tx = 10sm/250ms * dlt_fixed_tx`

`=` `dlt_var_tx = 0.04 * dlt_fixed_tx`

그리고 앞서 다음을 정의했으므로

> `dlt_fixed_tx = 1 dlt_min_tx`

결과는 다음과 같습니다.

> `dlt_var_tx = 0.04 * dlt_min_tx`

병렬 처리가 잘 되어도 ledger에는 한계가 있습니다. CPU, database 또는 network가 제약이 될 수 있으므로 가장 먼저 도달하는 상한을 계산하고 그에 맞게 설계해야 합니다. 구체적으로 최대 throughput `max_throughput`은 `dlt_min_tx/second`로 측정하고, 최대 transaction size `max_transaction`은 `dlt_min_tx`로 측정합니다. 이 예제에서는 CPU 병목이 `max_throughput`을 제한한다고 가정합니다. 사용할 수 있는 CPU가 10개이고 빈 transaction 하나가 CPU 시간 10ms를 사용한다면 매초 다음과 같습니다.

> `max_throughput = 10 * each CPU’s capacity`

각 `dlt_min_tx`에는 10ms가 들고 1초는 1,000ms이므로 CPU 하나의 capacity는 초당 100 `dlt_min_tx`입니다. 따라서 throughput은 다음과 같습니다.

> `max_throughput = 10 * 100 dlt_min_tx/second`

`=` `max_throughput = 1,000 dlt_min_tx/second`

마찬가지로 `max_transaction`은 message size limit에 의해 제한될 수 있습니다. 이 예제에서는 message size limit이 3MB이고 빈 transaction `dlt_min_tx`가 1MB라고 가정합니다.

> `max_transaction = 3 * dlt_min_tx`

세 transaction 중 하나는 settlement 없이 approval을 담아야 합니다. 따라서 가능한 가장 큰 transaction에서 여러 settlement를 담는 데 사용할 수 있는 공간은 `(2 * dlt_min_tx)`에 해당합니다. 앞서 정의한 비율에 따라 settlement 한 건의 `dlt_var_tx`는 `0.04 * dlt_min_tx`를 사용합니다. 따라서 초당 최대 settlement 수는 다음과 같습니다.

> `(2 * dlt_min_tx)/(0.04 * dlt_min_tx)`

`=` `50 settlements/second`

같은 가정에서 settlement를 순차 처리하지 않고 병렬 처리하되 transaction마다 settlement 하나만 담으면 latency는 일정하게 유지되고 settlement throughput은 증가합니다. 앞서 단순 workflow는 `(2 * fixed_tx) + var_tx`가 될 수 있다고 했습니다. DLT system에서는 다음과 같이 계산합니다.

> `(2 * dlt_min_tx) + dlt_var_tx`

`=` `(2 * dlt_min_tx) + (0.04 * dlt_min_tx)`

`=` `2.04 * dlt_min_tx`

앞서 max_throughput을 `1,000 dlt_min_tx/second`로 가정했습니다. 따라서 예제 DLT system에서 병렬 처리만으로 가능한 초당 최대 settlement 수는 다음과 같습니다.

> `1,000/2.04 settlements per second`

`=` `490.196 or ~490 settlements per second`

이 계산은 성능 개선 기법들을 비교할 때 사용할 기준선을 제공합니다. 다음 절에서 해당 기법들을 설명합니다.

## Contention 없는 병렬 처리를 위한 Transaction 준비

이 절에서는 UTXO ledger model에서 어떤 요소를 병렬 처리하여 성능을 높일 수 있는지 살펴봅니다. UTXO ledger model에서 system state는 immutable contract 집합으로 구성되며, 이를 UTXO라고도 부릅니다.

Contract에는 두 가지 일만 일어날 수 있습니다. 생성된 뒤 소비되거나 사용됩니다. 각 transaction은 input contract 집합과 output contract 집합이며 두 집합은 겹칠 수 있습니다. Transaction은 같은 transaction에서 소비되지 않은 output contract를 생성하고, smart contract logic에서 소비하지 않도록 정의한 경우를 제외하면 input contract를 소비합니다.

Smart contract logic을 제외하면 모든 UTXO ledger system의 execution model은 같습니다.

1.  **Interpretation**: 제출 party가 input/output contract로 구성된 transaction을 미리 계산합니다.
2.  **Submission**: 제출 party가 transaction을 network에 제출합니다.
3.  **Sequencing**: network의 consensus algorithm이 모든 transaction의 전체 순서에서 해당 transaction의 위치를 지정합니다.
4.  **Validation**: transaction을 검증하며, input이 이전 transaction에서 이미 사용되지 않았다면 유효한 것으로 판단합니다.
5.  **Commitment**: transaction을 commit합니다.
6.  **Response**: 제출 party가 transaction이 commit되었다는 response를 받습니다.

이 과정에서 순차 요소가 있는 유일한 단계는 sequencing입니다. Transaction 처리의 다른 모든 단계는 병렬화할 수 있으므로 UTXO는 고성능 system에 적합한 model입니다. 다만 제출 party에는 문제가 있습니다. Interpretation 단계는 사용 가능한 input contract를 알아야 하며, 정의상 이는 이전 transaction의 미사용 output입니다. 이러한 output은 최소 `fixed_tx` 지연이 지난 response 단계에서야 알 수 있습니다.

예를 들어 한 party가 \$1,000 contract 하나를 가지고 \$1씩 1,000건을 settlement하려 한다고 가정합니다. 1,000건 모두를 병렬로 sequencing하면 1,000개 transaction이 같은 contract를 소비하려 합니다. 하나만 성공하고 나머지는 contention으로 실패합니다. System이 남은 999건, 그다음 998건을 반복 재시도할 수 있지만 성능이 좋은 system이 되지는 않습니다. 반면 settlement당 예제 latency 260ms를 적용해 순차 처리하면 `max_throughput`이 제시하는 이론적 최적값 1초가 아니라 260초, 즉 4분 20초가 걸립니다. Trading party에는 더 나은 전략이 필요합니다. 다음을 가정합니다.

> `max_transaction > dlt_fixed_tx + 1,000 * dlt_var_tx = 41 dlt_min_tx`

Trading party는 1,000건을 모두 다음 시간이 드는 단일 transaction으로 처리할 수 있습니다.

> `fixed_tx + 1,000 * var_tx = 10.25s`

Latency 한도가 너무 작거나 이 latency를 허용할 수 없다면 trading party는 세 단계로 \$1,000을 다음과 같이 나눌 수 있습니다.

- 10 \* \$100
- 100 \* \$10
- 1,000 \* \$1

그런 다음 1,000건의 settlement를 병렬 처리합니다. 이때 이론적 latency는 다음과 같습니다.

> `3 * fixed_tx + (fixed_tx + var_tx) = 1.01s`

하지만 실제 settlement는 750ms 후에 시작되고 `max_throughput`은 `1,000 dlt_min_tx/s`이므로 실제 값은 다음과 같습니다.

> `0.75s + (1,000 * (dlt_fixed_tx + dlt_var_tx)) / 1,000 dlt_min_tx/s = 1.79s`

이러한 전략은 시작 state가 매우 정적인 특정 상황에 적용됩니다. 실제 고성능 system의 전략은 다음 가정에서도 성능을 내야 합니다.

- 예측하기 어려운 settlement 요청이 계속 들어옵니다. 이를 어떤 분포에서 생성되는 무한한 random settlement stream으로 보고 합리적인 latency에서 settlement throughput을 최대화해야 합니다.
- Withdrawal, rejection, business error 때문에 모든 settlement가 성공하지는 않습니다.

여러 기법을 비교하기 위해 settlement workflow가 앞서 Alice와 Bob의 예로 설명한 다음 단계로 구성된다고 가정합니다.

1.  **Proposal**: settlement 제안
2.  **Acceptance**: settlement 수락
3.  **Settlement**: 실제 settlement

일반적으로 acceptance와 settlement 단계를 transaction 하나로 묶어 이 과정을 두 transaction으로 나눕니다. 첫 두 단계인 proposal과 acceptance에는 contention이 없고 모든 contention은 마지막 settlement 단계에서 발생한다고 가정합니다. Cost model은 latency와 throughput 비용 `var_tx`, `dlt_var_tx` 전체를 settlement에 할당하므로 여기서 다루는 대상은 고성능 trading system보다는 고성능 settlement system입니다. 다음 절에서는 이러한 가정에서 사용할 수 있는 trading 전략과 tradeoff를 설명합니다.

## UTXO가 아닌 대안 Ledger Model

UTXO ledger model의 대안으로 transaction 계산이 sequencing 이후에만 이루어지는 replicated state machine ledger model을 사용할 수 있습니다.

단계는 다음과 같습니다.

1.  **Submission**: 제출 party가 command를 network에 제출합니다.
2.  **Sequencing**: network의 consensus algorithm이 모든 command의 전체 순서에서 해당 command의 위치를 지정합니다.
3.  **Validation**: command를 transaction으로 평가한 뒤 검증합니다.
4.  **Response**: 제출 party가 command의 결과에 대한 response를 받습니다.

**장점**

이 기법은 제출 party에 contention이 없다는 큰 장점이 있습니다. Party가 들어오는 transaction stream을 ledger의 command stream으로 전달하면 나머지는 ledger가 처리합니다.

**단점**

이 접근 방식의 단점은 제출 party가 command의 결과를 예측할 수 없다는 것입니다. 이 때문에 system은 frontrunning이나 reordering 같은 공격에 취약해집니다.

또한 validation 단계는 최적화하기 어렵습니다. Command 평가는 이전 command의 결과에 의존할 수 있으므로 일반적으로 single-thread 방식으로 수행합니다. Transaction 평가는 최소한 transaction validation만큼 비용이 듭니다. 단순화하여 `var_tx`의 대부분이 evaluation과 validation 비용이라고 가정하면 single-thread system은 초당 `1s / var_tx = 100` settlement로 제한됩니다. Hardware를 추가해도 더 확장할 수 없습니다.

## UTXO Ledger Model을 위한 단순 전략

높은 throughput과 scalability를 달성하려면 UTXO가 적합한 ledger model입니다. 다만 settlement 처리를 병렬화하려면 contention을 줄이는 전략이 필요합니다.

### Transaction을 batch로 묶어 순차 처리

`(var_tx << fixed_tx)`이므로 settlement 두 건을 transaction 하나에서 처리하는 편이 두 transaction으로 처리하는 것보다 훨씬 저렴합니다. 한 가지 전략은 transaction을 batch로 묶고 한 번에 batch 하나씩 순차 제출하는 것입니다.

**장점**

이 기법은 replicated state machine model과 마찬가지로 contention을 완전히 제거합니다. Reordering이나 frontrunning 공격에도 취약하지 않습니다.

**단점**

Replicated state machine 기법처럼 각 batch는 single-thread 방식으로 실행됩니다. 여기에 evaluation 시간뿐 아니라 transaction latency도 추가됩니다. Batch size를 `N < max_settlements`라고 가정하면 latency는 다음과 같습니다.

> `fixed_tx + N * var_tx`

Transaction throughput은 다음과 같습니다.

> `N / (fixed_tx + N * var_tx)`

`N`이 증가하면 이 값은 `1 / var_tx = 100`에 가까워지며, replicated state machine ledger의 throughput과 같습니다.

또한 `max_settlements` 상한이 있습니다. `max_settlements = 50`이라고 가정하면 throughput은 초당 `50 / 0.75 = 67` settlement transaction, latency는 750ms로 제한됩니다. Proposal과 acceptance 단계가 settlement 전에 transaction 하나를 더 추가한다고 가정하면 settlement throughput은 초당 67건이고 settlement latency는 1초입니다. 처음의 초당 4건보다는 낫지만 완전한 병렬 처리로 가능한 초당 490건과는 큰 차이가 있습니다.

또한 transaction batch 전체의 성공과 실패가 함께 묶입니다. Transaction 하나라도 어떤 이유로든 실패하면 전부 실패하며 error handling도 복잡합니다. Daml exception handling 같은 기능으로 일부 완화할 수 있지만 contention error는 처리할 수 없습니다. System에서 둘 이상의 party가 활동하고 party 간 contention 가능성이 있는 한, 일반적으로 그러하듯 batch가 실패할 수 있습니다. Batch가 클수록 실패 가능성과 실패 비용이 모두 커집니다.

### Asset type과 owner별 순차 처리 또는 batching

이 기법에서는 모든 contention이 asset allocation 단계에서 발생한다고 가정합니다. 다음 Daml code snippet처럼 ledger의 단일 contract가 모든 bookkeeping을 담당한다고 생각해 봅니다.

```haskell
template AllAssets
  with
    -- A map from owner and type to quantity
    holdings : Map Party (Map AssetType Decimal)
  where
    signatory (keys holdings)
```

이는 contention이 중요하지 않은 replicated state machine ledger의 전형적인 pattern입니다. 하지만 UTXO ledger에서는 asset에 대한 임의의 두 operation 사이에 contention이 발생합니다. 이러한 asset 표현에서는 순차 batching보다 나은 성능을 낼 수 없습니다. Privacy와 contract size를 포함한 다른 문제도 많습니다.

일반적으로 한 번에 한 owner가 보유한 한 type의 asset만 변경하고 non-negativity 같은 constraint도 그 수준에서 적용하므로, UTXO ledger에서는 보통 다음 Daml code snippet처럼 asset을 asset position으로 표현합니다.

```haskell
template
  with
    assetType : AssetType
    owner : Party
    quantity : Decimal
  where
    signatory assetType.issuer, owner
```

Asset position은 owner, asset type, quantity의 세 값을 담은 contract입니다. 한 owner가 가진 특정 asset type의 total asset position은 같은 owner와 asset type을 가진 모든 asset position의 quantity 합계입니다. Settlement transaction이 buy-side의 total asset position 두 개와 sell-side의 total asset position 두 개를 변경한다면 asset type과 owner별 batching의 효과는 크지 않습니다.

Alice가 Bob과 USD를 EUR로 settlement하고, Bob은 Carol과 EUR를 GBP로 settlement하며, Carol은 Alice와 GBP를 USD로 settlement하려 한다고 가정합니다. 세 settlement transaction 모두 contention을 겪으므로 순차 batching보다 나은 성능을 낼 수 없습니다.

반면 각 transaction이 total asset position 하나만 변경하도록 보장할 수 있다면 total asset position별로 순차 처리나 batching을 적용할 수 있습니다. Settlement 단계를 다음과 같이 분해하면 항상 가능합니다.

1.  **Buy-side allocation**: buy-side가 자신의 total asset position에서 asset position을 분리해 settlement에 할당합니다.
2.  **Sell-side allocation**: sell-side가 자신의 total asset position에서 asset position을 분리해 settlement에 할당합니다.
3.  **Settlement**: asset position의 ownership이 변경됩니다.
4.  **Buy-side merge**: buy-side가 새 position을 total asset position에 다시 병합합니다.
5.  **Sell-side merge**: sell-side가 새 position을 total asset position에 다시 병합합니다.

이 과정이 반드시 다섯 transaction이 되어야 하는 것은 아닙니다.

- Buy-side allocation은 보통 settlement proposal의 일부로 수행합니다.
- Sell-side allocation은 일반적으로 settlement의 일부로 처리합니다.
- Buy-side merge와 sell-side merge에는 기술적으로 별도 action이 필요하지 않습니다. Total asset position의 정의상 merge는 선택적 단계입니다. 추가 transaction 없이도 정리된 상태를 유지하기 쉽습니다. 위의 buy-side 또는 sell-side allocation 과정에서 total asset position을 변경할 때마다 모든 position을 하나로 병합할 수 있습니다. Total asset position의 inbound/outbound traffic 양이 비슷하면 개별 position 수는 낮게 유지됩니다.

**장점**

Settlement 단계 후 settlement가 완료된 것으로 보고 위 allocation 단계를 proposal과 settlement 단계에 묶는다면 system 성능은 최적 settlement latency인 510ms를 유지합니다.

또한 서로 다른 total asset position에 open settlement가 충분하면 전체 throughput은 최적값인 초당 490건까지 도달할 수 있습니다.

Proposal과 settlement 모두 batch size가 `N=50`이고 open settlement가 있는 total asset position이 충분하다면 이론상 최대 settlement throughput은 다음과 같습니다.

`50 stls * 1,000 dlt_min_tx/s / (2 * dlt_fixed_tx + 50 * dlt_var_tx) = 12,500 stls/s`

**단점**

Batching을 사용하지 않으면 total asset position별 outgoing settlement가 처음 계산한 초당 4건으로 제한됩니다. Central counterparty의 USD position처럼 traffic이 많은 asset이 있으면 system 전체의 병목이 될 수 있습니다.

Batch size를 높이면 global 수준이 아닌 total asset position 수준이라는 점을 제외하고 순차 batching과 같은 tradeoff가 발생합니다. Latency도 순차 batching과 동일하게 증가합니다.

Batch size 50을 사용하면 settlement latency는 약 1.5초이고 total asset position별 최대 throughput은 초당 67건입니다.

또 다른 단점은 settlement 전에 transaction에서 buy-side asset을 할당하므로 asset position이 잠시 lock될 수 있다는 것입니다.

Settlement가 실패하면 이미 할당한 asset을 total asset position에 다시 병합해야 합니다.

## UTXO Ledger Model의 Asset Position Sharding

단일 total asset position의 peak load가 초당 수십 또는 수백 settlement에 이르는 system에는 더 정교한 전략이 필요합니다. 해당 total asset position을 단일 asset position으로 구성할 수 없으며 shard로 나누어야 합니다.

### Global constraint가 없는 total asset position sharding

On-ledger constraint 없이 bookkeeping position을 나타내는 total asset position을 생각해 봅니다. 예를 들어 trading system이 fiat settlement를 off-ledger에서 처리하고 양수 또는 음수 여부와 관계없이 balance만 기록하려 할 수 있습니다. 이 상황에서는 모든 allocation에 임의 금액을 지정하여 contention을 쉽게 완전히 제거할 수 있습니다. Settlement에 \$1을 할당하려면 ledger에 \$1과 -\$1의 새 asset position 두 개를 기록한 뒤 \$1을 할당에 사용합니다. Total asset position은 변하지 않습니다.

**장점**

이 접근 방식은 total asset position의 모든 contention을 제거합니다.

Global constraint가 없는 두 total asset position 사이의 trading은 이론상 최적 latency와 throughput으로 실행할 수 있습니다. 이를 batch size 50의 batching과 결합하면 global 수준에서 가능한 것과 같은 total asset position별 초당 최대 12,500 settlement를 달성할 수 있습니다.

**단점**

Total asset position에 global constraint를 적용할 수 없을 뿐 아니라 많은 새 contract가 생성됩니다. 초당 500 settlement, settlement당 allocation 2개, allocation당 새 asset 2개라면 초당 새 asset position 2,000개가 생성되어 빠르게 누적됩니다.

이 영향은 일정 주기마다 여러 position을 하나로 netting하는 automation으로 완화해야 합니다. 예를 들어 total position에 asset position이 \>= 100개가 될 때마다 수행할 수 있습니다. 이 automation은 trading과 contention을 일으키지 않지만 system에 초당 최대 20개의 큰 transaction을 추가하여 전체 throughput을 조금 낮춥니다.

### Global constraint가 있는 total asset position sharding

Global constraint의 예로 total asset position이 항상 양수여야 한다고 가정합니다. 일반적으로 각 asset position이 양수임을 보장하는 방식으로 구현합니다. 이 경우 total position을 더 작은 `N`개의 shard position으로 분해하는 sharding scheme을 정의하고 shard position별로 순차 처리 또는 batching을 실행합니다.

Shard 사이에 contention이 없도록 각 asset position을 단일 shard position에 명확히 할당할 수 있어야 합니다. Total asset position을 반드시 on-ledger에서 partition할 필요는 없습니다. 모든 shard의 automation이 off-ledger에서 통신할 수 있다면 원하는 asset position 총수를 설정하는 방식으로 sharding 전략을 실행할 수 있습니다.

예를 들어 일정 최소값을 가진 total asset position에 asset position 100개를 유지해야 한다고 가정합니다.

- Automation은 사용 중인 asset position을 표시하는 synchronized pending asset position 집합을 추적합니다.
- Automation이 trigger될 때마다 동시에 여러 번 발생할 수도 있으며, 목표 100개 대비 현재 asset position 수와 open settlement 할당에 필요한 quantity를 확인합니다.
- 그런 다음 적절한 non-pending asset position 집합을 선택하여 open settlement를 할당하고, 총수가 100에 가까워지도록 새 asset position을 반환합니다.
- Transaction을 보내기 전에 해당 position을 pending 집합에 추가하여 다른 thread가 동시에 사용하지 못하게 합니다.

다른 방법으로 settlement value에 비해 total position이 충분히 크다면 settlement value의 99th percentile인 `p_99`를 선택하고, 값이 `p_99`와 `2 * p_99` 사이인 `N-1`개 position과 나머지 큰 값의 position 하나를 유지할 수 있습니다. Transaction의 99%는 `N-1`개 shard position에서 처리하고 나머지 1%는 remaining pool에서 처리합니다. Shard가 원하는 범위를 벗어나면 pool과 다시 balance를 맞춥니다.

**장점**

Total asset position에 항상 충분한 liquidity가 있다고 가정하면 global constraint가 없는 경우와 같은 성능, 즉 단일 total asset position에서 초당 최대 12,500 settlement를 달성할 수 있습니다.

**단점**

Settlement value가 total asset holding에 비해 크면 이 기법의 효과는 작습니다. 극단적으로 모든 settlement에 total holding의 50%를 넘는 값이 필요하다면 asset type과 owner별 순차 처리 또는 batching 기법보다 나은 성능을 내지 못합니다.

실제 환경에서는 settlement value가 total asset position 대비 넓은 범위에 분포하고 holding이 증감함에 따라 상대 비율도 변하므로 최적으로 동작하는 전략을 개발하기가 복잡합니다. 다음의 상충하는 우선순위를 신중하게 조정해야 합니다.

- Active contract 수가 system 성능에 영향을 주지 않도록 asset position 총수를 제한합니다.
- 빈번한 소액 settlement를 병렬 처리할 수 있도록 충분한 수의 큰 asset position을 유지합니다.
- 사용 가능한 total asset position의 최대 100%가 필요할 수 있는 큰 settlement가 차단되지 않게 하는 mechanism을 마련합니다.

## Application 개발 성능 실무

_Module 7의 Performance Best Practices에서 이동한 내용입니다._

Canton application의 performance optimization은 on-ledger와 off-ledger operation의 경계를 이해하고 어떤 정보가 그 경계를 넘어갈지 의도적으로 선택하는 것을 의미합니다. Ledger operation에는 database operation에는 없는 synchronization overhead가 있으므로 business-critical state는 on-ledger에 유지하면서 불필요한 ledger interaction을 최소화해야 합니다.

## On-Ledger와 Off-Ledger

{/* COPIED_START source="docs-website:manual/build/3.5/sdlc-howtos/sdlc-best-practices.rst" hash="on-off-ledger" */}

Canton Network application을 설계할 때는 on-ledger와 off-ledger 구현을 신중하게 비교하여 성능 특성을 고려해야 합니다. 정보를 on-ledger에 저장할지 결정할 때는 다음 기준을 사용합니다.

- **State** — Workflow의 핵심 사실입니다. 조직 간 합의가 필요한 사실은 on-ledger에 저장합니다.
- **Data** — 핵심이 아닌 사실입니다. 효율성을 위해 중요하지 않은 data는 off-ledger 기술로 공유합니다.
- **Workflows** — 조직 경계를 넘는 workflow만 on-ledger에 배치합니다.

{/* COPIED_END */}

실제 예로 licensing application에서는 양쪽 party가 license의 상태에 합의해야 하므로 license 자체, 즉 보유자, 적용 범위, 활성 여부는 on-ledger에 둡니다. License의 상세 설명, marketing 자료, usage analytics는 일반 database의 off-ledger data로 두는 것이 적합합니다.

### Transaction별 stakeholder 최소화

Contract에 signatory나 observer를 추가할 때마다 transaction protocol에 참여해야 하는 party가 늘어납니다. Business logic이 요구하는 범위 안에서 stakeholder 집합을 최소화합니다.

### Contract key를 신중하게 사용

Contract key는 효율적인 lookup을 제공하지만 contention을 유발합니다. 여러 transaction이 같은 key를 가진 contract를 동시에 생성하거나 exercise하려 하면 충돌합니다. Party나 business entity를 기준으로 자연스럽게 partition되도록 key를 설계하여 contention을 줄입니다.

### PostgreSQL tuning

기본 PostgreSQL Docker image는 최소 설정으로 제공됩니다. 실제 workload에서는 다음 항목을 tuning합니다.

- `max_connections` — 예상 connection pool size에 맞춥니다.
- `autovacuum` settings — Write pattern에 맞게 tuning합니다.

### Query pattern

- `explain analyze`를 사용해 query가 index를 사용하는지 확인합니다.
- 모든 contract를 가져와 application code에서 filtering하는 대신 SQL에서 filtering합니다.
- Time-series query에는 active contract set 대신 event table을 사용합니다.
- 자주 실행하는 aggregation query에는 materialized view 사용을 고려합니다.

## 병렬 Command 제출

Ledger API는 병렬 command 제출을 지원합니다. 서로 다른 contract에 영향을 주는 command는 synchronizer에서 동시에 실행될 수 있습니다. 이를 활용하도록 backend를 구성합니다.

- Backend에서 async/concurrent command 제출을 사용합니다.
- Deduplication을 위해 고유한 command ID를 할당합니다.
- 영향을 주는 contract별로 command를 그룹화하여 contention을 피합니다.
- Command 완료 시간을 monitoring하여 병목 pattern을 찾습니다.

## Traffic Management

DevNet, TestNet, MainNet에서는 모든 ledger transaction이 Canton Coin(CC)으로 구매한 traffic credit을 소비합니다. 다음 방법으로 traffic 비용을 최적화합니다.

- On-ledger transaction의 수와 size를 줄입니다.
- 가능한 경우 batch operation을 사용합니다.
- Peak usage 중 traffic 부족을 방지하도록 auto-top-up을 설정합니다.
- Traffic 소비 pattern을 monitoring하여 비용을 예측합니다.
