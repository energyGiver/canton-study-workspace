# Canton Network Quickstart observability 및 문제 해결 개요

<Note>
이 가이드의 screenshot은 여러 session에서 가져왔기 때문에 서로 일관되지 않습니다. 일부 update가 commit되면 이를 바로잡을 예정입니다.
</Note>

Quickstart 시작 가이드와 demo 살펴보기를 이미 읽었다고 가정합니다. 아직 읽지 않았다면 observability의 기본적인 이해를 갖추기 위해 해당 문서를 읽어 보기를 강력히 권장합니다.

## Observability 개요

Canton Network Quickstart deployment configuration에는 완전한 observability suite가 포함되어 있습니다. 개발 환경과 production 환경 모두에서 분산 Canton application을 monitoring하고 문제를 해결할 수 있도록 tool이 미리 구성되어 있습니다. Observability suite는 다음 세 가지 핵심 monitoring data를 제공합니다.

- Application 및 system event를 위한 **통합 structured log**
- End-to-end transaction flow를 시각화하는 **distributed trace**
- 핵심 성능 지표를 monitoring하는 **metric**

이 suite를 사용하면 data type을 서로 연결하여 root cause analysis를 위한 insight를 얻을 수 있습니다. 또한 Canton Ledger는 여러 조직과 환경에 걸쳐 Transaction의 provenance를 추적할 수 있도록 다양한 correlation ID와 tracing ID를 제공합니다.

### LocalNet configuration

Quickstart runtime configuration은 `.env.local`에 정의되며, 이를 통해 Observability Stack의 local deployment를 실행할지 선택할 수 있습니다. 이 파일은 `$ make setup`으로 만들 수 있으며, 이 command는 `$ ./gradlew configureProfiles --no-daemon --console=plain --quiet`를 감쌉니다. 또는 직접 편집하여 환경 변수 `LOCALNET_ENABLED`와 `OBSERVABILITY_ENABLED`를 필요에 따라 `true` 또는 `false`로 설정할 수 있습니다.

`LocalNet` runtime configuration은 `docker-compose`가 처리하며, `compose.yaml`에서 `.env`의 환경 변수를 사용하도록 구성됩니다. 이 파일은 `quickstart/` project root directory에 있습니다. 일반적인 Docker command와 tooling을 적용할 수 있습니다.

바로 유용하게 사용할 수 있으며 이미 알고 있을 가능성이 높은 command는 다음과 같습니다.

- `$ docker ps`는 실행 중인 container를 나열합니다.
- `$ docker logs [-f] <container>`는 container log를 가져오며, `-f` option을 사용하면 log를 계속 추적합니다.
  - 나중에 설명할 observability stack을 신뢰하기 어려울 정도로 system이 제대로 작동하지 않는다면, 문제 원인을 파악할 단서를 제공하는 error를 찾기 위해 `docker logs backend-service`부터 확인하는 것이 좋습니다.
- Container가 멈춘 것처럼 보일 때는 `$ docker restart <container>`를 사용합니다.

### Observability 개괄

Quickstart application은 production Daml application의 기초를 제공합니다. Application 문제 해결과 debug에 도움이 되는 완전한 observability configuration이 포함되어 있습니다. 실행 가능한 demo인 Quickstart는 선택한 technology stack에 대해 명확한 방향성을 갖지만, platform 자체는 특정 기술에 종속되지 않습니다. 필요에 따라 개별 component를 교체할 수 있습니다.

현재 제공되는 문제 해결 및 debugging service는 다음과 같습니다.

- [Daml Shell](/sdks-tools/cli-tools/daml-shell)을 통한 local ledger 검사
- **OpenTelemetry**를 통한 datasource 수집 및 관리
  - **OTEL Collector**를 사용합니다([https://opentelemetry.io/docs/collector](https://opentelemetry.io/docs/collector)).
- **Prometheus**를 사용한 metric 집계([https://prometheus.io/](https://prometheus.io/))
- **lnav**를 사용한 log 검사([lnav 다운로드 및 문서](/appdev/quickstart/lnav) page 참조)
- **Tempo**를 사용한 trace 집계([https://grafana.com/oss/tempo/](https://grafana.com/oss/tempo/))
- Observability field를 hyperlink로 탐색할 수 있게 해주는 **Grafana**를 통한 집계된 관측 결과(metric, log, trace) 확인([https://grafana.com/oss/grafana/](https://grafana.com/oss/grafana/))

#### Daml Shell

Daml Shell은 PQS 위에서 대화형 local ledger 검사를 제공하는 terminal application입니다. Quickstart는 Docker container에서 Daml Shell을 실행하고 포함된 application provider의 PQS instance에 연결하도록 구성되어 있습니다. 최상위 project script를 `make`로 실행하는 것이 가장 간단하며, 이 script는 `quickstart/`에서 접근합니다. 실제로 확인하려면 Quickstart app을 build하고 시작한 다음 아래 절차를 따릅니다.

`$ make create-app-install-request`를 실행하여 `curl`로 `create AppInstallRequest ...` command를 ledger에 제출하고[^1] user onboarding을 시작합니다.[^2] 그런 다음 다음 Daml Shell command를 사용할 수 있습니다.

\> `active`: 생성한 contract의 요약을 확인합니다.

\> `active quickstart-licensing:Licensing.AppInstall:AppInstallRequest`: Ledger의 Asset contract에 대한 contract 상세 정보를 확인합니다.

\> `contract [contract-id from the previous command]`[^3]: Ledger의 `AppInstallRequest` contract 전체 상세 정보를 확인합니다.

\> `help [command]`: Daml Shell command에 대한 상황별 도움말을 제공합니다.[^4]

#### Grafana

Grafana는 [http://localhost:3030/](http://localhost:3030/)에 port mapping된 web interface를 통해 접근할 수 있으며, command line에서 `make open-observe`를 실행하면 현재 browser에서 열 수 있습니다.

Debugging할 때는 Grafana의 trace와 log 기능, 그리고 Daml Shell을 통한 ledger 검사에 집중해야 합니다. 개발 중 debugging을 지원하기에 충분한 log와 trace를 export하도록 하면 production에서도 진단을 지원할 가능성이 높아집니다.

Quickstart에는 `LocalNet` debugging에 도움이 되는 추가 access도 구성되어 있습니다. 개발과 production에서 동일한 진단 tool을 사용하세요. 개발 중 bug를 식별하고 수정할 수 있는 log line을 추가했다면 이를 `trace` 또는 `debug` log level로 유지하면 운영 준비 수준이 높아집니다. Production에서 사용할 수 없는 tool로 개발 환경을 debug하면 운영 준비 수준이 낮아집니다.

#### Postgres 직접 접근

예제 application의 모든 persistent state는 하나 이상의 Postgres database에 저장됩니다. `.env`의 Postgres configuration을 사용해 이러한 instance에 직접 연결할 수 있습니다.

## Observability와 tracing

오류가 있는 분산 system은 진단하기 매우 어려울 수 있습니다. Quickstart는 보통 project 후반에야 개발되는 observability와 진단 기능을 project 시작부터 제공합니다. 각 project의 처음부터 새로운 Canton Network Application의 진단을 단순화하는 것이 Quickstart를 개발한 동기 중 하나입니다.

개요의 link에는 Quickstart에 포함된 여러 tool의 공식 user 및 reference documentation이 있습니다. 공식 documentation을 대체할 수는 없지만, 다음 Quickstart 기능 둘러보기가 직접 실험을 시작하는 출발점이 되기를 바랍니다.

### Correlation identifier

다른 분산 system을 검사할 때와 마찬가지로 Canton 검사도 identifier를 서로 연결하는 것에서 시작합니다. Canton은 시간, 여러 node 및 변화하는 ledger state 전반의 correlation에 적합한 다양한 identifier를 수신하거나 생성할 수 있습니다.

알아 두어야 할 핵심 identifier는 다음과 같습니다.

| `Identifier`       | `Specified by`                | `Scope`                                                                                                                                                                                                                                                      |
|--------------------|-------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `ApplicationId`    | `The Ledger Client`           | `Identifies the ledger client during command submission and processing.`                                                                                                                                                                                     |
| `WorkflowId`       | `The Ledger Client`           | `Identifies the business process. Persisted to the ledger.`                                                                                                                                                                                                  |
| `CommandId`        | `The Ledger Client`           | `Identifies the business “act” associated with a ledger command. Persisted to the ledger. Visible only to the submitting party. Common across retries.`                                                                                                      |
| `SubmissionId`     | `The Ledger Client`           | `Identifies an individual ledger submission to a participant node.`                                                                                                                                                                                          |
| `TransactionId`    | `Daml Ledger`                 | `Global identifier for a committed transaction to the ledger. Only visible to participant nodes that witness or are informed of the transaction.`[^5]                                                                                                        |
| `LedgerEventId`    | `Daml Ledger`                 | `Global identifier for a node within a committed transaction tree corresponding to a ledger event.`                                                                                                                                                          |
| `Trace/SpanId`[^6] | `Ledger Client (or upstream)` | `Accepted by GRPC/HTTP ledger interfaces and honoured throughout the Canton Network code. Where one is not provided may sometimes be generated internally to provide tracing support within the network.`                                                    |
| `LedgerOffset`     | `Participant Node`            | `The height of a transaction within the local linearization of the ledger by a participant node.`[^7]                                                                                                                                                        |
| `ContractId`       | `Daml Ledger`                 | `Global identifier for a contract that was created successfully on the ledger at some point. If the contract has been subsequently archived the id remains a stable and valid way to refer to it even though the associated contract can no longer be used.` |
| `TemplateId`       | `Daml Application`            | `Combined with a PackageId this provides a global identifier for a Daml smart contract.`                                                                                                                                                                     |
| `PartyId`          | `Participant Node`            | `Identifier of the Party on the Canton ledger.`[^8]                                                                                                                                                                                                          |

유용한 Correlation Identifier

Observability configuration의 목표는 더 넓은 system에 있는 state나 event의 provenance를 쉽게 탐색하도록 하는 것입니다. 이러한 identifier 일부 또는 전부를 사용해 log, metric 및 state의 조합을 연결할 수 있습니다. 특히 application-id, workflow-id, command-id 세 가지는 해당 business domain에서 파생된 business identifier에 맞춰 설정하기 위한 것입니다.

가능한 한 많은 component에서 structured log를 사용하여 탐색할 수 있습니다.[^9] Custom component도 OpenTelemetry가 더 정확히 처리할 수 있도록 structured log를 내보내는 것이 좋습니다.

- AppInstall contract를 가져오기 위한 backend의 PQS query
- Backend Service에서 App-Provider Ledger API로 보내는 call
- Participant Node의 Transaction 준비 및 Canton Network 제출

Grafana suite의 매우 강력한 측면 중 하나는 Quickstart stack의 여러 observability tool을 통합하는 수준입니다. 앞서 통합 log에서 Tempo로 연결되는 link를 확인했지만 반대 방향도 가능합니다. Tempo에서 span을 펼치면 “Logs for this span” link가 제공됩니다.

![Tempo span log link](/images/docs_website/12-temo-span.png)

이 link는 해당 span과 연결된 특정 component(backend-service, Participant, Sequencer 등)의 log로 이동합니다.

서로 다른 correlation ID를 사용하면 분산 application의 변경 이력을 탐색할 수 있습니다. Participant Node 내 ACS에 Transaction이 commit되는 것을 확인했지만, PQS도 index하는 Transaction과 연관된 identifier를 기록합니다.

TransactionId와 traceId를 모두 사용해 create-license backend operation 및 그 이후 과정에 대한 이해를 넓힐 수 있습니다.

![log](/images/docs_website/13-logs.png)

PQS ingestion은 background process가 수행하는 별도의 operation입니다. 따라서 이 log의 traceId는 서로 다르지만, ingestion 중인 ledger data와 연관된 trace 및 Transaction identifier로 다시 연결됩니다. Tempo link를 따라가면 이를 확인할 수 있습니다.

![PQS ingestion trace](/images/docs_website/14-pqs-ingestion.png)

“export transaction” span에서 펼친 “references” section에는 관련 PQS process의 trace와, 특히 해당 Transaction을 만든 command 제출 trace로 연결되는 link가 포함되어 있습니다. 이 link는 해당 trace로 바로 이동하며, 여기서는 방금 출발한 trace와 동일합니다.

연결된 log, trace 및 span을 query하고 탐색하면 Canton Network Application과 관련된 여러 구성 요소를 훨씬 쉽게 이해할 수 있습니다. 내보낸 log와 trace만 탐색할 수 있고 포함되거나 첨부된 identifier만 query할 수 있다는 점을 기억하세요. 따라서 application의 logging을 보강하고 확장할 기회가 있는지 주기적으로 시간을 내어 살펴보기를 강력히 권장합니다.

마지막으로 바로 보이지는 않지만 log line 위에 pointer를 놓으면 해당 line의 log context를 보는 option이 나타납니다.

![Grafana log context link](/images/docs_website/15-log-line-hover.png)

그러면 해당 시간대 component log의 필터링되지 않은 전체 view가 관련 line을 강조한 상태로 window에 표시됩니다. Nginx log line의 경우 동일한 시간에 처리된 다른 traffic을 한 번의 click으로 볼 수 있습니다.

![Grafana log context view](/images/docs_website/16-log-context-view.png)

Grafana가 Tempo 및 Prometheus의 raw query에 대한 access를 제공한다는 점도 기억할 만합니다. 이를 직접 실험하며 observability stack을 통해 제공되는 통합 metric과 trace를 조사하는 방법을 찾아보는 것은 충분히 가치가 있습니다. Log 검사에는 [lnav](/appdev/quickstart/lnav)를 사용하세요.

![Tempo TraceQL](/images/docs_website/17-tempo-trace-ql.png)

[^5]: Canton을 다른 모든 layer-one blockchain과 구분하는 핵심 요소는 privacy를 제공한다는 점입니다. Canton은 의사 익명성이나 모호함을 통한 은닉 대신 알 권리를 강제하여 이를 구현합니다. Canton은 두 가지 privacy 보장을 제공합니다. 암호화된 형태라 하더라도 (sub-)transaction은 이를 통지받을 권리가 있는 Participant Node에만 전송되며, Participant Node는 통지받을 권리가 있는 모든 (sub-)transaction을 통지받습니다. Canton이 "권리"를 정의하는 방식과 기타 측면에 대한 자세한 내용은 [Daml ledger privacy model](/appdev/deep-dives/privacy-model)을 참조하세요.

[^6]: Distributed tracing은 분산 application을 효율적으로 debug하고 진단하는 데 필수적입니다. Trace ID와 Span ID는 기술적으로 별개의 identifier지만 밀접하게 연결되어 있습니다. 사용법이 익숙하지 않다면 OpenTelemetry의 유용한 입문 자료([https://opentelemetry.io/docs/concepts/signals/traces/](https://opentelemetry.io/docs/concepts/signals/traces/)), Grafana demo([https://grafana.com/docs/tempo/latest/introduction/](https://grafana.com/docs/tempo/latest/introduction/))를 확인하세요. 이 가이드의 뒷부분에서도 사용법을 설명합니다.

[^7]: Privacy를 지원하지 않는 다른 public blockchain의 “blockheight”에 해당합니다. Privacy에 따라 각 Participant Node가 global blockchain의 서로 다른 projection을 보게 되므로 서로 다른 Participant Node의 offset은 비교할 수 없습니다. 한 Participant Node가 확인한 ledger event에 대해 단순하고 단조 증가하며 total order를 제공하기 때문에 단일 Participant Node를 다룰 때 일반적으로 선호되는 ID입니다.

[^8]: Ledger Model에서의 역할에 따라 모든 Party는 (그리고 연관된 entity도) (sub-)transaction 또는 ledger event를 승인할 수 있어야 합니다. 자세한 내용은 [Daml ledger authorization model](/appdev/deep-dives/authorization)을 참조하세요.

[^9]: Logger가 structured log를 직접 내보내도록 구성할 수 없는 경우 일반적인 방식으로 log parser를 사용해 raw log file을 변환합니다. 이는 주로 OTEL Collector configuration에서 수행됩니다.

[^10]: 이는 Canton Network의 중요한 기능을 보여주는 예입니다. Participant Node는 관련 Daml Smart Contract와 Daml Ledger Model의 privacy semantics에 의해 해당 Transaction을 통지받도록 승인되었기 때문에 이 Transaction의 존재를 알 수 있습니다. Privacy는 contract data를 ciphertext로 가리기 때문에 보장되는 것이 아니라, 알 권리가 검증되지 않은 Participant에게 ledger model이 어떤 형태로든 Transaction을 전달하지 않도록 하기 때문에 보장됩니다.
