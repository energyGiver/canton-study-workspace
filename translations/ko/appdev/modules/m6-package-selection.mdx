여러 Package version이 Validator에 upload되면 Validator는 execute할 version을 결정하는 rule이 필요합니다. Package selection이 이를 결정합니다. V1과 V2 Package를 모두 사용할 수 있을 때 Daml runtime이 Template과 Choice를 resolve하는 방식을 govern합니다.

## How Version Resolution Works

Ledger의 모든 Contract는 이를 생성한 Package version과 연결됩니다. Contract를 fetch하거나 exercise할 때 runtime은 반드시 Contract를 생성한 version이 아니라 code에서 reference하는 Package version을 사용합니다.

Resolution은 다음 rule을 따릅니다.

- **Creating contracts** — Runtime은 code에서 reference하는 Package version을 사용합니다. Backend가 V2를 import하면 새 Contract는 V2로 생성됩니다.
- **Fetching contracts** — Runtime은 code에서 reference하는 version을 기준으로 Contract data를 evaluate합니다. SCU와 vetting rule이 fetch 성공 여부를 결정합니다([Upgrade Compatibility](/appdev/modules/m6-upgrade-compatibility) 참조).
- **Exercising choices** — Contract를 생성한 version이 아니라 code에서 reference하는 version의 Choice body가 execute됩니다. 즉 V2 Choice의 bug fix가 V1 Contract에 적용됩니다.

## Symbolic Package References

Backend에 특정 Package version을 hardcode하지 마세요. Ledger API query에서 symbolic Package reference를 사용합니다. 특정 Package ID를 지정하는 대신 name으로 Package를 reference합니다.

```text
#com-example-licensing:Main:License
```

이 설정은 Ledger API가 `Main.License` Template을 포함하는 모든 `com-example-licensing` Package version의 Contract를 match하도록 합니다. Backend는 각 version에 별도 query logic을 사용할 필요 없이 V1과 V2 Contract를 모두 받습니다.

Symbolic reference를 사용하지 않으면 새 Package version을 upload할 때마다 backend query filter를 update해야 하므로 seamless upgrade의 목적에 어긋납니다.

## Multi-Version Coexistence

V2 upload 후에도 V1과 V2 Package는 모두 Ledger에서 active 상태로 유지됩니다. 즉 다음이 가능합니다.

- V1로 생성된 Contract가 계속 존재하며 fetch, exercise, archive 가능
- Code가 reference하는 version에 따라 V1 또는 V2로 새 Contract 생성 가능
- Rollout period에 서로 다른 organization이 서로 다른 version을 동시에 사용 가능

Ledger는 V1 Contract를 V2로 자동 migrate하지 않습니다. V1 Contract는 archive될 때까지 V1 Contract로 유지됩니다. 새로 추가된 `Optional` field의 non-`None` value 같은 V2 data를 Contract에 추가해야 하면 V1 Contract를 archive하고 새 V2 Contract를 생성해야 합니다. Normal business operation 또는 explicit upgrade Choice를 통해 수행할 수 있습니다.

## Package Vetting

{/* COPIED_START source="docs-website:manual/build/3.5/sdlc-howtos/applications/upgrade/arch-considerations-upgrading.rst" hash="package-vetting" */}

Package vetting을 통해 다른 Participant Node는 해당 Participant의 Party가 참여할 수 있는 workflow를 결정할 수 있습니다. Package는 vet되기 전까지 사용할 수 없으므로 deployment process에 추가 verification step을 제공합니다. 기본적으로 Daml Package를 upload하면 Participant Node가 이를 자동으로 vetted로 mark하고 Synchronizer에 vetting status를 publish합니다.

Package는 unvet할 수도 있습니다. 예를 들어 V2를 upload/vet한 후 V1을 unvet하면 Participant Node가 더 이상 V1 workflow에 참여할 수 없다는 signal이 되어 upgrade process가 finalize됩니다.

잠재적인 issue를 방지하려면 Participant Node가 V1을 unvet하기 전에 모든 V1 Contract를 완전히 upgrade해야 합니다.
V2가 vetted 상태이면 V1을 unvet했더라도 V1 Template로 생성된 Contract를 V2로 사용/upgrade할 수 있습니다.

## Cross-Version Fetch Behavior

Runtime은 code에서 reference하는 Package version을 사용합니다. 새 version에 대한 자동 "preference"는 없습니다. 사용되는 version은 code가 compile된 Package에 따라 달라집니다. Cross-version behavior는 다음 rule을 따릅니다.

- V2 code로 `License`를 fetch하고 Contract가 V1로 생성된 경우 runtime은 V2 logic을 적용합니다(새 `Optional` field를 `None`으로 채움).
- V1 code로 `License`를 fetch하고 Contract가 새 field value가 `None`인 V2로 생성된 경우 runtime은 V1 logic을 적용합니다(알 수 없는 field 무시).
- V1 code로 `License`를 fetch하고 Contract가 새 field에 non-`None` value가 있는 V2로 생성된 경우 data loss를 막기 위해 fetch가 실패합니다.

Version이 incompatible하면 system은 data를 silently drop하지 않고 안전하게 실패합니다.
