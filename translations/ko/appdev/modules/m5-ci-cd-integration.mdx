Canton application용 CI/CD pipeline은 다른 software project와 같은 build, package, test, deploy 구조를 따릅니다. Canton에 특화된 부분은 Daml compile, Script test 실행 및 DAR artifact 관리에 사용하는 `dpm` command입니다.

## Pipeline 구조

일반적인 pipeline에는 네 단계가 있습니다.

1. **Build**: Daml code를 compile하고 client binding 생성
2. **Package**: 배포 가능한 artifact(DAR, container image) 생성
3. **Test**: Daml Script unit test 및 backend integration test 실행
4. **Deploy**: DAR를 upload하고 off-ledger service를 target environment에 배포

## Build 단계

Build 단계에서는 Daml package를 compile하고 backend와 frontend용 code binding을 생성합니다.

<DamlDocsAppdevModulesM5CiCdIntegrationL21 />

Multi-package project에서는 root directory의 `dpm build`가 모든 package를 dependency 순서로 build하며, 이 동작에는 `multi-package.yaml`이 있어야 합니다.

### Build caching

DAR compile은 deterministic합니다. 같은 source code와 SDK version은 같은 DAR를 생성합니다. CI 실행 사이에 `.daml/dist/` directory를 cache하여 Daml source가 변경되지 않았으면 recompile을 건너뜁니다. 대부분 CI system(GitHub Actions, GitLab CI, Jenkins)은 file hash를 기준으로 한 caching을 지원합니다.

## Test 단계

### Daml Script test

<DamlDocsAppdevModulesM5CiCdIntegrationL45 />

Test package의 모든 `Script ()` declaration을 Sandbox에서 실행합니다. Assertion이 하나라도 실패하면 `dpm test`가 non-zero code로 종료되고 pipeline이 실패합니다.

별도의 test package가 있는 project에서는 각 test package directory에서 `dpm test`를 실행하거나 test package를 포함하는 `multi-package.yaml`을 사용합니다.

### Backend integration test

Daml test가 통과하면 sandbox를 대상으로 backend integration test를 실행합니다.

<DamlDocsAppdevModulesM5CiCdIntegrationL57 />

완전한 Multi-Validator 설정이 필요한 test에서는 sandbox 대신 Docker Compose로 [LocalNet](/appdev/modules/m5-localnet-development)을 시작합니다. 더 무겁지만 cross-Validator scenario를 다룹니다.

## Package 단계

### DAR artifact

`.dar` file은 `dpm build`가 생성하는 기본 Daml artifact입니다. Version metadata와 함께 CI artifact repository(Artifactory, Nexus, S3 또는 CI system의 built-in artifact storage)에 저장하세요.

Version을 포함하는 naming convention을 사용하면 추적이 쉬워집니다.

```text
your-app-1.0.0.dar
your-app-1.1.0.dar
```

DAR의 version은 `version` field에서 가져오며 이 field는 `daml.yaml`에 있습니다. Environment variable interpolation을 사용하여 CI pipeline에서 설정합니다.

<DamlDocsAppdevModulesM5CiCdIntegrationL89 />

### Container image

Backend와 frontend를 containerize했다면 이 단계에서 image를 build하고 tag합니다. DAR를 embedded artifact로 포함하거나 deployment 시 mount합니다.

## Deploy 단계

각 environment로의 deployment는 Validator에 DAR를 upload하는 것과 off-ledger service(backend, frontend, PQS)를 배포하는 두 부분으로 구성됩니다.

### DAR upload

Participant HTTP Ledger API를 통해 target Validator에 DAR를 upload합니다.

<DamlDocsAppdevModulesM5CiCdIntegrationL106 />

Upload를 verify합니다.

<DamlDocsAppdevModulesM5CiCdIntegrationL115 />

### Environment promotion

CI system의 environment 또는 stage abstraction을 사용하여 promotion에 gate를 적용합니다. 일반적인 pattern은 다음과 같습니다.

- `main`으로 push하면 DevNet에 자동 배포
- Manual approval gate로 DevNet에서 TestNet으로 promotion
- 또 다른 manual gate로 TestNet에서 MainNet으로 promotion

각 promotion은 서로 다른 environment configuration을 사용하여 같은 deployment 단계를 실행합니다([Environment Configuration](/appdev/modules/m5-environment-configuration) 참조).

## CI 상태 Monitoring

{/* COPIED_START source="docs-website:manual/build/3.5/sdlc-howtos/sdlc-best-practices.rst" hash="ci-monitoring" */}

CI 실행에서 log를 capture하고 CI failure debugging에 사용하는 등 개발과 test 중 log를 정기적으로 검토하세요. Metric에 alert를 설정하여 test와 개발 중 application 상태를 monitoring합니다. 이렇게 하면 장기 실행 test instance에 통합하고 운영에서 재사용할 수 있습니다. 개발 중 잘 조정된 alert를 운영에서 재사용하여 system health issue를 감지할 수 있습니다.
