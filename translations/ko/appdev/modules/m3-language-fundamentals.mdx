## Haskell과의 연관성

이전 Daml introduction chapter에서는 주로 Template의 구조와 Daml Ledger Model과의 관계를 다뤘습니다. Choice의 `do` block 안에서 일어나는 logic은 비교적 단순하게 유지했습니다. 이 chapter에서는 해당 `do` block 안에 logic을 작성할 수 있게 하는 Daml expression language를 더 깊이 살펴봅니다. 다만 여기서는 기초만 다룹니다. Daml language의 많은 부분은 [Haskell](https://www.haskell.org)에서 가져왔습니다. 더 깊이 배우거나 language의 특정 측면을 알아보려면 Haskell 표준 문헌을 참조할 수 있습니다. 다음 자료를 권장합니다.

- [Finding Success and Failure in Haskell (Julie Moronuki, Chris Martin)](https://joyofhaskell.com/)
- [Haskell Programming from first principles (Christopher Allen, Julie Moronuki)](http://haskellbook.com/)
- [Learn You a Haskell for Great Good! (Miran Lipovača)](http://learnyouahaskell.com/)
- [Programming in Haskell (Graham Hutton)](http://www.cs.nott.ac.uk/~pszgmh/pih.html)
- [Real World Haskell (Bryan O'Sullivan, Don Stewart, John Goerzen)](http://book.realworldhaskell.org/)

Daml과 Haskell을 비교할 때 다음 사항에 유의할 필요가 있습니다.

- Haskell은 lazy language이므로 "무한 list의 첫 element를 가져온다"는 뜻의 `head [1..]` 같은 표현을 작성할 수 있습니다. 반면 Daml은 strict합니다. Expression을 완전히 evaluate하므로 무한 data structure를 다룰 수 없습니다.
- Daml에는 Record를 위한 `with` syntax와 Record field access를 위한 dot syntax가 있으며 Haskell에는 둘 다 없습니다. 다만 Daml은 Haskell의 curly brace Record notation을 지원합니다.
- Daml은 여러 Haskell compiler extension을 default로 활성화합니다.
- Daml은 Haskell type system의 모든 feature를 지원하지 않습니다. 예를 들어 existential type이나 GADT가 없습니다.
- Action은 Haskell에서 Monad라고 부릅니다.

## Function

`data`에서는 Daml type system의 한 축인 Data type을 배웠습니다. 이제 다른 축인 Function type을 알아봅니다. Daml의 Function type은 "maps to"로 읽을 수 있는 `->`를 통해 식별할 수 있습니다.

예를 들어 function signature `Int -> Int`는 integer를 다른 integer로 mapping합니다. 이러한 function은 많으며 그중 하나는 다음과 같습니다.

2.  Constraint `Additive a`가 있는 type parameter `a`가 있습니다.

### Function application

오른쪽 부분 `a -> a -> a`부터 살펴보겠습니다. `->`는 right associative이므로 `a -> a -> a`는 `a -> (a -> a)`와 같습니다. `->`를 "maps to"로 읽으면 "`a`는 `a`를 `a`로 mapping하는 function으로 mapping된다"는 뜻입니다.

실제로 그렇게 작동합니다. `add`를 *partially applying*하여 다른 version의 `increment`를 정의할 수 있습니다.

<DamlAppdevModulesM3LanguageFundamentalsL84 />

IDE에서 시도하면 compiler가 다시 `Int -> Int` type을 infer하는 것을 볼 수 있습니다. Literal `1 : Int` 때문에 가능합니다.

따라서 function `f : a -> b -> c -> d`와 값 `valA : a`가 있으면 `f valA : b -> c -> d`를 얻습니다. 즉 function을 argument별로 apply할 수 있습니다. `valB : b`도 있다면 `f valA valB : c -> d`를 얻습니다. 이는 function *application*이 left associative임을 보여줍니다. `f valA valB == (f valA) valB`입니다.

### Infix function

`add`는 분명 `+`의 alias일 뿐이지만 `+`는 무엇일까요? `+`도 function입니다. Symbol로 시작한다는 점만 특별합니다. Symbol로 시작하는 function은 default로 *infix*이므로 두 argument 사이에 작성할 수 있습니다. 그래서 `+ 1 2` 대신 `1 + 2`를 작성할 수 있습니다. Normal function과 infix function을 변환하는 rule은 간단합니다. Infix function을 parenthesis로 감싸 normal function, 즉 *prefix*로 사용하고, normal function을 backtick으로 감싸 infix로 만듭니다.

#### Associativity 및 precedence

여러 infix operator를 다룰 때 precedence는 Daml compiler가 expression을 parse하는 방식을 결정합니다. 예를 들어 expression `x + y * z`에서 `\*`의 precedence가 `+`보다 높으므로 `(x + y) * z`가 아니라 `x + (y * z)`로 parse됩니다. Precedence가 같은 infix operator를 다룰 때는 associativity가 Daml compiler의 parse 방식을 결정합니다. 예를 들어 `+`와 `-`가 left-associative이므로 expression `x + y - z`는 `x + (y - z)`가 아니라 `(x + y) - z`로 parse됩니다. Built-in operator에는 미리 정의되어 있고 user-defined operator에는 user가 정의해야 합니다. 자세한 내용은 [Fixity, Associativity 및 Precedence에 관한 Daml reference](/appdev/reference/daml-language-reference#fixity-associativity-and-precedence)를 참조하세요.

### Type constraint

`add` signature의 `Additive a =>` 부분은 type parameter `a`에 대한 type constraint입니다. 여기서 `Additive`는 typeclass입니다. 앞에서 `Eq`, `Show` 같은 typeclass를 살펴봤습니다. `Additive` typeclass는 어떤 값을 더할 수 있음을, 즉 function `(+) : a -> a -> a`가 있음을 나타냅니다. 따라서 `add`의 전체 signature는 "`a`가 `Additive` typeclass instance를 가지면 `a`는 `a`를 `a`로 mapping하는 function으로 mapping된다"고 읽습니다.

Daml의 typeclass는 다른 language의 interface와 비슷합니다. `+` function으로 두 값을 더하려면 해당 값이 `Additive` interface, 즉 typeclass를 "노출"하거나 그 instance를 가져야 합니다.

Interface와 달리 typeclass는 여러 type parameter를 가질 수 있습니다. 여러 constraint를 동시에 사용하는 좋은 예는 `exercise` function의 signature입니다.

<DamlAppdevModulesM3LanguageFundamentalsL126 />

이를 문장으로 바꾸면 다음과 같습니다. `t`가 Template type이고 `t`에 return type `r`인 Choice `c`가 있으면 `exercise` function은 type `t`인 Contract의 `ContractId`를 type `c`의 Choice argument를 받아 type `r`을 결과로 내는 `Update`를 반환하는 function으로 mapping합니다.

상당히 긴 설명이며 typeclass `Choice`가 parameter `t`, `c`, `r`에 어떤 *의미*를 부여하는지 알아야 합니다. 하지만 많은 경우 context나 typeclass 및 variable name으로 명확히 알 수 있습니다.

한 글자를 사용하는 방식은 일반적이지만 필수는 아닙니다. Code가 조금 길어지더라도 type parameter name을 풀어 쓰면 위 내용을 좀 더 명확하게 만들 수 있습니다.

### 어디서나 사용하는 function

이미 짐작했겠지만 Daml에서 값을 넣을 수 있는 곳이면 어디든 function도 넣을 수 있습니다. Data type 안에도 가능합니다.

<DamlAppdevModulesM3LanguageFundamentalsL205 />

Function은 `let` clause 같은 곳에서 local하게 정의하는 편이 더 적합할 때가 많습니다. 좋은 예는 `dependencies`의 Model에서 `Trade_Settle` Choice 내부에 local로 정의한 `validate`와 `transfer` function입니다.

<DamlAppdevModulesM3LanguageFundamentalsL212 />

여기서는 context를 바탕으로 function signature가 infer됩니다. 자세히 살펴보거나 IDE에서 function 위에 pointer를 올리면 다음 signature를 확인할 수 있습니다.

```bash
validate : (HasFetch r, Eq r, HasField "observers" r a) => (r, ContractId r) -> Update ()
```

<Note>
Function은 serializable하지 않으므로 Template argument 내부, Choice input 또는 Choice output으로 사용할 수 없습니다. 또한 data type에서 일반적으로 필요한 `Eq` 또는 `Show` typeclass instance도 없습니다.
</Note>

`mapA`와 `mapA_` function은 Asset 및 approval list를 loop하며 각 element에 `validate`와 `transfer` function을 apply하고 그 과정에서 결과 `Update` action을 수행합니다. 아래 `loops`에서 더 자세히 살펴봅니다.

### Lambda

Daml은 "lambda"라고 하는 inline function을 지원합니다. `(\x y z -> ...)` syntax로 정의합니다. 예를 들어 `increment`의 lambda version은 `(\n -> n + 1)`입니다.

## Control flow

이 section에서는 branch와 loop를 다루고 procedural code를 functional code로 변환하는 일반적인 pattern을 몇 가지 살펴봅니다.

### Branch

`compose`까지 소개한 실질적인 control flow는 강력한 branching tool인 `case`뿐이었습니다.

#### If-else expression

### Loop

Branching 외에 가장 일반적인 control flow 형태는 looping입니다. Looping은 보통 state를 반복적으로 수정하는 데 사용합니다. 이 section에서는 procedural 방식을 설명하기 위해 JavaScript를 사용합니다.

``` JavaScript
function sum(intArr) {
  var result = 0;
  intArr.forEach (i => {
    result += i;
  });
  return result;
}
```

더 일반적인 loop는 다음과 같습니다.

``` JavaScript
function whileF(init, cont, step, finalize) {
  var state = init();
  while (cont(state)) {
    state = step(state);
  }
  return finalize(state);
}
```

두 경우 모두 state가 mutate됩니다. 전자는 `result`, 후자는 `state`입니다. Daml의 값은 immutable이므로 다르게 작동해야 합니다. Daml에서는 fold와 recursion을 사용합니다.

#### Fold

Fold는 procedural language의 `for` 및 `forEach` loop처럼 명시적인 iterator를 사용한 looping에 대응합니다. 위의 `sum` function처럼 가장 일반적인 iterator는 list입니다. 이러한 경우를 위해 Daml에는 `foldl` function이 있습니다. `l`은 "left"를 뜻하며 list를 왼쪽부터 처리한다는 의미입니다. 오른쪽부터 처리하는 대응 function `foldr`도 있습니다.

<DamlAppdevModulesM3LanguageFundamentalsL452 />

Type parameter에 의미 있는 이름을 부여해 보겠습니다. `b`는 state이고 `a`는 item입니다. `foldl`의 첫 번째 argument는 state와 item을 받아 새 state를 반환하는 function입니다. 이는 `forEach`의 내부 block에 해당합니다. 그다음 initial state인 state와 iterator인 item list를 받습니다. 결과도 state입니다. 이러한 대응을 생각하면 위의 `sum` function을 거의 즉시 Daml로 변환할 수 있습니다.

<DamlAppdevModulesM3LanguageFundamentalsL458 />

더 자세히 쓰려면 `(+)`를 lambda `(\result i -> result + i)`로 바꿀 수 있으며, 그러면 JavaScript의 `result += i`와의 대응이 더 명확해집니다.

명시적인 iterator가 있는 거의 모든 loop를 fold로 변환할 수 있지만 `for` loop를 변환할 때는 performance에 조금 주의해야 합니다.

``` JavaScript
function sumArrs(arr1, arr2) {
  var l = min (arr1.length, arr2.length);
  var result = new int[l];
  for(var i = 0; i < l; i++) {
    result[i] = arr1[i] + arr2[i];
  }
  return result;
}
```

값 `[0..(l-1)]`을 포함하는 array가 있으면 `for`를 `forEach`로 쉽게 변환할 수 있습니다. Daml에서는 *range*를 사용하여 그렇게 합니다. `[0..(l-1)]`은 예상하는 list를 반환하는 `enumFromTo 0 (l-1)`의 shorthand입니다.

Daml에는 list의 element를 반환하는 operator `(!!) : [a] -> Int -> a`도 있습니다. 따라서 `sumArrs`를 다음과 같이 작성하고 싶을 수 있습니다.

<DamlAppdevModulesM3LanguageFundamentalsL481 />

하지만 이는 좋은 approach가 아닙니다. Daml의 list는 linked list이므로 이러한 iteration에서 `(!!)`를 통한 access가 너무 느립니다. Daml에서는 `i`를 완전히 없애고 먼저 `zip` function으로 list를 merge한 다음 "zip"된 list를 iterate하는 편이 낫습니다.

<DamlAppdevModulesM3LanguageFundamentalsL491 />

`zip : [a] -> [b] -> [(a, b)]`은 두 list를 받아 단일 list로 merge합니다. 새 list의 첫 element는 두 input list의 첫 element를 포함하는 2-tuple이며 이후도 같은 방식입니다. 더 긴 list에 남는 element는 제거하므로 `min` logic이 필요 없습니다.

#### Map

실제로 `foldl`에 전달되는 lambda는 zip된 input list의 단일 element에만 작용하려 하지만 전체 state의 concatenation도 관리해야 합니다. 각 element에 별도로 작용하는 pattern은 매우 일반적이므로 전용 function `map : (a -> b) -> [a] -> [b]`이 있습니다. 이를 사용하면 `sumArr`를 다음과 같이 다시 작성할 수 있습니다.

<DamlAppdevModulesM3LanguageFundamentalsL501 />

일반적으로 결과와 input의 shape가 같고 iteration 간에 state를 전달할 필요가 없으면 `map`을 사용합니다. 어떤 방식으로든 state를 accumulate해야 한다면 fold를 사용합니다.

#### Recursion

명시적인 iterator가 없으면 recursion을 사용할 수 있습니다. 예를 들어 list를 뒤집는 function을 작성해 보겠습니다. `(!!)`를 피하려 하므로 여기에는 적절한 iterator가 없습니다. 대신 recursion을 사용합니다.

<DamlAppdevModulesM3LanguageFundamentalsL511 />

`reverseWorker`를 `reverse` 내부의 local definition으로 만들고 싶을 수 있지만 Daml은 top-level function에서만 recursion을 지원하므로 recursive 부분인 `recurseWorker`는 별도의 top-level function이어야 합니다.

#### Action context의 fold 및 map

위의 fold와 `map` function은 앞에서 소개한 의미에서 pure합니다. Item을 map하거나 처리하는 function에는 side effect가 없습니다. Multi-package Model을 살펴봤다면 `Action` 안에서 비슷한 역할을 하는 것으로 보이는 `mapA`, `mapA_`, `forA`를 발견했을 것입니다. 좋은 예는 `testMultiTrade` script의 `mapA` call입니다.

<DamlAppdevModulesM3LanguageFundamentalsL524 />

여기에는 relationship list, 즉 type `[Relationship]`과 function `setupRelationship : Relationship -> Script (ContractId AssetHolder)`이 있습니다. 해당 relationship의 `AssetHolder` Contract, 즉 type `[ContractId AssetHolder]`가 필요합니다. Map function을 사용하면 거의 얻을 수 있지만 `map setupRelationship rels`의 type은 `[Update (ContractId AssetHolder)]`입니다. 이는 각각 `ContractId AssetHolder`를 산출하는 `Update` action의 list입니다. 필요한 것은 `[ContractId AssetHolder]`를 산출하는 `Update` action입니다. 목적에 비해 list와 `Update`가 잘못된 순서로 nested되어 있습니다.

## Native type

이미 몇 가지 native Daml type을 살펴봤습니다. `contracts`의 `Party`, `daml-scripts`의 `Text`와 `ContractId`입니다. 다음은 이러한 native type과 그 밖의 type입니다.

- `Party`: Contract에 서명하고 Transaction을 제출하는 방식으로 Ledger에서 action을 수행할 수 있는 entity의 identity를 저장합니다. 일반적으로 `Party`는 opaque합니다.
- `Text`: `"Alice"` 같은 Unicode character string을 저장합니다.
- `ContractId a`: Type `a`인 Contract의 reference를 저장합니다.
- `Int`: Signed 64-bit integer를 저장합니다. 예: `-123`
- `Decimal`: Decimal point 앞 28자리, 뒤 10자리의 fixed-point number를 저장합니다. 예: `0.0000000001` 또는 `-9999999999999999999999999999.9999999999`
- `Bool`: `True` 또는 `False`를 저장합니다.
- `Date`: Date를 저장합니다.
- `Time`: Absolute UTC time을 저장합니다.
- `RelTime`: 시간 차이를 저장합니다.

간단한 Script지만 유의할 사항이 많습니다.

- 위쪽의 `import` statement는 Daml Standard Library에서 Package 두 개를 import합니다. 여기서 사용하는 모든 date/time 관련 function과 Daml Script에서 사용하는 function이 들어 있습니다. Package, import, Standard Library는 뒤에서 자세히 설명합니다.

  `script do` block은 `submit`이나 `allocateParty` 같은 Script action을 기대하기 때문입니다. `123` 같은 integer는 action이 아니라 Ledger 없이 evaluate할 수 있는 pure expression입니다. `let`이 variable declaration을 action으로 바꾼다고 생각할 수 있습니다.

- 대부분의 variable에는 type을 나타내는 annotation이 없습니다.

  Daml은 type *inference*에 매우 뛰어나기 때문입니다. Compiler는 `123`이 `Int`임을 알므로 `my_int = 123`을 declare하면 `my_int`도 `Int`라고 infer할 수 있습니다. 따라서 type annotation `my_int : Int = 123`을 작성하지 않아도 됩니다.

  하지만 type이 ambiguous하여 compiler가 infer할 수 없으면 type annotation을 추가해야 합니다. 모든 `Numeric n`일 수 있는 `0.001`이 이러한 경우입니다. 여기서는 `Numeric 10`의 synonym인 `0.001 : Decimal`을 지정합니다. Readability를 위해 언제든 type annotation을 추가할 수 있습니다.

- `assert` function은 boolean 값을 받아 `True`이면 성공하고 `False`이면 실패하는 action입니다.

  Script 어딘가에 `assert False`를 넣고 Script 결과를 확인해 보세요.

## Type 조합

위의 `CashBalance`에는 정보가 많으므로 data에 더 많은 구조를 부여하면 좋습니다. 다행히 Daml type system은 이러한 native type을 훨씬 표현력 있는 structure로 조합하는 여러 방법을 제공합니다.

### Tuple

일반적인 작업 중 하나는 값을 generic 방식으로 group화하는 것입니다. 예를 들어 `Text` key와 `Int` 값의 key/value pair를 생각해 보겠습니다. Daml에서는 type `(Text, Int)`인 2-tuple을 사용할 수 있습니다. 3차원 coordinate를 표현하려면 3-tuple `(Decimal, Decimal, Decimal)`로 `Decimal` 값 세 개를 group화할 수 있습니다.

<DamlAppdevModulesM3LanguageFundamentalsL506 />

다음을 사용하여 tuple의 data에 access할 수 있습니다.

- Function `fst`, `snd`, `fst3`, `snd3`, `thd3`
- Field name `_1`, `_2`, `_3` 등을 사용하는 dot syntax

Daml은 최대 20개 element의 tuple을 지원하지만 `fst` 같은 accessor function은 2-tuple과 3-tuple에만 포함됩니다.

### List

Daml의 list는 list 안에 있는 값의 type을 정의하는 type parameter 하나를 받습니다. 따라서 integer list `[Int]` 또는 string list `[Text]`는 가능하지만 integer와 string을 섞은 list는 불가능합니다.

Daml은 statically/strongly typed language이기 때문입니다. List에서 element를 가져올 때 compiler는 element의 type을 알아야 합니다.

아래 Script는 integer list 몇 개를 instantiate하고 가장 중요한 list function을 보여줍니다.

<DamlAppdevModulesM3LanguageFundamentalsL539 />

`empty : [Int] = []`의 type annotation에 유의하세요. `[]`가 ambiguous하므로 필요합니다. Integer list일 수도 string list일 수도 있지만 compiler는 어느 쪽인지 알아야 합니다.

### Record

Record는 이름 있는 field를 가진 이름 있는 tuple이라고 생각할 수 있습니다. `data` keyword로 declare합니다. `data T = C with`에서 `T`는 type name이고 `C`는 data constructor입니다. 실제로는 type과 data constructor에 항상 같은 이름을 사용하는 것이 좋습니다.

<DamlAppdevModulesM3LanguageFundamentalsL572 />

Record declaration syntax가 Template declaration syntax와 매우 비슷하다는 점을 알 수 있습니다. Template은 실제로 특별한 Record이므로 우연이 아닙니다. `template Token with`를 작성하면 background에서 일어나는 일 중 하나는 이것이 `data Token = Token with`가 되는 것입니다.

위의 `assert` statement에서는 항상 built-in type의 값을 비교했습니다. Script에 `assert (my_record == my_record)`를 작성하면 `No instance for (Eq MyRecord) arising from a use of ‘==’` error message에 놀랄 수 있습니다. Daml의 equality는 항상 value equality이며 아직 `MyRecord` 값의 value equality를 확인하는 function을 작성하지 않았습니다. 하지만 이 명백한 function을 직접 구현할 필요는 없습니다. `deriving (Eq)`를 사용하면 compiler가 대신 처리합니다.

<DamlAppdevModulesM3LanguageFundamentalsL633 />

`Eq`는 *typeclass*입니다. Typeclass는 다른 language의 interface와 비슷하다고 생각할 수 있습니다. 여러 type에서 작동하는 function set, 예를 들어 `Eq`의 `==`와 `/=`를 정의하고 적용 가능한 각 type에 구체적인 implementation을 제공하는 mechanism입니다.

Compiler가 자동으로 derive할 수 있는 다른 typeclass도 있습니다. 대표적으로 많은 language의 `toString`에 해당하는 function `show`에 access하게 하는 `Show`, 그리고 comparison operator `<`, `>`, `<=`, `>=`에 access하게 하는 `Ord`가 있습니다.

`deriving (Eq, Show)`를 사용하여 항상 `Eq`와 `Show`를 derive하는 것이 좋습니다. `template T with`로 생성한 Record type은 이를 자동으로 수행하며 native type에는 적절한 typeclass instance가 있습니다. 예를 들어 `Int`는 `Eq`, `Show`, `Ord`를 derive합니다. 또 다른 예로 `ContractId a`는 `Eq`와 `Show`를 derive합니다.

Record를 사용하면 `CashBalance` data에 구조를 더 부여할 수 있습니다.

<DamlAppdevModulesM3LanguageFundamentalsL670 />

결과 Script view를 보면 여전히 table 하나가 생성됩니다. Record는 dot notation을 사용하는 column으로 expand됩니다.

### Variant 및 pattern matching

보유 중인 현금도 추적하려 한다고 가정합니다. 보유 현금에는 bank가 없지만 `bank`를 비워 둘 수는 없습니다. Daml에는 `null`에 해당하는 것이 없습니다. Variant는 현금이 보유 중이거나 bank에 있을 수 있음을 표현합니다.

<DamlAppdevModulesM3LanguageFundamentalsL727 />

`Location` declaration은 "*Location은* `InHand` *값을 가지거나* `a` *가 Account type인* `InAccount a` *값을 가진다*"고 읽습니다. 이는 `CashBalance`와 연결된 `Account`가 있을 수도 없을 수도 있음을 명시적으로 나타내고 두 case에 의미 있는 이름을 부여합니다.

다른 option은 built-in `Optional` type을 사용하는 것입니다. Type `Optional a`의 `None` 값은 Daml에서 `null` 값에 가장 가깝습니다.

<DamlAppdevModulesM3LanguageFundamentalsL793 />

어떤 data constructor도 parameter를 받지 않는 Variant type을 enum이라고 합니다.

<DamlAppdevModulesM3LanguageFundamentalsL802 />

Variant data에 access하려면 가능한 여러 case를 구분해야 합니다. 예를 들어 `Location`이 `InHand`이면 account number가 없을 수 있으므로 더 이상 account number에 직접 access할 수 없습니다.

이를 위해 *pattern matching*을 사용하여 error를 throw하거나 모든 case에 compatible한 type을 반환할 수 있습니다.

## Data 조작

이제 Ledger에 write하려는 data를 표현하는 풍부한 type을 build하는 데 필요한 모든 요소를 갖추었고 새 값을 생성하고 값에서 field를 읽는 방법도 살펴봤습니다. 그렇다면 생성한 값을 어떻게 조작할까요?

Daml의 모든 data는 immutable이므로 생성된 값은 변경되지 않습니다. 값을 변경하는 대신 이전 값을 바탕으로 일부 변경을 적용한 새 값을 생성합니다.

<DamlAppdevModulesM3LanguageFundamentalsL878 />

`changed_record`와 `better_changed_record`는 각각 `my_int` field가 변경된 `eq_record` copy입니다. `better_changed_record`는 Record field를 변경하는 권장 방식을 보여줍니다. Syntax는 새 Record를 만드는 방식과 거의 같지만 Record name을 이전 값으로 바꿉니다. `EqRecord with` 대신 `eq_record with`를 사용합니다. 이제 `with` block은 `EqRecord`의 모든 field에 값을 줄 필요가 없습니다. 누락된 field는 `eq_record`에서 가져옵니다.

Script 전체에서 `eq_record`는 변경되지 않습니다. Expression `"Zero" :: eq_record.my_list`는 list를 in-place로 변경하지 않고 `eq_record.my_list`의 시작 부분에 element 하나가 추가된 새 list를 생성합니다.

## Contract 조작

Daml type system을 사용하면 Daml Contract 안에 structured data를 저장할 수 있습니다. Record와 다른 data structure처럼 Contract도 immutable합니다. 생성하거나 archive할 수만 있습니다. Contract를 변경해야 한다면 원래 Contract를 archive하고 update된 data로 새 Contract를 생성해야 합니다.

<DamlAppdevModulesM3LanguageFundamentalsL918 />

위 Script는 `archiveCmd`와 `createCmd`를 사용하여 같은 Transaction에서 type `Account`인 Contract를 수정합니다. `newAccountCid =/= accountCid`가 보여주듯 이 process는 새 Contract와 구별되는 새 Contract ID를 생성합니다.
