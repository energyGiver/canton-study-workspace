Canton application은 evolve합니다. Template에 새 field가 추가되고 Choice behavior가 변경되며 완전히 새로운 workflow가 도입됩니다. Smart Contract Upgrade(SCU)는 기존 Contract를 break하거나 organization 간 coordinated downtime을 요구하지 않고 이를 가능하게 하는 mechanism입니다. 참고: SCU에는 따라야 할 rule이 있습니다.

## Why Upgrades Are Different on Canton

Traditional database에서는 migration script를 실행하면 schema가 변경됩니다. Canton에서는 Contract가 immutable하며 여러 organization의 Validator에 분산됩니다. Template structure를 변경하면 해당 Template을 사용하는 Party를 hosting하는 모든 Validator가 변경을 알아야 합니다.

여기에는 모든 organization에 동시에 upgrade를 강제할 수 없다는 challenge가 있습니다. SCU는 controlled cross-version interaction rule과 함께 여러 Package version이 Ledger에 공존하도록 하여 이를 해결합니다.

## The Upgrade Model

{/* COPIED_START source="docs-website:manual/build/3.5/sdlc-howtos/applications/upgrade/arch-considerations-upgrading.rst" hash="recommended-approach" */}

권장 approach는 asynchronous rollout과 synchronous switch-over를 결합합니다.

**Asynchronous rollout:**

1. App Provider가 V2 app component를 구현하고 test합니다.
2. App Provider가 V2 component를 App User에게 제공합니다.
3. App Provider와 User가 upgraded backend/frontend를 asynchronously rollout하고 upgraded DAR Package를 audit한 다음 Package를 vet합니다.

Frontend와 backend는 V1/V2 workflow를 모두 지원해야 하므로 App Provider와 App User가 각자 schedule에 따라 독립적으로 update를 deploy할 수 있습니다. 모든 User가 V2 workflow로 전환할 때까지 mixed-version deployment가 예상됩니다.

**Synchronous switch-over:**

1. App Provider가 App User의 upgrade 및 V1 decommission 완료 target date를 publish합니다.
2. Target upgrade date 직전에 App Provider와 User가 Validator에 V2 Package(DAR) file을 upload하도록 coordinate합니다.
3. 미리 정한 time에 모두 새로 upload한 Package를 vet하여 해당 version을 active하게 합니다.

{/* COPIED_END */}

## Package Versioning

모든 Daml Package에는 `daml.yaml`에 정의된 name/version이 있습니다. 같은 name과 더 높은 version number를 가진 새 Package version을 upload하면 두 version이 Ledger에 동시에 존재합니다. 기존 Contract는 생성한 version과 계속 연결되지만 Ledger는 SCU compatibility rule에 따라 newer version을 기준으로 resolve할 수 있습니다.

이 multi-version coexistence가 zero-downtime upgrade의 기반입니다. 새 version이 active하기 전에 old Contract를 migrate할 필요가 없습니다. Compatibility가 허용하면 newer version code를 통해 read/exercise할 수 있습니다.

## When to Use Upgrades vs. New Templates

모든 변경에 upgrade mechanism이 필요한 것은 아닙니다. Trade-off를 고려하세요.

**Use SCU when:**
- 기존 Template에 optional field 추가
- 기존 Template에 새 Choice 추가
- Migration 없이 기존 Contract가 새 code와 작동해야 함
- Zero-downtime deployment가 필요함

**Use new templates when:**
- 변경이 근본적으로 incompatible함(field 제거, type 변경)
- 새 workflow가 old workflow와 logically distinct함
- Old/new behavior를 명확히 분리하려 함

## Key Challenges

{/* COPIED_START source="docs-website:manual/build/3.5/sdlc-howtos/applications/upgrade/arch-considerations-upgrading.rst" hash="challenges" */}

- **Asynchronous rollouts** — App Provider와 App User는 흔히 동시에 upgrade할 수 없습니다. Upgrade는 independent deployment schedule을 지원해야 합니다.
- **Mixed-version deployments** — Asynchronous rollout으로 인해 application은 일시적으로 organization 간 mixed-version deployment를 지원해야 합니다. Backend와 frontend는 V1/V2 DAR workflow 모두와 compatible한 상태를 유지해야 합니다.
- **Zero-downtime upgrades** — 일부 workflow는 중단 없이 24/7 진행되어야 할 수 있습니다. SCU와 asynchronous rollout approach는 upgrade process 중 workflow가 중단 없이 계속되도록 합니다.
