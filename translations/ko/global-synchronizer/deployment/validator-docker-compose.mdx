이 section에서는 [Docker Compose](https://docs.docker.com/compose/)를 사용하여 VM 또는 local machine에 standalone validator node를 배포하는 방법을 설명합니다. Deployment는 validator node와 관련 wallet 및 CNS UI로 구성되며 target network에 validator node를 onboarding합니다.

이 deployment는 다음에 유용합니다.

- 쉽게 배포할 수 있는 ephemeral validator가 필요한 application development
- 다음 caveat가 적용되는 production validator
  - 기본 deployment는 매우 안전하지 않습니다. [Authentication section](/global-synchronizer/deployment/validator-kubernetes)에 설명된 대로 authentication을 활성화해야 합니다.
  - Machine 외부의 ingress 및 TLS를 지원하지 않습니다. Deployment는 machine local로만 유지하고 외부에 노출해서는 안 됩니다.
  - Reliability & scalability: Docker Compose는 crash한 container를 restart하며 아래 설명대로 backup & restore를 지원하지만, Docker Compose deployment는 본질적으로 cloud 기반 Kubernetes deployment보다 제한적입니다.
  - Monitoring: Kubernetes 기반 deployment와 달리 monitoring을 포함하지 않습니다.
  - Production setting에서는 reward 손실과 긴 downtime 후 ledger state catch-up 문제를 방지하도록 validator를 지속적으로 실행하는 것을 목표로 해야 합니다.

## 특정 host의 proxy 우회

<Note>
`http.nonProxyHosts` setting은 다음에 영향을 줍니다.

- CN app(Validator, Scan, SV, Wallet)이 사용하는 HTTP client
- 동일한 JVM의 JDK-level HTTP client, 기본 `ProxySelector`를 통해 적용. CN app과 Canton participant가 JWKS/OIDC discovery에 사용하는 Auth0 JWK library 및 `java.net.HttpURLConnection`을 사용하는 file download 포함
- gRPC Netty transport가 proxy 결정을 기본 JDK `ProxySelector`에 위임하므로 다른 component의 gRPC egress
</Note>

특정 target host에 proxy를 우회하도록 `http.nonProxyHosts`를 설정할 수 있습니다. 일치하는 host에는 구성된 proxy 대신 직접 연결합니다. In-cluster Scan instance 또는 internal monitoring endpoint처럼 local network에서 접근할 수 있는 service에 유용합니다.

값은 표준 Java `nonProxyHosts` grammar를 따르는 `|`로 구분된 pattern 목록입니다.

- Pattern은 request host name에서 case-insensitive하게 일치합니다.
- `*`는 wildcard입니다. 일반적으로 pattern의 시작(`*.internal`) 또는 끝(`10.*`)에 사용합니다.
- Request URI의 raw host string을 대상으로 matching하며 DNS resolution은 수행하지 않습니다. 따라서 둘 다 나열하지 않으면 `localhost`와 `127.0.0.1`은 서로 다른 name으로 처리됩니다.
- 빈 값, 예를 들어 `-Dhttp.nonProxyHosts=`은 "bypass pattern 없음"을 의미합니다.

`validator` service의 external [traffic](/global-synchronizer/deployment/synchronizer-traffic)은 proxy하지만 `localhost`/`127.0.0.1`, `.internal` domain의 모든 host, literal string representation이 `10.`으로 시작하는 모든 IPv4 address에는 proxy를 우회하는 예는 다음과 같습니다.

<Tab title="DevNet (0.7.1)">

1)  Extract한 bundle 내부의 `docker-compose` directory로 이동합니다.

```bash
cd splice-node/docker-compose/validator
```
2)  Current version을 environment variable로 export합니다. export IMAGE_TAG=0.7.1
3)  다음 command로 validator node를 시작하고 ready 상태가 될 때까지 기다립니다. 몇 분 걸릴 수 있습니다.

> ```bash
> ./start.sh -s "<SPONSOR_SV_URL>" -o "<ONBOARDING_SECRET>" -p "<party_hint>" -m "<MIGRATION_ID>" -w
> ```
>
> 여기서:
>
> `<party_hint>`는 validator administrator의 Party ID prefix로 사용됩니다.
> `<organization>-<function>-<enumerator>` format이어야 합니다. 예: `myCompany-myWallet-1`. Validator operator party ID의 일부이므로 이후 변경할 수 없습니다.

<Note>
Splice `0.6.8`부터 `-m` flag는 선택 사항입니다. 새 validator node에서는 생략해야 합니다. 기존 validator node에는 마지막으로 알려진 migration ID 값을 계속 제공해야 합니다.
</Note>

Validator는 `./stop.sh` command로 중지하고 위와 동일한 `start.sh` command로 다시 시작할 수 있습니다. 호출 사이에도 data가 유지됩니다. 이후 호출에서는 secret 자체를 비워 둘 수 있지만 `-o`는 여전히 필수이므로 `-o ""` argument를 제공해야 합니다.

</Tab>

Splice `0.6.8`부터 `-m` flag는 선택 사항입니다. 새 validator node에서는 생략해야 합니다. 기존 validator node에는 마지막으로 알려진 migration ID 값을 계속 제공해야 합니다.
</Note>

Validator는 `./stop.sh` command로 중지하고 위와 동일한 `start.sh` command로 다시 시작할 수 있습니다. 호출 사이에도 data가 유지됩니다. 이후 호출에서는 secret 자체를 비워 둘 수 있지만 `-o`는 여전히 필수이므로 `-o ""` argument를 제공해야 합니다.

## Wallet UI login

<Note>
Docker Compose 기반 validator deployment는 `wallet.localhost` 같은 `.localhost` subdomain을 addressing에 사용합니다. 일부 browser에서는 `.localhost` URL이 작동하지 않는 것으로 보고되었습니다. 문제가 발생하면 Firefox 또는 Chrome 같은 다른 browser를 사용해 보세요. Custom program 또는 script에서 API에 접근하는 데 문제가 있다면 HTTP request의 `HOST` header를 target `.localhost` address로 명시적으로 설정해야 할 수 있습니다.
</Note>

Browser에서 [http://wallet.localhost](http://wallet.localhost)로 wallet UI에 접근할 수 있습니다. Validator administrator username은 `administrator`입니다. Username field에 해당 name을 입력하고 `Log in`을 클릭하면 wallet administrator의 wallet이 표시됩니다.

Administrator account에서 logout하고 다른 username으로 login할 수도 있습니다. User가 처음 login하면 validator node에 onboarding할지 확인하는 message가 표시됩니다.

## CNS UI login

Browser에서 [http://ans.localhost](http://ans.localhost)를 열고, 현재 기본값은 `cns`가 아닌 `ans`입니다, 동일한 administrator user 또는 wallet을 통해 onboarding된 다른 user로 login하여 해당 user의 CNS entry를 구매할 수 있습니다.

### Canton Participant API 접근

[JSON Ledger API](/sdks-tools/api-reference/json-api)는 `json-ledger-api.localhost:80`에서 노출됩니다. 일부 client에서는 올바르게 resolve하도록 `Host: json-ledger-api.localhost` header를 명시적으로 설정해야 할 수 있습니다.

[gRPC Ledger API](/sdks-tools/api-reference/ledger-api)는 `grpc-ledger-api.localhost:80`에서 노출됩니다. 일부 client에서는 올바르게 resolve하도록 `:authority: json-ledger-api.localhost` pseudo-header를 명시적으로 설정해야 할 수 있습니다.

Canton Admin API는 아직 auth를 지원하지 않으므로 기본적으로 노출되지 않습니다. `nginx.conf`에 comment 처리된 section이 있으며 network restriction 등을 통해 공개 노출되지 않도록 보장한다면 활성화하여 노출할 수 있습니다.

## Authentication 구성

<Warning>
기본 deployment는 매우 안전하지 않은 self-signed token을 사용합니다. Wallet UI 또는 machine 및 network interface에 접근할 수 있는 누구나 원하는 user로 wallet에 login할 수 있습니다. Production에서 사용하려면 이 section에 설명된 대로 적절한 authentication을 구성해야 합니다.
</Warning>

Validator용 OAuth provider 설정 지침은 authentication section을 참조하세요. Callback에 구성할 URL은 `http://wallet.localhost` 및 `http://ans.localhost`입니다.

OAuth provider를 설정한 뒤 `.env` file에 다음 environment variable을 설정하여 구성해야 합니다.

| Name | Value |
|------|-------|
| AUTH_URL | `openid-configuration` 및 `jwks.json`을 가져올 OIDC provider URL |
| AUTH_JWKS_URL | `jwks.json`을 가져올 OIDC provider URL. 일반적으로 `${AUTH_URL}/.well-known/jwks.json` |
| AUTH_WELLKNOWN_URL | `openid-configuration`을 가져올 OIDC provider URL. 일반적으로 `${AUTH_URL}/.well-known/openid-configuration` |
| LEDGER_API_AUTH_AUDIENCE | Participant Ledger API의 audience. 예: `https://ledger_api.example.com`. Participant의 `ledger-api.auth-services.target-audience` configuration 설정 |
| LEDGER_API_AUTH_SCOPE | Participant Ledger API의 scope. Participant의 `ledger-api.auth-services.target-scope` configuration 설정. 선택 사항 |
| VALIDATOR_AUTH_AUDIENCE | Validator backend API의 audience. 예: `https://validator.example.com` |
| VALIDATOR_AUTH_CLIENT_ID | Validator app backend용 OAuth app의 client ID |
| VALIDATOR_AUTH_CLIENT_SECRET | Validator app backend용 OAuth app의 client secret |
| LEDGER_API_ADMIN_USER | Validator app용으로 발급한 JWT의 `sub` field와 일치해야 함. 일부 auth provider에서는 `CLIENT_ID@clients` 형태 |
| WALLET_ADMIN_USER | Wallet administrator로 login할 user의 user ID. `auth0\|43b68e1e4978b000cefba352` 같은 full user ID여야 하며 suffix `43b68e1e4978b000cefba352`만 사용하면 안 됨 |
| WALLET_UI_CLIENT_ID | Wallet UI용 OAuth app의 client ID |
| ANS_UI_CLIENT_ID | CNS UI용 OAuth app의 client ID |
| CONTACT_POINT | 필요할 때 다른 node operator가 연락할 수 있는 validator node contact point, Slack username 또는 email address. 선택 사항 |

Deployment에서 auth를 활성화하려면 다음과 같이 `start.sh` command에 `-a` flag를 추가합니다.

<ExternalSpliceMainSpliceRstCodeDocsSrcValidatorOperatorValidatorComposeBash281 />

기본적으로 client ID 및 secret은 request body에 전달됩니다. IAM에서 HTTP Basic Authentication 사용을 요구한다면 [Ad-Hoc Configuration](./configuration)을 통해 environment variable을 설정할 수 있습니다. 이 option은 Splice >= 0.6.10에서만 사용할 수 있습니다.

```
ADDITIONAL_CONFIG_HTTP_BASIC_AUTH=canton.validator-apps.validator_backend.participant-client.ledger-api.auth-config.http-basic-auth = true
```

Machine에 non-authenticated validator를 이미 배포했다면 `./stop.sh`로 validator를 중지하고 위와 같이 `-a` flag로 restart하여 authenticated validator로 migrate할 수 있습니다. Validator operator user는 자동으로 migrate되며 `WALLET_ADMIN_USER` variable로 지정한 user가 validator operator party와 연결됩니다. 다른 user도 validator에 onboarding했다면 자동 migrate되지 않으므로 OAuth user를 해당 party와 수동으로 연결해야 합니다. 먼저 모든 관련 user의 party ID를 기록하세요. Non-authenticated validator를 중지하기 전에 wallet UI 오른쪽 위에서 복사할 수 있습니다. 이제 migrate할 각 user에 대해 [Splice Wallet의 User, Party 및 Wallet section](/global-synchronizer/deployment/validator-users)의 user-party 연결 지침을 따르되 admin party ID를 각 user와 연결하려는 party ID로 교체합니다.

## Transfer offer sweep 및 auto-accept 구성

<ExternalSpliceMainSpliceRstFullDocsSrcCommonWalletSweeps />

이를 위해 다음 section을 채우고 validator environment에 다음 additional config를 추가합니다.

```yaml
# sweep by transferring directly through the transfer preapproval of the receiver,
# if set to false sweeping creates transfer offers that need to be accepted on the receiver side.
# Note that this refers to the preapprovals described in /appdev/modules/m7-canton-coin-preapprovals
# and not to auto accepting transfers. Auto accept transfers does not setup preapproval contracts that allow
# for a direct transfer but just automates the acceptance of the transfer offer so in that case
# useTransferPreapproval should be set to false.
services:
  validator:
    environment:
       - |
          ADDITIONAL_CONFIG_WALLET_SWEEP=
            canton.validator-apps.validator_backend.wallet-sweep {
              "<senderPartyId1>" {
                max-balance-usd = 1000
                min-balance-usd = 100
                receiver = "<receiverPartyId>"
                use-transfer-preapproval = false
              }
            }
```

## Systemd 및 기타 init system과 통합

Systemd 또는 유사한 init system으로 validator를 관리하려면 올바른 argument로 `start.sh` script를 호출하는 service를 생성합니다. 다만 `start.sh`는 `-d/--detach` option으로 `docker compose up`을 호출하므로 container가 실행된 후 script가 계속 실행되지 않고 exit합니다.

이 시점에 service가 Docker Compose를 중지하지 않도록 해야 합니다. Systemd에서는 `RemainAfterExit=true`를 설정합니다. 자세한 내용은 [systemd 문서](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)를 참조하세요. 다른 init system을 사용한다면 script exit 후 Docker Compose가 계속 실행되도록 유사한 option을 찾으세요.

또는 script에서 `-d` option을 제거하여 script가 계속 실행되도록 편집할 수 있습니다.
