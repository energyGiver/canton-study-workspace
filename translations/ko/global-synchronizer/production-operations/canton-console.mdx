# Canton Console

Canton은 entity를 동적으로 시작하고 중지하며 다양한 administrative 또는 debugging command를 실행할 수 있는 console(REPL)을 제공합니다.

모든 console command는 유효한 Scala여야 합니다. Console은 Scala 기반 scripting 및 [REPL]() framework인 [Ammonite]()를 기반으로 구축됩니다. Console 사용성을 개선하기 위해 implicit type [conversion]() 집합도 정의합니다. 특히 console command에 [SynchronizerAlias](), [Fingerprint]() 또는 [Identifier]()가 필요할 때 자동으로 올바른 type으로 변환되는 `String`을 대신 전달할 수도 있습니다.

`examples/` sub-directory에는 `.canton` extension을 사용하는 몇 가지 sample script가 있습니다.

Command는 thematic group으로 구성됩니다. 일부 command는 접근할 수 있도록 configuration directive를 통해 명시적으로 활성화해야 합니다.

어떤 operation은 두 node type 모두에서 사용할 수 있지만 다른 operation은 participant node 또는 synchronizer에만 해당합니다. 일관성을 위해 manual을 node type별로 구성하므로 일부 command가 두 번 나타납니다. 다만 자세한 설명은 participant documentation에서만 제공합니다.

## Remote Administration

Canton console은 local in-process node와 remote node 모두에서 작동합니다. Network address, port 및 authentication information을 구성한 뒤 하나의 Canton console을 사용하여 system의 모든 node를 관리할 수 있습니다.

예를 들어 이전에 다음과 같은 command로 daemon mode에서 Canton instance를 시작했을 수 있습니다.

```bash
./bin/canton daemon -c <some config>
```

그런 다음 다음과 같은 `remote-participant` configuration을 사용하여 이미 실행 중인 participant에 command를 실행할 수 있습니다.

``` none
// Example remote participant configuration

// Include TLS configuration
include required("../tls/mtls-admin-api.conf")
include required("../tls/tls-ledger-api.conf")
canton {
    remote-participants.participant {
        ledger-api {
            address = localhost
            port = 10001
            tls = ${?_shared.ledger-api-client-tls}
        }
        admin-api {
            address = localhost
            port = 10002
            tls = ${?_shared.admin-api-client-mtls}
        }
    }
}
```

Remote config file이 있다면 다음과 같이 remote Canton instance에서 command를 실행하도록 구성된 local Canton console을 시작합니다.

```bash
./bin/canton -c config/remote-participant1.conf
```

또한 remote configuration을 사용하여 script를 실행할 수 있습니다.

```bash
./bin/canton run <some-canton-script> -c config/remote-participant1.conf
```

대부분의 Canton command는 remote console에서 실행할 수 있습니다. 다만 일부 command는 node 자체의 local console에서만 호출할 수 있습니다.

Participant의 config file이 있으면 `generate` command를 사용하여 skeleton remote config file을 생성할 수 있습니다.

```bash
./bin/canton generate remote-config -c participant1.conf
```

Network에 따라 자동 생성된 configuration을 수동으로 편집하여 hostname을 조정해야 할 수 있습니다. 여러 remote node에 접근하려면 자동 생성된 configuration을 하나의 remote configuration file로 통합하거나 command line에 모든 configuration file을 포함합니다.

```bash
./bin/canton -c participant1.conf,participant2.conf,mysynchronizer.conf
```

### TLS 및 Authorization

Production use case, 특히 Admin API가 localhost에만 bind되지 않는 경우 mutual authentication을 사용하는 TLS 활성화를 권장합니다.

유효한 access token이 있다면 authorization을 사용하는 installation에서도 remote console을 사용할 수 있습니다. 다음 snippet과 같이 configuration을 수정하거나 remote console launch command에 option을 추가하면 됩니다.

```bash
./bin/canton daemon \
   -c remote-participant1.conf \
   -C canton.remote-participants.<remote-participant-name>.token="<encoded-and-signed-access-token-as-string>" \
   --bootstrap <some-script>
```

Remote console은 target participant의 Ledger API와 상호작용할 때 token을 사용합니다. 또한 token에서 user ID를 추출하여 command submission 및 completion subscription request의 userId field를 채우는 데 사용합니다. 이는 다음 console command에 영향을 줍니다.

- ledger_api.commands.submit
- ledger_api.commands.submit_flat
- ledger_api.commands.submit_async
- ledger_api.completions.list
- ledger_api.completions.list_with_checkpoint
- ledger_api.completions.subscribe

## Node Reference

특정 node에 command를 실행하려면 Scala variable인 reference로 node를 참조해야 합니다. 구성된 identifier를 사용하여 모든 synchronizer entity 및 participant에 named variable이 생성됩니다. 예를 들어 sample `examples/01-simple-topology/simple-topology.conf` configuration file은 synchronizer `mysynchronizer`와 participant `participant1`, `participant2`를 참조합니다. Console에서 `mysynchronizer`, `participant1`, `participant2`로 사용할 수 있습니다.

Console은 type별 node 목록을 참조할 수 있는 추가 generic reference도 제공합니다. Generic node reference는 각 node type에 대해 local, remote 또는 해당 type의 모든 node라는 세 subset을 지원합니다. Participant에는 다음을 사용할 수 있습니다.

```scala
participants.local
participants.remote
participants.all
```

Generic node reference는 Scala syntax 방식으로 사용할 수 있습니다.

```scala
participants.all.foreach(_.dars.upload("my.dar"))
```

Participant reference는 다음처럼 여러 node에 한 번에 수행해야 하는 경우가 많은 action을 위한 generic command도 지원합니다.

```scala
participants.local.dars.upload("my.dar")
```

## Help

Canton에 help를 요청하면 유용한 정보를 얻을 수 있습니다. 다음을 입력해 보세요.

    help

또는

    participant1.help()

존재하는 command 및 command group의 개요를 확인할 수 있습니다. `help()`는 모든 level에서 작동하며, 예를 들면 `participant1.synchronizers.help()`입니다. 특정 function을 검색하려면 `help("list")`를 사용하고 각 command의 자세한 help 설명을 가져오려면 `participant1.parties.help("list")`를 사용할 수도 있습니다.

## Lifecycle Operation

개별 synchronizer 및 participant와 이들의 sequence에서 지원됩니다. Sequence에서 호출하면 sequence 순서대로 operation이 실행됩니다. 예를 들면 다음과 같습니다.

```bash
nodes.local.start()
```

구성된 모든 local synchronizer 및 participant를 시작하는 데 사용할 수 있습니다.

Node가 database persistence를 사용하여 실행 중이면 database migration command(`db.migrate`)를 지원합니다. Node를 처음 시작할 때 migration이 자동으로 수행됩니다. 하지만 새 software version의 일부로 추가된 새 migration은 기본적으로 command를 사용하여 수동으로 실행해야 합니다. 드문 경우 `db.migrate`를 실행하기 전에 `db.repair_migration`을 실행해야 할 수도 있습니다. 자세한 내용은 `db.repair_migration` 설명을 참조하세요. 원한다면 다음 configuration option으로 "migrate-and-start" mode를 활성화하여 database migration을 자동으로 수행할 수도 있습니다.

Data continuity와 이에 따른 database migration은 minor 및 patch version update 사이에서만 작동한다고 보장됩니다.

Synchronizer, sequencer 및 mediator node가 완전히 작동하려면 추가 설정이 필요할 수 있습니다. 자세한 내용은 synchronizer bootstrapping을 확인하세요.

## Timeout

Console command timeout은 configuration file의 해당 console command timeout section에서 구성할 수 있습니다.

``` none
canton.parameters.timeouts.console = {
    bounded = 2.minutes
    unbounded = Inf // infinity
    ledger-command = 2.minutes
    ping = 30.seconds
}
```

`bounded` argument는 processing이 완료되면 끝나야 하는 모든 command에 사용하고, `unbounded` timeout은 processing time을 제어할 수 없는 command에 사용합니다. 특히 실행 시간이 매우 길 수 있는 command에 사용됩니다.

일부 command에는 `NonNegativeDuration` type으로 명시적으로 전달할 수 있는 특정 timeout argument가 있습니다. 편의를 위해 console에는 기본적으로 `scala.concurrent.duration._`의 implicit과 Scala type `scala.concurrent.duration.FiniteDuration`에서 `NonNegativeDuration`으로의 implicit conversion이 포함됩니다. 따라서 일반 Scala expression을 사용하여 timeout을 다음과 같이 작성할 수 있습니다.

    participant1.health.ping(participant1, timeout = 10.seconds)

Implicit conversion이 올바른 type으로 변환합니다.

일반적으로 timeout을 재구성할 필요는 없으며 안전한 기본값을 사용하는 것이 좋습니다.

## Console의 Code Generation

Daml SDK는 Daml model용 **Java** 또는 **Scala** binding을 생성하는 code generation [utility]()를 제공합니다. 이러한 binding은 console에서 typed 방식으로 ledger와 상호작용하는 편리한 방법입니다. 연결된 문서는 `daml` command를 사용하여 binding을 생성하는 방법을 설명합니다. **Scala** binding은 공식적으로 지원되지 않으므로 application development에 사용해서는 안 됩니다.

Binding build를 성공적으로 완료한 뒤에는 console script에서 **Ammonite** magic import를 사용하여 결과 `jar`를 Canton console에 load할 수 있습니다.

```scala
interp.load.cp(os.Path("codegen.jar", base = os.pwd))

@ // the at triggers the compilation such that we can use the imports subsequently

import ...
```

## Canton Administration API

Canton은 administrative interaction을 위한 built-in mode로 console을 제공합니다. 내부적으로 모든 administrative console action은 administration gRPC API를 사용하여 수행됩니다. 따라서 자체 administration application을 작성하여 administration gRPC endpoint에 연결할 수도 있습니다.

Release artifact의 `protobuf/` sub-directory에는 gRPC 기반 protocol buffer가 포함됩니다. 특히 administrative gRPC API는 `admin` sub-directory에 있습니다.

예를 들어 deployment를 smoke-test하는 간단한 workflow를 구현하는 Ping Pong Service는 protocol buffer `*/protobuf/*/admin/*/ping_pong_service.proto`로 정의됩니다. 여기서 `*`는 중간 directory를 나타냅니다. 이 service는 console command health.ping에서 사용됩니다.

Protocol buffer는 위에서 언급한 것과 유사한 sub-directory structure를 따르는 [repository]()에서도 제공됩니다.
