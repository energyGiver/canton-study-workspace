## Node Identity Backup

SV Node가 실행되고 onboarding되면 SV Node identity를 반드시 backup하세요. **이 information은 매우 sensitive하며 Participant, Sequencer 및 Mediator의 private key를 포함한다는 점에 유의하세요.** Secret Manager와 같은 안전한 위치에 저장하세요. 한편 이 information은 identity를 유지하고 Canton Coin holding 등에 접근하는 데 매우 중요하므로 cluster 외부에 backup해야 합니다.

## Postgres Instance Backup

### Backup 수행

대부분의 backup은 독립적으로 수행할 수 있지만 다음 두 가지 엄격한 순서 requirement가 있습니다.

1. App Postgres instance backup은 Participant backup보다 반드시 이른 시점에 수행해야 합니다. Participant backup을 시작하기 전에 app instance backup이 완료되었는지 확인하세요.
2. CantonBFT(`cantonbft`) database backup은 Sequencer database backup보다 반드시 이른 시점에 수행해야 합니다. Sequencer backup을 시작하기 전에 CantonBFT backup이 완료되었는지 확인하세요.

Cluster에서 자체 Postgres instance를 실행하는 경우 `pgdump` 같은 tool을 사용하거나 underlying Persistent Volume snapshot을 생성하여 backup할 수 있습니다. 마찬가지로 Cloud-hosted Postgres를 사용하는 경우 `pgdump` 같은 tool이나 Cloud provider가 제공하는 backup tool을 사용할 수 있습니다.

Postgres instance를 최소 4시간마다 backup하세요.

### Historical backup

Genesis부터 gap이 없는 history를 보존하려면 historical backup이 필요합니다. 이 history는 audit 중에 사용할 수 있으며 더 일반적으로 current Synchronizer state의 correctness를 external observer에게 증명할 수 있습니다.

Sequencer와 Participant에서 [pruning](/global-synchronizer/production-operations/sv-pruning)을 활성화하면 각 pruning window마다 historical backup을 유지해야 합니다. 즉 두 historical backup 사이의 time difference가 Sequencer와 Participant에 설정된 `retentionPeriod`보다 작도록 backup을 보존해야 합니다.

Default로 SV의 Mediator와 Splice app에는 pruning이 활성화되어 있지 않습니다.

또한 [Logical Synchronizer upgrade](/global-synchronizer/production-operations/logical-synchronizer-upgrade) 전후에 걸쳐 backup을 유지해야 합니다. 여기에는 모든 historical Sequencer backup과 다른 app backup이 포함됩니다.

## CometBFT Backup

Postgres instance 외에도 CometBFT가 사용하는 storage를 4시간마다 backup해야 합니다. CometBFT는 Postgres를 사용하지 않습니다. Underlying Persistent Volume snapshot을 생성하여 storage를 backup하는 것이 좋습니다.

### Historical backup

Genesis부터 gap이 없는 history를 보존하려면 historical backup이 필요합니다. 이 history는 audit 중에 사용할 수 있으며 더 일반적으로 current Synchronizer state의 correctness를 external observer에게 증명할 수 있습니다.

CometBFT에는 default로 [pruning](/global-synchronizer/production-operations/sv-pruning)이 활성화되어 있습니다. Pruning window는 유지할 block 수로 정의합니다. 최소 30일 data를 유지하는 값으로 block 수를 설정하는 것을 목표로 합니다. 두 backup을 수행한 block height 차이가 구성된 유지 block 수보다 작도록 CometBFT historical backup을 유지해야 합니다. 2주마다 더 적극적으로 backup을 수행하고 보존하는 것이 좋습니다.

또한 Logical Synchronizer upgrade 전후에 걸쳐 backup을 유지해야 합니다.
