# Party Management

Party는 User 또는 organization을 represent하며 Daml ledger와 상호작용하는 entity입니다. Participant Node에 onboard하면 transaction을 submit하고 ledger에 access할 수 있습니다.

다음 section에서는 local Party를 onboard하는 방법을 설명합니다. 다른 종류의 Party onboarding은 다음 how-to를 참고하세요.

- Decentralized Party는 Decentralized Party Overview 문서를 참고하세요.
- External Party는 Onboard External Party tutorial을 참고하세요.
- Participant에서 이미 host되는 Party는 Party Replication 문서를 참고하세요.

## Ledger API를 통한 새 Party onboarding

Ledger API에 access할 수 있다면 `parties` command로 새 Party를 onboard할 수 있습니다. 이 command는 기반 Ledger API endpoint를 wrapping한 것입니다. 자세한 내용은 Ledger API 문서를 참고하세요.

1. Party name을 정의합니다. Name은 자유롭게 선택할 수 있지만 `\[a-zA-Z0-9:-\_ \]` format을 따라야 하고 185자를 넘을 수 없으며 연속된 colon 두 개를 사용할 수 없고 Namespace에서 unique해야 합니다.

예를 들어 Party `bob`을 host하려고 합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties1 />

2. Party를 allocate할 optional Synchronizer ID를 지정합니다. Participant는 이 Synchronizer에 연결되어 있어야 합니다. Participant가 Synchronizer 하나에만 연결되어 있다면 이 parameter를 생략할 수 있습니다. 그렇지 않으면 각 Synchronizer에서 Party를 명시적으로 enable해야 합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties2 />

3. Optional annotation을 정의합니다. 이는 Party와 연관되고 이 Ledger API server local에 저장되는 key-value pair입니다. Annotation은 allocated Party의 metadata를 유지하는 데 유용합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties3 />

4.  Optional Identity Provider ID를 정의합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties4 />

5.  이 Participant의 ""my-synchronizer""에서 Party를 enable합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties5 />

6.  두 번째 Synchronizer에 Party를 onboard하려면 다른 Synchronizer ID로 `allocate` command를 다시 실행합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties6 />

### Party 갱신

1.  `update` command를 사용하여 Party annotation을 갱신할 수 있습니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties7 />

2.  `update_idp` command를 사용하여 Party Identity Provider도 갱신할 수 있습니다.

`list` command를 사용하여 Party를 찾을 수 있습니다.

## Admin API를 통한 새 Party onboarding

Party allocation을 더 세밀하게 control하려면 Admin API를 사용합니다. Participant Node에 새 Party를 onboard하려면 다음 단계를 수행합니다.

1. Party name을 정의합니다. 위에서 설명한 것과 같은 rule이 적용됩니다. 예를 들어 Party `alice`를 host하려고 합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties10 />

2.  Optional Namespace를 정의합니다. 기본적으로 Alice는 command를 submit하는 Participant의 Namespace를 사용합니다.

Namespace에 관한 자세한 내용은 Namespaces 문서를 참고하세요.

3. Party를 allocate할 optional Synchronizer alias를 지정합니다. Participant는 해당 Synchronizer에 연결되어 있어야 합니다. Participant가 Synchronizer 하나에만 연결되어 있다면 이 parameter를 생략할 수 있습니다. 그렇지 않으면 각 Synchronizer에서 Party를 명시적으로 enable해야 합니다.

4.  이 Participant에서 Party를 enable합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties11 />

5.  Party가 onboard되었는지 verify합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties12 />

6.  두 번째 Synchronizer에 Party를 onboard하려면 다른 Synchronizer alias로 `enable` command를 다시 실행합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties13 />

### Party 찾기

`list` command를 사용하여 Party를 찾을 수 있습니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties14 />

Participant Node 및 Synchronizer로도 filter할 수 있습니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesParties15 />

<Warning>

수행할 작업을 확실히 이해하고 있다면 다음 command로 특정 Synchronizer에서 Party를 비활성화할 수 있습니다.

## Multi-hosted Party

*Multi-hosted Party*는 두 개 이상의 Participant에서 host되는 Party입니다. 그러면 한 Participant에서 다른 Participant로 Party를 replicate하는 방법이 필요합니다.

Party를 multi-host하는 가장 단순하고 안전한 방법은 해당 Party가 아직 어떤 Daml transaction에도 참여하지 않은 경우에만 사용할 수 있습니다. 그렇지 않으면 offline Party replication 절차를 수행해야 합니다.

# Party replication

*Party replication*은 **단일 Synchronizer 안에서** 기존 Party를 추가 Participant에 복제하는 process입니다. 이 process에서 Party를 이미 host하는 Participant를 *source* Participant, 새 Participant를 *target* Participant라고 합니다.

Replicate하려는 Party가 Daml transaction에 참여한 적이 있는지에 따라 운영 절차의 complexity 및 risk가 크게 달라집니다.

따라서 Participant에 Party를 onboard하고 **Party를 사용하기 전에** simple Party replication 단계에 따라 다른 Participant로 replicate하세요.

그렇지 않으면 offline Party replication 절차를 적용해야 합니다.

<Note>
**Party replication**은 **Party migration**과 다릅니다. Party migration에는 기존 Participant에서 Party를 제거, 즉 *offboard*하는 최종 단계가 추가됩니다.

Party offboarding과 이에 따른 Party migration은 현재 지원되지 않습니다.
</Note>

## Party replication authorization

### Authorization 동작 방식

Party와 새 hosting Participant가 각각 Party-to-Participant mapping Topology transaction을 발행하여 동의해야 합니다. 이를 통해 Party replication에 대한 상호 합의를 보장합니다.

### External Party

External Party의 경우 Party topology 변경은 External Party Namespace key의 signature로 명시적으로 authorize해야 합니다. How-to에서 Party authorization이 필요할 때마다 *local* Party와 *external* Party를 구분합니다. External Party 절차에서는 Party-to-Participant mapping update를 authorize하는 abstract function을 참조합니다.

```python
class HostingParticipant:
    participant_uid: str
    permission: Enums.ParticipantPermission

def update_external_party_hosting(
    party_id: str,
    synchronizer_id: str,
    confirming_threshold: int,
    hosting_participants_add_or_update: [HostingParticipant]
)
```

이 function의 구현 예시는 External Party onboarding 문서에 있습니다. 구현은 Party Namespace private key와 Party confirming Node 중 하나의 Admin API에 연결된 gRPC channel도 받습니다. 간결성을 위해 위 function declaration에서는 생략했습니다.

이 how-to에서 Topology 변경 authorize 외의 action에 `source` Participant를 사용할 때는 External Party의 기존 confirming Participant 중 하나를 사용해야 합니다.

### Owner가 여러 명인 Party

Decentralized Namespace의 member group이 Party를 소유하면 해당 owner 중 최소 수, 즉 정의된 threshold가 새 hosting arrangement를 승인해야 합니다. 충분한 개별 owner가 각각 자체 Party-to-Participant mapping Topology transaction을 발행하면 threshold가 충족됩니다.

### Activation

상호 authorization process를 완료하면 target Participant에서 Party가 *activate*됩니다.

## Simple Party replication

Party를 replicate하는 가장 단순하고 안전한 방법은 Party가 contract의 stakeholder가 되기 **전에** 수행하는 것입니다.

<Warning>
Party가 이미 Daml transaction에 참여했다면 offline Party replication을 사용해야 합니다.
</Warning>

Simple Party replication은 다음 단계로 구성되며 나열된 **순서대로** 수행해야 합니다.

1.  Participant Namespace 또는 전용 Namespace에 Party를 생성합니다.
2.  Package를 vet합니다.
3.  하나 이상의 추가 Participant가 Party를 host하도록 authorize합니다.
4.  Party를 사용합니다.

다음에서는 두 Participant를 사용하여 이 단계를 보여줍니다.

``` none
@ val source = participant1
    source : com.digitalasset.canton.console.LocalParticipantReference = Participant 'participant1'
```

``` none
@ val target = participant2
    target : com.digitalasset.canton.console.LocalParticipantReference = Participant 'participant2'
```

``` none
@ val synchronizerId = source.synchronizers.id_of("mysynchronizer")
    synchronizerId : SynchronizerId = da::1220a82692ab...
```

### 1. Party 생성

Party Alice를 생성합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesPartyReplication1 />

<Note>
이 예시에서 **local Party Alice**는 `source` Participant가 소유하며 이는 단순화한 설정입니다. Alice가 Participant Namespace에 register되어 있음을 의미하지만 필수 조건은 아닙니다.

대신 Party를 자체 전용 Namespace에 생성하거나 External Party를 생성할 수 있습니다.
</Note>

### 2. Package vetting

진행하기 **전에** target Participant에서 package를 vet합니다.

<Note>
이 process가 익숙하지 않다면 package vetting에 관한 일반 설명을 읽으세요.
</Note>

### 3. Party multi-host

Party Alice가 target Participant에서 host되는 데 동의해야 합니다.

Source Participant가 Party Alice를 소유하므로 `source` Participant에서 Party-to-Participant mapping Topology transaction을 발행해야 합니다.

#### Source Participant에서 hosting update authorize

Local Party

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesPartyReplication2 />

Participant는 서로 다른 permission으로 Party를 host할 수 있습니다. 이 예시에서 target Participant는 submission permission으로 Party Alice를 host하며 Alice는 해당 Participant에서 Daml transaction을 submit할 수 있습니다.

External Party

External Party onboarding process에서는 Party 생성 중 여러 Node에 host하는 multi-hosted External Party를 포함하여 Party hosting relationship을 declare하는 방법을 보여줍니다. 항상 단일 Node에서 먼저 host되어 나중에 multi-host를 위해 Party-to-Participant mapping을 amend해야 하는 local Party와 달리 External Party는 onboarding process 중 한 단계로 이를 수행할 수 있습니다. 자세한 내용은 onboarding process를 참고하세요.

#### Target Participant에서 hosting update authorize

Process를 완료하려면 target Participant도 Alice를 새로 host하는 데 동의해야 합니다. 따라서 `target` Participant에서 **동일한** Party-to-Participant mapping Topology transaction을 발행해야 합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesPartyReplication3 />

<Note>
여기서 Participant permission은 이전 단계와 같아야 합니다. 특히 External Party에서는 `Confirmation` 또는 `Observation`이어야 합니다.
</Note>

Party-to-Participant mapping이 적용되면 replication이 완료됩니다. 결과적으로 Party Alice가 `source` 및 `target` Participant 모두에서 multi-host됩니다.

Alice를 더 많은 Participant로 replicate하려면 먼저 `newTarget` Participant에서 package를 vet한 다음 기존 `source` 및 `newTarget` Participant를 사용하여 replication을 다시 수행합니다.

### 3.a Confirmation threshold를 동시에 변경하여 Party replicate(3번 단계 variant)

<Note>
**External Party**는 onboarding process 중 이미 threshold가 정의되므로 이 section이 적용되지 않습니다.
</Note>

Party confirmation threshold를 변경하려면 이전과 다른 Party-to-Participant mapping propose 절차를 사용해야 합니다.

이 alternative method를 사용하면 단일 operation으로 replication을 수행하고 threshold를 update할 수 있습니다.

다음 예시는 앞의 예시에서 이어지며 Party Alice를 `source` Participant에서 `newTarget` Participant로 replicate하면서 confirmation threshold를 3으로 설정하는 방법을 보여줍니다. 또한 Alice를 host할 세 Participant 모두의 Participant permission을 confirmation으로 설정합니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantHowtosOperatePartiesPartyReplication4 />


## Offline Party replication

Offline Party replication은 여러 단계로 이루어진 manual process입니다.

Replication을 시작하기 전에 target Participant와 Party가 모두 새 hosting arrangement에 명시적으로 동의해야 합니다.

그런 다음 source Participant에서 Party의 Active Contract Set(ACS)을 export하고 target Participant로 import하여 replication을 수행합니다.

<Note>
- 단일 physical machine 또는 environment에서 Party ACS file을 export/import할 수 있도록 하나의 Canton Console을 source 및 target Participant 모두에 연결합니다. 그렇지 않으면 ACS export file을 target Participant로 import할 위치에 secure하게 전달해야 합니다.
- Offline Party replication에서는 Party ACS를 import하기 전에 target Participant를 모든 Synchronizer에서 disconnect해야 합니다. 이것이 *offline* Party replication이라고 부르는 이유입니다.
- Target Participant에 Party를 onboard하는 동안 ACS commitment mismatch가 감지될 수 있습니다. 이는 예상된 현상이며 시간이 지나면 해결되므로 Party replication 절차 중에는 해당 error를 무시합니다.
</Note>

<Warning>
**주의: ACS import를 시작하기 전에 target Participant를 backup해야 합니다.**

ACS import가 crash 또는 의도하지 않은 Node restart 등으로 중단되거나 manual 운영 단계를 끝까지 수행하지 못한 경우 clean recovery point를 보장합니다. 이 backup이 있으면 target Participant를 안전하게 reset하고 **진행 중인 Offline Party replication을 계속 완료**할 수 있습니다.
</Warning>

## Offline Party replication 단계

다음 단계를 나열된 **정확한 순서대로** 수행해야 합니다.

1.  **Target: Package Vetting** - Target Participant가 필요한 모든 package를 vet하는지 확인합니다.
2.  **Source: Data Retention** - Source Participant가 export에 충분한 기간 동안 data를 유지하는지 확인합니다.
3.  **Target: Authorization** - Target Participant가 onboarding flag를 설정하여 새 hosting을 authorize합니다.
4.  **Target: Isolation** - 모든 Synchronizer에서 disconnect합니다.
5.  **Target: Disable auto-reconnect** - Restart 시 automatic reconnection을 비활성화합니다.
6.  **Source: Party Authorization** - Party가 onboarding flag를 설정하여 replication을 authorize합니다.
7.  **Source: ACS Export** - 현재 Party를 host하는 Participant가 ACS를 export합니다.
8.  **Source: Re-enable pruning** *(optional)* - Automatic pruning을 다시 활성화합니다.
9.  **Target: Backup** - ACS import를 시작하기 전에 target Participant를 backup합니다.
10. **Target: ACS Import** - Target Participant가 ACS를 import합니다.
11. **Target: Reconnect** - Target Participant가 Synchronizer에 reconnect합니다.
12. **Target: Re-enable auto-reconnect** *(optional)* - Automatic reconnection을 다시 활성화합니다.
13. **Target: Onboarding Flag Clearance** - Target Participant가 onboarding flag clearance를 발행합니다.

<Warning>
Offline Party replication은 문서에 설명된 **단계와 순서**를 엄격히 지켜 신중하게 수행해야 합니다. 설명된 운영 flow를 따르지 않으면 상당한 manual correction이 필요한 error가 발생할 수 있습니다.

이 문서는 guide를 제공합니다. Environment에 따라 조정이 필요할 수 있으므로 production 사용 전에 test environment에서 철저히 테스트하세요.
</Warning>

# Decentralized Party 개요

Decentralized Party는 서로 다른 세 feature를 결합합니다.

- Party Topology Management의 decentralization: 해당 Party의 모든 Topology transaction에 threshold 수의 key signature가 필요하도록 보장하는 `decentralized namespace`
- Party transaction confirmation의 decentralization: 여러 confirming Participant와 threshold를 포함하는 `party to participant mapping`을 사용하여 해당 Party confirmation이 필요한 transaction에 threshold 수의 Participant Node confirmation도 필요하도록 보장
- Party transaction submission의 decentralization: 선택적으로 `party to key mapping`을 사용하여 External Party의 direct authorization이 필요한 transaction submit을 지원합니다. 예를 들어 threshold 수의 key로 prepared transaction에 sign하여 해당 Party가 signatory인 contract를 생성합니다. Party-to-Key mapping이 정의되지 않았다면 `party to participant` threshold가 1인 시점이 있었을 때 submission right를 가진 Node가 initial contract를 생성해야 하며 confirmation right만으로는 부족합니다.

## Member set 변경

Member 추가 및 제거 단계는 동일합니다. 기존 member의 threshold가 있으며 새 member는 세 Topology transaction을 submit해야 합니다. 세 mapping 모두가 아니라 일부에만 추가할 수도 있지만 일반적으로 세 mapping을 sync 상태로 유지하는 것이 좋습니다.

`PartyToParticipant`에 member를 추가하려면 Topology transaction뿐 아니라 ACS export 및 import를 포함하는 full Party migration이 필요합니다. 자세한 내용은 이 topic의 scope를 벗어납니다.

## Decentralized Namespace 계산

위 예시에서는 `DecentralizedNamespaceDefinition.computeNamespace(Set(aliceNamespace, bobNamespace, charlieNamespace))`를 사용하여 initial owner의 Namespace에서 Decentralized Namespace를 계산했습니다. 여기서는 initial owner만 중요하며 owner를 추가하거나 제거해도 Decentralized Namespace는 바뀌지 않습니다.

하지만 Topology gRPC API를 직접 사용하는 등의 이유로 Canton Console에서 실행하지 않거나 다른 이유로 Namespace를 직접 계산해야 할 수 있습니다. 이러한 경우 Python에서 계산하는 방법은 다음과 같습니다.

Namespace를 lexicographic 순서로 정렬:

```python
def compute_decentralized_namespace(owners):
    builder = hashlib.sha256()
    # hash purpose prefix
    builder.update((37).to_bytes(4))
    for owner in sorted(owners):
        # namespace length
        builder.update(len(owner).to_bytes(4))
        builder.update(owner.encode("utf-8"))
    # 1220 is the Canton prefix for sha256 hashes
    return f"1220{builder.hexdigest()}"
```
