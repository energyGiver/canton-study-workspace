# 시작하기

Canton에 관심이 있다면 여기서 시작하세요. 사전 지식은 필요하지 않으며 다음 내용을 학습합니다.

- Canton을 설치하고 간단한 test configuration에서 실행하는 방법
- Canton의 주요 개념
- 주요 configuration option
- Canton의 간단한 diagnostic command
- Canton identity management의 기본 사항
- 새로운 smart contract code를 upload하고 실행하는 방법

## 설치

Canton은 JVM application입니다. Native로 실행하려면 system에 Java 11 이상이 설치되어 있어야 합니다. 또는 `ghcr.io/digital-asset/decentralized-canton-sync/docker/canton`의 Docker image를 사용할 수 있으며, 공개된 tag는 [decentralized-canton-sync packages page](https://github.com/digital-asset/decentralized-canton-sync/pkgs/container/decentralized-canton-sync%2Fdocker%2Fcanton)에 나열되어 있습니다. 각 network의 현재 tag는 [Version Compatibility Dashboard](/shared/version-compatibility-dashboard)를 참조하세요.

Canton은 platform에 종속되지 않습니다. Development 용도로는 macOS, Linux, Windows에서 실행할 수 있습니다. Production 지원 platform은 Linux입니다.

참고: Windows 10에서 terminal color를 활성화하지 않으면 Canton console output이 깨집니다. 예를 들어 `cmd.exe`를 실행한 뒤 `reg add HKCU\Console /v VirtualTerminalLevel /t REG_DWORD /d 1`을 실행하세요.

먼저 [latest release](https://github.com/digital-asset/daml/releases)를 download하고 archive를 압축 해제합니다.

압축 해제한 archive의 구조는 다음과 같습니다.

``` none
.
├── bin
├── config
├── daml
├── dars
├── demo
├── drivers (enterprise)
├── examples
├── lib
└── ...
```

- `bin`: Canton 실행 script를 포함합니다. Unix 계열 system에서는 `canton`, Windows에서는 `canton.bat`을 사용합니다.
- `config`: 각 node type의 reference configuration file을 포함합니다.
- `daml`: 일부 sample smart contract의 source code를 포함합니다.
- `dars`: 위 contract를 compile하고 package한 code를 포함합니다.
- `demo`: interactive Canton demo 실행에 필요한 모든 항목을 포함합니다.
- `examples`: Canton console의 sample configuration과 script file을 포함합니다.
- `lib`: Canton 실행에 필요한 Java executable(JAR)을 포함합니다.

이 tutorial은 Unix 계열 shell을 사용한다고 가정합니다.

## Canton 시작

Canton은 production 용도의 daemon mode를 지원하지만, 이 tutorial에서는 내장 interactive read-evaluate-print loop(REPL)인 console을 사용합니다. REPL은 모든 Canton 기능을 바로 사용할 수 있는 interface를 제공합니다. 또한 [Ammonite](https://ammonite.io/) 기반이므로 새로운 script로 확장해야 할 때 Scala의 모든 기능을 사용할 수 있습니다. 따라서 console에는 유효한 모든 Scala expression을 입력할 수 있습니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantTutorialsGettingStarted0 />

Shell에서 Canton을 압축 해제한 directory로 이동한 뒤 다음을 실행합니다.

```bash
bin/canton --help
```

Canton이 지원하는 command line option을 확인할 수 있습니다. `bin/canton` 대신 `java -jar lib/canton-*.jar`로 Canton을 직접 시작할 수도 있습니다. 이 경우 다른 jar dependency도 모두 `lib` folder에 있어야 합니다.

다음으로 아래 command를 실행합니다.

```bash
bin/canton -c examples/01-simple-topology/simple-topology.conf
```

## Example topology

Canton의 기본 element를 이해하기 위해 이 초기 configuration을 간단히 살펴보겠습니다. 아래와 같이 [HOCON](https://github.com/lightbend/config/blob/master/HOCON.md) format으로 작성되어 있습니다. Local alias가 `participant1`, `participant2`인 두 *participant node*와 local alias가 `mysynchronizer`인 하나의 *synchronizer*를 실행하도록 지정합니다. 또한 각 node가 사용할 storage backend와 여러 service의 network port를 지정합니다. 이 tutorial에서는 in-memory storage를 사용하며, 각 service는 곧 설명합니다.

<ExternalCantonMainCommunitySrcExampleSimpleTopology />

Protocol을 실행하려면 participant가 하나 이상의 synchronizer에 연결되어야 합니다. 여러 party가 공유하는 contract를 update하는 변경인 *transaction*을 실행하려면 모든 party의 participant node가 같은 synchronizer에 연결되어야 합니다. 이 tutorial의 나머지 부분에서는 아래와 같이 Alice, Bob, Bank 세 party가 서로 transact할 수 있는 network topology를 구성합니다.

![images/canton-tutorial-elements.svg](./images/canton-tutorial-elements.svg)

Participant Node는 party가 ledger에 접근할 수 있도록 [gRPC Ledger API](/sdks-tools/api-reference/ledger-api)를 제공합니다. Party는 console을 사용해 gRPC Ledger API와 수동으로 interact할 수 있지만, 실제로는 application이 interaction을 처리하고 사용자 친화적인 interface로 data를 표시합니다.

각 participant node는 gRPC Ledger API 외에도 *Admin API*를 노출합니다. Admin API를 사용하면 administrator인 사용자가 다음 작업을 수행할 수 있습니다.

- participant node와 synchronizer 사이의 connection 관리
- participant node가 host할 party 추가 또는 제거
- 새로운 Daml archive upload
- cryptographic key와 같은 participant operational data 설정
- diagnostic command 실행

Synchronizer는 participant node가 synchronization synchronizer와 통신하는 데 사용하는 *Public API*를 노출합니다. Participant node가 host된 위치에서 이 API에 접근할 수 있어야 합니다.

Participant node와 마찬가지로 synchronizer도 administration service를 위한 Admin API를 노출합니다. 예를 들어 key를 관리하고 synchronizer parameter를 설정하며 synchronizer 내 participant node를 활성화 또는 비활성화할 수 있습니다. Console은 설정된 participant와 synchronizer의 Admin API에 대한 접근을 제공합니다.

<Note>
Canton의 Admin API와 gRPC Ledger API의 `admin` package를 혼동하면 안 됩니다. Ledger API의 `admin` package는 *모든 Daml participant*에서 party와 package를 관리하는 service를 제공합니다. Canton Admin API는 *Canton 기반 node*를 관리하는 데 사용합니다. `participant` node와 `synchronizer`는 일부 기능이 겹치는 Admin API를 각각 노출합니다.
</Note>

또한 participant node와 synchronizer는 Public API를 통해 서로 통신합니다. Participant는 서로 직접 통신하지 않지만 원하는 만큼 많은 synchronizer에 연결할 수 있습니다.

Configuration에는 `participant1`과 `participant2`를 `mysynchronizer`에 연결하라는 설정이 없습니다. Canton connection은 static하게 설정하지 않고 dynamic하게 추가합니다. 먼저 participant를 synchronizer에 연결해 보겠습니다.

모든 설정이 올바르면 두 participant의 Ledger API 사이 "roundtrip time"이 보고됩니다. 첫 시도에는 JVM warm-up으로 몇 초가 걸릴 수 있습니다. 다음 시도에서는 크게 줄고 JVM just-in-time compilation이 동작한 후에는 다시 줄어듭니다. 기본적으로 이는 10,000회 iteration 후에 발생합니다.

방금 Canton에서 첫 smart contract transaction을 실행했습니다. 모든 participant node에는 smart contract interaction에 참여할 수 있는 내장 party가 연결되어 있습니다. `ping` command는 모든 Canton participant에 기본으로 사전 설치된 특정 smart contract를 사용합니다. 이 command는 Admin API로 사전 설치된 application에 접근하고, application은 이 smart contract를 조작하는 Ledger API command를 실행합니다.

이론적으로는 application의 모든 smart contract interaction에 participant node의 내장 party를 사용할 수 있지만, participant보다 더 많은 party가 필요한 경우가 많습니다. 예를 들어 회사 내에서 participant node 하나를 실행하고 각 직원을 별도의 party로 둘 수 있습니다. 이를 위해 party를 provisioning할 수 있어야 합니다.

## Canton Identity와 Party Provisioning

Canton에서는 각 party, node(participant, sequencer 또는 mediator), synchronizer의 identity를 *unique identifier*로 나타냅니다. Unique identifier는 사람이 읽을 수 있는 string과 public key의 fingerprint라는 두 component로 구성됩니다. Canton에 표시될 때 두 component는 double colon으로 구분됩니다. Console에서 다음을 실행하면 여러 node의 identifier를 확인할 수 있습니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantTutorialsGettingStarted11 />

Synchronizer identifier는 sequencer node에서 가져올 수 있습니다.

<ExternalCantonMainDocsOpenTargetSnippetJsonDataParticipantTutorialsGettingStarted12 />

이 unique identifier에서 사람이 읽을 수 있는 string은 기본적으로 local alias에서 파생되지만 원하는 string으로 설정할 수 있습니다. *Namespace*라고 부르는 public key는 이 identifier의 root of trust입니다. 즉 Canton에서 이 identity의 이름으로 수행하는 모든 action은 다음 중 하나여야 합니다.

- 이 namespace key로 서명하거나
- namespace key가 이 identity의 이름으로 직접 또는 간접적으로 발언하도록 authorize한 key로 서명해야 합니다. 예를 들어 `k1`이 `k2`의 이름으로, `k2`가 `k3`의 이름으로 발언할 수 있다면 `k1`도 `k3`의 이름으로 발언할 수 있습니다.

Canton에서는 여러 unique identifier가 같은 namespace를 공유할 수 있으며 곧 그 예를 확인합니다. 그러나 직전 console command 결과의 identity를 보면 서로 다른 namespace에 속합니다. 기본적으로 각 Canton node는 처음 시작할 때 자체 namespace를 위한 새로운 asymmetric key pair(secret key와 public key)를 생성합니다. 이후 key를 storage에 저장하며 storage가 persistent하면 재사용합니다. `simple-topology.conf`는 persistent하지 않은 memory storage를 사용한다는 점을 기억하세요.

<Note>
Canton은 Daml contract와 interact할 때 발생하는 대부분의 synchronization 문제를 완화합니다. 하지만 Canton은 concurrent distributed system이며 모든 operation은 asynchronous하게 발생합니다. `Bank` party 생성은 `participant2`의 local operation이고 `mysynchronizer`는 지연 후에 이 party를 인식합니다. 자세한 내용은 Topology Transactions를 참조하세요. 여러 node에 영향을 주는 다른 모든 operation에도 processing 및 network delay가 있지만, 모두가 synchronizer의 operation을 같은 순서로 확인합니다. Command를 interactive하게 실행할 때는 일반적으로 지연을 인식하기 어렵습니다. 그러나 여러 node와 통신하는 Canton script나 application을 작성한다면 manual synchronization이 필요할 수 있습니다. 대부분의 Canton console command는 편의를 위한 synchronization 기능을 제공하며, 때로는 `utils.retry_until_true(...)`가 유용합니다.
</Note>

이 예제에서 사용할 Daml contract는 다음과 같습니다.

``` none
module Iou where

import Daml.Script

data Amount = Amount {value: Decimal; currency: Text} deriving (Eq, Ord, Show)

amountAsText (amount : Amount) : Text = show amount.value <> amount.currency

template Iou
  with
    payer: Party
    owner: Party
    amount: Amount
    viewers: [Party]
  where

    ensure (amount.value >= 0.0)

    signatory payer
    observer owner
    observer viewers

    choice Call : ContractId GetCash
      controller owner
      do
        create GetCash with payer; owner; amount

    choice Transfer : ContractId Iou
      with
        newOwner: Party
      controller owner
      do
        create this with owner = newOwner; viewers = []

    choice Share : ContractId Iou
      with
        viewer : Party
      controller owner
        do
          create this with viewers = (viewer :: viewers)
```

Canton의 privacy 기능은 하나의 atomic transaction 내에서도 모든 참여자가 서로를 알지 못할 정도로 적용됩니다. 이를 Canton synchronization protocol 고유의 특성인 *sub-transaction privacy*라고 부릅니다. Protocol은 자격이 있는 participant만 data를 받도록 보장합니다. 또한 `mysynchronizer`를 실행하는 node가 이 data를 받기는 하지만 data가 encryption되어 있어 `mysynchronizer`는 읽을 수 없습니다.

제안을 accept하면 Bank가 Paint 합의를 알지 못한 상태에서 Bank IOU가 transfer됩니다. 이 방식으로 sub-transaction privacy가 적용된 단계를 실행할 수 있습니다.

## Bootstrap Script를 사용한 Automation

Canton을 시작할 때마다 node 시작이나 party provisioning 같은 반복 작업을 수동으로 수행하지 않도록 bootstrap script를 설정할 수 있습니다. Bootstrap script는 Canton이 시작된 후 자동으로 실행되며 유효한 Canton Console command를 포함할 수 있습니다. Canton 시작 시 `--bootstrap` CLI argument로 bootstrap script를 전달합니다. 관례상 `.canton` file extension을 사용합니다.

예를 들어 participant node를 local synchronizer에 연결하고 participant2에서 participant1로 ping하는 bootstrap script는 다음과 같습니다. Starting and Connecting The Nodes를 참조하세요.

``` none
// start all local instances defined in the configuration file
nodes.local.start()

// Bootstrap the synchronizer
bootstrap.synchronizer_local()

// Connect participant1 to da using the connect macro.
// The connect macro will inspect the synchronizer configuration to find the correct URL and Port.
// The macro is convenient for local testing, but obviously doesn't work in a distributed setup.
participant1.synchronizers.connect_local(sequencer1, alias = "da")

val daPort = Option(System.getProperty("canton-examples.da-port")).getOrElse("5001")

// Connect participant2 to da using just the target URL and a local name we use to refer to this particular
// connection. This is actually everything Canton requires and this second type of connect call can be used
// in order to connect to a remote Canton synchronizer.
//
// The connect call is just a wrapper that invokes the `synchronizers.register`, `synchronizers.get_agreement` and `synchronizers.accept_agreement` calls.
//
// The address can be either HTTP or HTTPS. From a security perspective, we do assume that we either trust TLS to
// initially introduce the synchronizer. If we don't trust TLS for that, we can also optionally include a so called
// EssentialState that establishes the trust of the participant to the synchronizer.
// Whether a synchronizer will let a participant connect or not is at the discretion of the synchronizer and can be configured
// there. While Canton establishes the connection, we perform a handshake, exchanging keys, authorizing the connection
// and verifying version compatibility.
participant2.synchronizers.connect("da", s"http://localhost:$daPort")

// The above connect operation is asynchronous. It is generally at the discretion of the synchronizer
// to decide if a participant can join and when. Therefore, we need to asynchronously wait here
// until the participant observes its activation on the synchronizer. As the synchronizer is configured to be
// permissionless in this example, the approval will be granted immediately.
utils.retry_until_true {
    participant2.synchronizers.active("da")
}

participant2.health.ping(participant1)
```

Participant1에 ping하기 전에 participant2가 register되었는지 확인하도록 `retry_until_true`를 다시 사용해 manual synchronization point를 추가한 점에 유의하세요.

## Hardware Resource

Test, staging, production environment의 각 Canton node에는 충분한 hardware resource가 필요합니다. 처음에는 여유 있게 provisioning한 system으로 시작하는 것을 권장합니다. 장시간 performance benchmark로 application의 NFR을 충족하는지 입증한 후에는 available resource를 줄여볼 수 있습니다. 예를 들면 application request latency와 PQS query response time을 확인합니다. Resource를 줄인 뒤 benchmark를 다시 실행해 NFR이 계속 충족되는지 검증해야 합니다. 반대로 NFR을 충족하지 못하면 available resource를 늘려야 합니다.

시작점으로 권장하는 최소 resource는 다음과 같습니다.

- Physical host, virtual machine 또는 container에 RAM 6GB와 CPU core 4개 이상
- JVM에 RAM 4GB 이상

또한 `-XX:+UseG1GC`를 추가하면 JVM이 `G1` garbage collector를 사용하도록 강제할 수 있습니다. 경험상 resource가 부족하면 JVM이 다른 garbage collector를 사용해 latency가 길어질 수 있습니다.

## Topology

먼저 어떤 topology를 구축할지 결정해야 합니다. Canton topology는 다음 그림과 같이 party, participant, synchronizer로 구성됩니다.

![../images/topology.png](../images/topology.png)

Daml code는 participant node에서 실행되며 party 사이 smart contract를 표현합니다. Party는 participant node에 host됩니다. Participant node는 synchronizer를 통해 message를 교환하며 다른 participant node와 state를 synchronize합니다. Synchronizer는 database나 다른 distributed ledger 같은 기반 storage technology와 integrate되는 node입니다. Canton protocol은 participant node가 서로 신뢰하지 않는다고 가정하므로, scaling 목적을 제외하면 일반적으로 각 organization이 participant node 하나를 실행합니다.

자체 test network를 구축하려면 participant node와 synchronizer가 각각 하나 이상 필요합니다.

다음 지침은 release bundle의 root directory에서 모든 command를 실행한다고 가정합니다.

```bash
cd ./canton-<type>-X.Y.Z
```

## Config Directory 구성

<Warning>
이 section은 release 2.8.1 이상에 적용됩니다.
</Warning>

Config directory에는 node type별 reference configuration file이 있습니다.

``` none
.
└── config
      ├── shared.conf, sandbox.conf, participant.conf, sequencer.conf, mediator.conf
      ├── jwt
      ├── misc
      ├── monitoring
      ├── remote
      ├── storage
      ├── tls
      └── utils
```

- `participant.conf`: participant node configuration
- `sequencer.conf`, `mediator.conf`, `manager.conf`: synchronizer deployment를 위한 sequencer, mediator, manager node configuration
- `sandbox.conf`: test용 in-memory store를 사용하며 participant node 하나를 synchronizer node 하나에 연결하는 간단한 설정

이외에도 다음 file과 directory가 있습니다.

- `shared.conf`: 다른 모든 configuration이 include하는 shared configuration file
- `jwt`: Ledger API의 JWT configuration file
- `misc`: debugging과 development에 유용한 기타 configuration file
- `monitoring`: metrics와 tracing을 활성화하는 configuration file
- `remote`: Canton console을 remote node에 연결하는 configuration file
- `storage`: 여러 storage option의 storage configuration file을 포함하는 directory
- `tls`: 여러 API의 TLS configuration file과 test certificate 생성 script
- `utils`: 주로 database 설정에 사용하는 utility script

## Storage Layer 선택

어떤 node든 실행하려면 data를 persist할지, 어떻게 persist할지 결정해야 합니다. Data를 persist하지 않고 node restart 시 삭제되는 in-memory store를 사용하거나 `Postgres` database로 data를 persist할 수 있습니다.

<Note>
전통적인 deployment configuration에서 여러 Postgres version과 Canton/PQS의 compatibility를 test합니다. Postgres에는 latency, read operation scaling, HA, cost 등 NFR trade-off를 선택할 수 있는 다양한 variant가 있습니다. 모든 variant의 compatibility를 test하지는 않았지만 Canton과 PQS에서 동작할 것으로 예상합니다. 다만 Ledger API와 PQS client의 SLA를 충족하는지 확인하려면 충분한 application test가 필요합니다. 특히 serverless Postgres에는 transient behavior가 있으므로 auto-scaling이 transaction latency에 큰 영향을 주지 않는지 등 application SLA 충족 여부를 검증하는 견고한 application test process가 필요합니다.
</Note>

이를 위해 storage mixin configuration(`config/storage/`)이 정의되어 있습니다.

Storage mixin은 모든 node configuration과 함께 사용할 수 있습니다. 모든 reference example은 `config/shared.conf`를 include하며, 이 file은 기본적으로 `postgres.conf`를 include합니다. 반면 in-memory configuration은 추가 설정 없이 바로 동작하지만 data를 persist하지 않습니다. `config/shared.conf`의 include를 변경할 수 있습니다.

Mixin은 모든 node configuration에서 참조할 수 있는 shared variable을 정의하는 방식으로 동작합니다.

```hocon
storage = ${_shared.storage}
storage.parameters.databaseName = "canton_participant"
```

`Could not resolve substitution to a value: ${_shared.storage}` error가 표시되면 persistence mixin configuration file을 추가하지 않은 것입니다.

<Note>
Storage configuration의 상세 section도 참조하세요.
</Note>

Canton이 database schema를 관리하므로 table이나 index를 생성할 필요가 없습니다.

### Postgres를 사용한 Persistence

In-memory는 test와 demo에 적합하지만 production에서는 database를 persistence layer로 사용해야 합니다. Canton은 [Postgres](https://www.postgresql.org/)를 persistence layer로 지원합니다.

Postgres server가 실행 중인지 확인하고 node마다 database 하나를 생성합니다.

Canton은 [현재 지원되는 Postgres version](https://www.postgresql.org/support/versioning/) 중 일부에서 test됩니다. 특정 Canton release를 test하는 데 사용한 Postgres version은 [Canton release notes](https://github.com/digital-asset/canton/releases)를 참조하세요.

#### Database와 User 생성

`util/postgres`에는 database configuration을 돕고 선택적으로 Docker 기반 Postgres instance를 시작하는 `db.sh` script가 있습니다. [Docker](https://www.docker.com/)가 설치되어 있다면 다음을 실행합니다.

```bash
cd ./config/util/postgres
./db.sh start [durable]
./db.sh setup
```

Environment variable에 connection setting이 없으면 db.sh가 `config/util/postgres/db.env`에서 읽습니다. Script는 non-durable Postgres instance를 시작하며, restart 후에도 data를 유지하려면 `start durable`을 사용합니다. 또한 `config/util/postgres/databases`에 정의된 database를 생성합니다.

그 밖의 유용한 command는 다음과 같습니다.

- `create-user`: `db.env`에 정의된 user 생성
- `resume`: 이전에 중지한 Docker 기반 Postgres instance 재개
- `drop`: 생성된 database 삭제

#### Database Character Encoding

Canton application이 올바르게 동작하려면 Postgres에서 UTF8 database server encoding을 사용해야 합니다. 이렇게 하면 일부 UTF8 character를 database에 저장하지 못하는 character conversion 문제를 방지할 수 있습니다. Server character encoding이 UTF8이 아니면 Canton은 시작 시 ERROR log message를 보고합니다. SQL console(예: psql)로 database에 연결해 [SHOW SERVER_ENCODING;](https://www.postgresql.org/docs/current/sql-show.html)을 실행하면 Postgres database server encoding을 확인할 수 있습니다. Server encoding은 database initialization 중 OS environment에서 추론한 기본값으로 설정되지만 [override](https://www.postgresql.org/docs/current/sql-createdatabase.html#CREATE-DATABASE-ENCODING)할 수 있습니다. 자세한 내용은 [관련 Postgres documentation](https://www.postgresql.org/docs/current/multibyte.html#MULTIBYTE)을 참조하세요.

#### Connectivity 설정

`config/storage/postgres.conf` file을 수정하거나 관련 environment variable을 설정해 connectivity setting을 제공할 수 있습니다. 설정할 variable은 해당 file을 참조하세요.

``` none
export POSTGRES_HOST="localhost"
export POSTGRES_USER="test-user"
export POSTGRES_PASSWORD="test-password"
export POSTGRES_DB=postgres
export POSTGRES_PORT=5432
```

#### Database Tuning

Canton에는 적절한 규모와 올바른 configuration을 갖춘 database가 필요합니다. 자세한 내용은 Postgres performance guide를 참조하세요.

## TLS Certificate 생성

Reference example configuration은 TLS를 사용해 API를 보호합니다. Configuration file은 `config/tls`에 있으며 API별로 구분됩니다.

- `tls-ledger-api.conf`: participant node가 노출하는 Ledger API의 TLS configuration
- `mtls-admin-api.conf`: 모든 node type이 노출하는 Administration API의 TLS configuration
- `tls-public-api.conf`: sequencer와 synchronizer node가 노출하는 Public API의 TLS configuration

Public API의 client authentication은 내장되어 있으며 비활성화할 수 없습니다. Node identity와 연결된 특정 signing key를 사용합니다. Ledger API는 JWT 기반 authentication을 지원하고 Admin API에서는 mTLS를 활성화할 수 있습니다. 자세한 내용은 TLS documentation section을 참조하세요.

간단한 설정으로 시작하려면 제공된 `config/tls/gen-test-certs.sh` script로 self-signed certificate를 생성할 수 있습니다. Certificate에는 node가 bind할 address의 올바른 SAN entry가 포함되어야 합니다.

또는 관련 configuration file에서 TLS include를 comment 처리해 이 단계를 건너뛸 수 있습니다.

## Participant 설정

Reference example `config/participant.conf`를 사용해 participant를 시작합니다.

```bash
./bin/canton [daemon] -c config/participant.conf
```

`daemon` argument는 선택 사항입니다. 생략하면 node가 interactive console과 함께 시작됩니다. Logging configuration을 추가로 tuning하는 등 다양한 command line option을 사용할 수 있습니다.

<Note>
기본적으로 node는 identity command `identity-commands`를 사용해 자동으로 initialize됩니다. 이에 따라 필요한 key와 topology transaction을 생성하고 configuration file의 이름으로 자체 initialize합니다. 자세한 내용은 identity management section을 참조하세요.
</Note>

여기까지가 participant node 시작에 필요한 모든 작업입니다. 하지만 participant를 보호하고 실제로 사용하려면 몇 가지 단계를 더 처리해야 합니다.

### API 보호

1.  기본적으로 Canton의 모든 API는 localhost에서만 접근할 수 있습니다. 다른 machine에서 node에 연결하려면 localhost 대신 `0.0.0.0`에 bind해야 합니다. 관련 API configuration section에서 `address = 0.0.0.0` 또는 원하는 network name으로 설정하세요.
2.  모든 node는 administration API를 통해 관리합니다. Console을 사용할 때 거의 모든 request가 administration API를 통과합니다. TLS documentation section의 설명에 따라 mutual TLS authentication을 설정하는 것을 권장합니다.
3.  Application과 user는 gRPC Ledger API를 사용해 Participant Node와 interact합니다. TLS로 API를 보호하고 JWT token으로 client를 authorize하는 것을 권장합니다. Reference configuration의 `config/jwt`에 있는 configuration file을 시작점으로 사용할 수 있습니다.

### Application, User, Connection 설정

Canton은 static configuration과 dynamic configuration을 구분합니다.

- Static configuration은 변경되지 않는 항목이므로 configuration file에 기록합니다. Bind할 port가 그 예입니다.
- Dynamic configuration은 Daml archive(DAR), synchronizer connection, party 같은 항목입니다. 이러한 변경은 모두 console command 또는 administration API를 통해 적용합니다.

Synchronizer 연결, party onboarding, Daml code provisioning 방법을 모른다면 getting started guide를 참조하세요.

## Synchronizer 설정

이제 participant node는 다른 participant와 연결해 distributed ledger를 구성할 준비가 되었습니다. Connection은 다음 세 process로 구성된 synchronizer가 중개합니다.

- encrypted message ordering을 담당하는 sequencer
- 개별 participant의 validation response 집계를 담당하는 mediator
- topology change, 즉 distributed configuration change가 synchronizer에 배포되기 전에 validity를 검증하는 synchronizer manager

이 node들은 ledger data를 저장하지 않고 participant 사이 통신만 지원합니다.

Synchronizer를 설정하려면 sequencer에 사용할 driver 종류를 결정해야 합니다. 여러 infrastructure type을 위한 driver가 제공되며 trust와 performance 측면에서 서로 다른 fidelity를 가집니다. 현재 선택지는 다음과 같습니다.

1.  Postgres 기반 synchronizer
2.  [Canton Network](https://canton.network/)에서 사용하는 Native Canton BFT driver

이 section에서는 Postgres 기반 synchronization synchronizer 설정 방법을 설명합니다.

### Microservice 사용

Synchronizer process를 별도의 microservice로 시작할 수 있습니다.

```bash
./bin/canton daemon -c config/[mediator|sequencer|manager].conf
```

Node가 함께 동작하려면 먼저 initialize하고 연결해야 합니다. Synchronizer bootstrap 방법은 상세 guide를 참조하세요.

일반적으로 같은 process에서 실행되는 경우 embedded console을, 그렇지 않으면 remote console을 사용해 node를 연결할 수 있습니다.

```bash
./bin/canton -c config/remote/mediator.conf,config/remote/manager.conf,config/remote/sequencer.conf
```

그런 다음 bootstrap command를 실행합니다.

```scala
bootstrap.synchronizer(
  synchronizerName = "da",
  sequencers = sequencers.all,
  mediators = mediators.all,
  synchronizerOwners = Seq(sequencer1),
  synchronizerThreshold = PositiveInt.one,
  staticSynchronizerParameters = StaticSynchronizerParameters.defaultsWithoutKMS(ProtocolVersion.latest),
)
```

#### Participant 연결

마지막 단계는 participant를 synchronizer에 연결하는 것입니다. 자세한 지침은 connectivity guide를 참조하세요. 가장 간단한 경우 participant console에서 다음 command만 실행하면 됩니다.

```scala
participant.synchronizers.connect("da", "https://localhost:10018", certificatesPath = "config/tls/root-ca.crt")
```

Self-signed test certificate는 기본적으로 신뢰되지 않으므로 certificate를 명시적으로 제공합니다.

### API 보호

1.  Participant node와 마찬가지로 모든 API는 기본적으로 localhost에 bind됩니다. 다른 machine에서 node에 연결하려면 올바른 interface 또는 `0.0.0.0`에 bind해야 합니다.
2.  Administration API는 TLS documentation section의 설명에 따라 client certificate로 보호해야 합니다.
3.  Public API는 TLS로 적절히 보호해야 합니다. 관련 지침을 따르세요.

## Multi-node 설정

원한다면 같은 process에서 여러 node를 실행할 수 있습니다. Test와 demonstration에 편리합니다. 같은 configuration file에 여러 node configuration을 나열하거나, merge되는 여러 configuration file을 지정해 Canton process를 실행할 수 있습니다.

```bash
./bin/canton -c config/participant.conf -c config/sequencer.conf,config/mediator.conf -c config/manager.conf
```
