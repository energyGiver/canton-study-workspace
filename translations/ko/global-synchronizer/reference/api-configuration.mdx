# API Configuration

Participant node는 Admin API, gRPC Ledger API 및 선택적으로 JSON Ledger API를 노출합니다.

이 페이지에서는 Admin API와 gRPC Ledger API 모두에 적용되는 일반 option의 구성 방법을 설명합니다. 특정 API에만 적용되는 configuration option은 Administration API, gRPC Ledger API 및 JSON Ledger API 페이지를 참조하세요.

## Port

Admin API, gRPC Ledger API 및 JSON Ledger API의 port는 명시적으로 제공해야 합니다.

``` none
participant1 {
  storage.type = memory
  admin-api.port = 5012
  ledger-api.port = 5011
  http-ledger-api.port = 5013
}
```

JSON Ledger API가 비활성화된 경우 port를 제공할 필요가 없습니다.

``` none
participant3 {
  ledger-api.port = 13031
  admin-api.port = 13032
  http-ledger-api.enabled = false
  storage.type = memory
}
```

## Keep Alive

Canton은 connection에 잠시 traffic이 없을 때 load balancer 또는 firewall이 장시간 실행되는 RPC call을 종료하지 않도록 모든 gRPC connection에서 keep-alive를 기본적으로 활성화합니다.

Connection의 keep-alive configuration을 조정하려면 다음 parameter를 변경합니다.

- `time`
- `timeout`
- `permit-keep-alive-time`
- `permit-keep-alive-without-calls`

처음 두 parameter는 `keep-alive-client` section의 Synchronizer Public API client에 대해 조정하거나 `keep-alive-server` section의 Admin API 및 gRPC Ledger API server 측에 대해 조정할 수 있습니다. 마지막 두 parameter는 server 전용이므로 Admin API 및 gRPC Ledger API의 `keep-alive-server` section에서만 조정할 수 있습니다.

이 parameter와 효과에 대해서는 gRPC [문서]()에서 더 자세히 설명합니다.

<Note>
`permit-keep-alive-time`은 client가 사용할 수 있도록 허용되는 가장 aggressive한 keep-alive time을 지정합니다. Client가 server의 `permit-keep-alive-time`보다 더 aggressive한 keep-alive `time`을 사용하면 debug data가 “too_many_pings”인 `GOAWAY` error와 함께 connection이 종료됩니다.
</Note>

<Note>
`permit-keep-alive-without-calls`를 `true`로 설정하면 진행 중인 gRPC call이 없을 때도 client가 ping message를 보낼 수 있습니다. 그렇지 않으면 이러한 ping으로 `GOAWAY` error가 발생합니다.
</Note>

Canton은 API에 따라 이 parameter의 기본값을 다르게 설정합니다.

| API                             | Admin API | Ledger API |
|---------------------------------|-----------|------------|
| time                            | 40s       | 10min      |
| timeout                         | 20s       | 20s        |
| permit-keep-alive-time          | 20s       | 10s        |
| permit-keep-alive-without-calls | false     | false      |

다음 예는 여러 API의 keep-alive 구성 방법을 보여 줍니다.

``` none
sequencer-client {
    keep-alive-client {
        time = 60s
        timeout = 30s
    }
}

admin-api {
    keep-alive-server {
        time = 40s
        timeout = 20s
        permit-keep-alive-time = 20s
    }
}

ledger-api {
    keep-alive-server {
        time = 40s
        timeout = 20s
        permit-keep-alive-time = 20s
        permit-keep-alive-without-calls = true
    }
}
```

## Netty의 native library 사용

Canton은 Netty network access library가 Linux의 `epoll` system [call]()을 활용할 수 있도록 일부 processor architecture(x86_64, ARM64, S390_64)를 위한 native library와 함께 제공됩니다. 일반적으로 performance가 향상되고 JVM garbage collector의 부담이 줄어듭니다.

System은 현재 operating system 및 architecture에 사용 가능한 native library가 있으면 자동으로 선택하고, 사용할 수 없으면 표준 NIO library로 fallback합니다.

Native library 사용을 끄려면 Canton을 실행할 때 다음을 설정합니다.

``` text
-Dio.grpc.netty.shaded.io.netty.transport.noNative=true
```

예상된 동작인 경우에도 NIO로 fallback하면 log의 `DEBUG` level에서 warning이 출력될 수 있습니다.

# Admin API Configuration

## Administration API

Participant node의 Admin API와 synchronizer의 Admin API는 성격과 범위가 일부 겹칩니다. 예를 들어 synchronizer와 participant node API 모두에서 동일한 key management command를 찾을 수 있지만 participant에는 여러 synchronizer에 연결하기 위한 다른 command가 있습니다.

Configuration은 현재 단순하며, 아래 TLS example을 참조할 수 있습니다. 구체적으로 address와 port를 받습니다. Address의 기본값은 `127.0.0.1`이며 명시적으로 구성하지 않으면 기본 port가 할당됩니다.

Admin-api는 administrative purpose로만 사용되므로 안전하지 않은 방식으로 공개 노출해서는 안 됩니다.

# gRPC Ledger API Configuration

gRPC Ledger API configuration은 group이 `admin-api`가 아닌 `ledger-api`로 시작한다는 점을 제외하면 Admin API configuration과 유사합니다.

``` none
canton {
  participants {
    participant {
      ledger-api {
        port = 5011
        address = localhost
        auth-services = [{
          type = jwt-jwks
          url = "https://target.audience.url/jwks.json"
          target-audience = "https://rewrite.target.audience.url"
        }]
        jwt-timestamp-leeway {
          default = 5
          expires-at = 10
          issued-at = 15
          not-before = 20
        }
        keep-alive-server {
          time = 40s
          timeout = 20s
          permit-keep-alive-time = 20s
        }
        max-inbound-message-size = 20971520
      }
    }
  }
}
```

gRPC Ledger API connectivity를 구성하려면 **address**와 **port**를 지정해야 합니다. 다른 모든 attribute는 선택 사항이며 직관적인 기본값을 갖습니다.

- TLS를 구성하려면 **tls** parameter group 정의
- JWT authorization을 구성하려면 **auth-services** parameter group 정의
- JWT leeway를 구성하려면 **jwt-timestamp-leeway** parameter group 정의
- gRPC keepalive를 구성하려면 **keep-alive-server** parameter group 정의
- gRPC message의 최대 크기를 제어하려면 **max-inbound-message-size** parameter 정의

## Ledger API Cache

`max-contract-state-cache-size`와 `max-contract-key-state-cache-size` parameter는 각각 Ledger API contract cache 및 contract key cache 크기를 제어합니다. 이 parameter를 수정하면 최근에 접근, 생성 또는 read된 contract나 contract key를 사용하는 transaction이 database를 query하지 않고 memory에서 찾을 가능성이 달라집니다. Consistently fetch되거나 non-consuming exercise에 사용되는 많은 ambient contract pool이 있다면 더 큰 cache가 유용할 수 있습니다. 많은 contract pool이 create -\> archive -\> create-successor cycle을 반복하는 use case도 더 큰 cache의 이점을 얻을 수 있습니다. 특정 workflow의 performance가 큰 cache에 의존한다면 이 parameter를 명시적으로 조정하는 것을 고려하세요.

## In-Memory Fan-Out의 최대 Transaction 수

`max-transactions-in-memory-fan-out-buffer-size` parameter는 in-memory fan-out buffer 크기를 제어합니다. 이 buffer는 transaction stream이 finalize될 때 database가 아닌 memory에서 제공할 수 있게 합니다. Application이 database에서 transaction을 stream해야 할 가능성을 줄이도록 buffer가 충분히 큰지 확인하세요. 대부분의 경우 10초 buffer가 잘 작동합니다. 예를 들어 예상 throughput이 20 tx/s라면 이 값을 200으로 설정합니다. 새로운 기본 setting 1000은 100 tx/s를 가정합니다. Workflow의 performance가 100 tx/s보다 큰 transaction rate를 예상한다면 이 parameter를 명시적으로 조정하는 것을 고려하세요.

``` none
canton.participants.participant.ledger-api.index-service {
    max-transactions-in-memory-fan-out-buffer-size = 10000 // default 1000
}
```

# JSON Ledger API Configuration

JSON Ledger API configuration은 gRPC Ledger API configuration과 유사합니다. 대응하는 parameter group은 `http-ledger-api`로 시작합니다.

``` none
canton {
  participants {
    participant1 {
      http-ledger-api {
        enabled = true
        address = 0.0.0.0
        port = 10010
        port-file = "./json.port"
        path-prefix = "my-prefix"
        websocket-config {
            http-list-max-elements-limit = 1000,
            http-list-wait-time = 2s,
        }
        daml-definitions-service-enabled = true
      }
    }
  }
}
```

JSON Ledger API는 기본적으로 활성화됩니다. 비활성화하려면 `enabled` field를 `false`로 설정합니다.

## JSON Ledger API Endpoint

`server` parameter group을 추가하여 JSON API endpoint를 구성합니다.

- Listen할 IP address를 나타내도록 `address`를 지정합니다.
- Port를 나타내도록 `port`를 지정합니다.
- Participant Node가 JSON Ledger API가 listen 중인 port를 text file에 쓰도록 하려면 `port-file`을 지정합니다. Participant Node는 JSON Ledger API가 완전히 initialize된 뒤에만 file을 작성하므로 dependent service startup을 동기화하는 tool로 유용합니다.
- JSON Ledger API content를 `/` 대신 사용자 지정 path에서 제공하려면 `path-prefix`를 지정합니다.

## Websocket

큰 data set을 생성하는 endpoint(`/v2/commands/completions`, `/v2/state/active-contracts`, `/v2/updates`)는 두 가지 형태로 제공됩니다.

- 임의 길이의 result set을 stream으로 반환할 수 있는 websocket
- 제한된 result list를 반환하는 HTTP post request

두 번째 request type은 Participant Node config에서 parameterize할 수 있습니다.

- 반환되는 최대 row 수를 지정하려면 `http-list-max-elements-limit`을 설정합니다.
- Result를 보내기 전에 기다릴 idle time의 millisecond 수를 지정하려면 `http-list-wait-time`을 설정합니다. 이 parameter는 completion처럼 끝이 열려 있는 stream에 필요합니다. JSON Ledger API는 gRPC stream에서 읽으며 "wait" millisecond 동안 새 element가 없으면 -\> result가 client로 전송됩니다.

## Daml definitions service

`daml-definitions-service-enabled` parameter를 `true`로 설정하여 experimental `Daml Definitions Service`를 활성화할 수 있습니다.
