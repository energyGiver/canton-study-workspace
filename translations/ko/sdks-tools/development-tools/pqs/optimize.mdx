## Query 최적화

{/* COPIED_START source="docs-website:docs/replicated/pqs/3.4/component-howtos/pqs/optimize/index.rst" hash="8f5951c7" */}

예상 workload에 맞게 적절한 resource capacity planning을 수행해야 합니다.

## Host infrastructure

다음은 모든 production workload를 실행하는 host operating system의 최소 요구 사항이며, 특정 workload에 필요한 적절한 resource를 결정하는 출발점으로 봐야 합니다.

PQS host:

- Memory: 4 GB
- CPU: 4 cores

PostgreSQL:

- Memory: 8 GB
- CPU: 8 cores

### 의도적인 PostgreSQL tuning의 중요성

Traffic 형태와 사용 pattern 등을 모르면 client의 요구 사항을 예측하기 어렵습니다.

Active ACS가 큰 read scenario에서 PQS data를 많이 사용한다면 PostgreSQL의 cache capability를 극대화하도록 사용 가능한 RAM을 늘리는 것이 좋습니다.

CPU core 수는 최대 connection 수와 밀접하게 연관됩니다. Query 실행의 parallelism이 커지면 더 많은 동시 connection과 CPU가 필요합니다.

OLAP형 query, 즉 많은 aggregation과 큰 result set을 사용하는 여러 join 같은 **reporting-style** query를 실행하면 일반적인 OLTP형 workload에서는 불필요한 추가 resource가 필요할 수 있습니다. 실제로는 오래 실행되는 query가 동시에 있을 때 process scheduling을 피하도록 CPU 수를 최대 connection 수에 맞춰야 한다는 의미입니다.

PostgreSQL Docker image는 기본적으로 현대의 일반적인 scenario에는 부적절한 Raspberry Pi의 HDD 사용을 가정하는 등 tuning되지 않은 설정으로 제공됩니다. 실행 hardware에 맞춰 PostgreSQL을 적극적으로 tuning해야 합니다.

출발점으로 online calculator[^1]를 사용해 hardware parameter와 PostgreSQL startup setting을 연계하세요.

Docker container environment에서는 다음과 같이 configuration parameter를 startup argument로 전달합니다.

```yaml
services:
  postgres:
    command:
      - postgres
      - -c
      - max_connections=100
      - -c
      - shared_buffers=1GB
      - -c
      - effective_cache_size=3GB # and so on
```

AWS Aurora에는 provision된 기반 cloud resource를 고려한 합리적인 default가 미리 설정되어 있지만[^2], 아래 query나 Aurora management UI로 비정상적인 override가 없는지 확인합니다.

```sql
select name, setting, source from pg_settings;
```

### PQS를 AWS Aurora와 함께 실행할 수 있는가

PQS와 Aurora 모두 default setting을 사용한다면 AWS Aurora Serverful을 datastore로 사용하는 PQS가 production environment에서 예상 parameter 범위 안에서 동작한다는 것이 입증되었습니다.

AWS Aurora Serverless는 아직 test되지 않았습니다.

## Java Virtual Machine configuration

PQS가 효율적으로 실행될 충분한 resource를 확보하려면 적절한 JVM configuration이 중요합니다. 실제 deployment에서는 최소한 다음을 고려해야 합니다.

``` text
-XX:+AlwaysPreTouch
-XX:-UseAdaptiveSizePolicy

## containers:
-XX:InitialRAMPercentage=75.0
-XX:MaxRAMPercentage=75.0

## host/vm:
-Xms4g
-Xmx4g
```

Resource가 제한된 scenario에서는 out-of-memory error가 발생할 수 있습니다. 이를 진단하려면 다음 JVM parameter를 추가해 분석용 heap dump를 수집해야 합니다.

``` text
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/path/to/heap.dump
```

## PostgreSQL configuration

예상 workload 처리와 관련된 다음 PostgreSQL configuration item을 최소한 고려해야 합니다. `postgresql.conf`[^3]를 참조하세요.

- `autovacuum_*`[^4]
- `maintenance_work_mem`[^5]
- `checkpoint_*`[^6]
- `*_wal_size`[^7]
- `bgwriter_*`[^8]

높은 성능이 필요하면 Database Administrator가 목표 workload와 infrastructure에 맞춰 PostgreSQL을 tuning하고 simulated workload에서 system을 실행하면서 configuration을 반복 조정해야 합니다.

## Host environment

Daml Package를 임시 cache하기 위해 PQS에는 local cache directory에 대한 write access가 필요합니다. `--source-ledger-cachedir`로 설정하며 default는 `/tmp/scribe`입니다. Cache 크기는 Ledger에서 관찰할 수 있는 모든 Daml Package 크기에 비례합니다. 단일 실행 이후 유지할 필요가 없는 ephemeral cache입니다. 전체 성능에 중요하지 않으므로 container environment에서는 disk 기반 mount를 설정해야 합니다.

## Processing pipeline configuration

진단을 위해 더 상세한 logging이 필요하면 `--logger-level` parameter를 `DEBUG` 또는 `TRACE`로 조정할 수 있습니다. 다만 log output이 매우 많아지고 성능에 악영향을 줄 수 있습니다. 따라서 Netty처럼 특히 많은 log를 출력하는 component는 `INFO` level로 낮추는 것이 좋습니다. `pqs-logging`을 참조하세요.

Ledger API queue 길이 설정은 memory 사용량과 성능의 trade-off입니다. Default는 128이며 추가 memory를 사용하는 대신 더 안정적인 성능을 위해 늘릴 수 있습니다. Buffer는 buffer 크기의 rolling window에 있는 transaction 크기와 같은 양의 memory를 사용합니다.

``` text
--source-ledger-buffersize 1024
```

예상 workload에 따라 PQS가 사용하는 JDBC connection 수, default 16을 늘려야 할 수 있습니다. 다음과 같이 제어합니다.

``` text
--target-postgres-maxconnections 64
```

PostgreSQL의 `max_connections`[^9] parameter는 database의 모든 client가 요청하는 connection 총수 이상으로 설정해야 합니다.

## Query 분석

이 section은 PostgreSQL capability를 최대한 활용하기 위한 PQS database 최적화를 간략히 설명합니다. 범위가 넓고 참고할 resource가 많으므로 자세한 내용은 PostgreSQL documentation을 참조하세요.

PQS는 Ledger data 저장에 JSONB column을 광범위하게 사용합니다. Query를 최적화하려면 JSONB를 잘 알아야 합니다.

Query 수행 방식을 설명받으려면 query text 앞에 `explain analyze`를 붙입니다. Query가 예상한 index를 사용해 의도대로 실행되는지 확인하는 데 도움이 됩니다.

```sql
explain analyze
select * from active('MyModule:MyTemplate');
```

Query planner output 해석 방법은 article series[^10]를 참조하고 visualization에는 online tool[^11]을 사용하세요.

## Indexing

Index는 JSONB content query 성능을 높이는 중요한 tool입니다. 추가 read 효율이 불가피한 write amplification을 정당화한다면 user가 model 전용 query 최적화를 위해 JSONB 기반 index를 생성해야 합니다. 다음 helper function으로 간단한 index를 생성할 수 있습니다.

```sql
call create_index_for_contract('token_wallet_holder_idx',
                               'register:DA.Register:Token',
                               '(payload->''wallet''->>''holder'')',
                               'hash');
```

이 예시에서 index는 Wallet Holder 비교를 허용합니다. JSON inspection 결과가 cache/materialize되어 access할 때마다 다시 계산할 필요가 없다는 추가 장점도 있습니다.

PostgreSQL은 여러 index type을 제공합니다. 각 type은 서로 다른 query 유형에 적합한 algorithm을 사용합니다. 다음 표는 사용 위치를 기본적으로 설명합니다. 자세한 내용은 PostgreSQL manual의 index chapter[^12]를 참조하세요.

| Index Type | 설명                                                                                                                                                                                                                                                                                                                              |
|------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Hash       | Compact합니다. `=`를 사용하는 filter에만 유용합니다.                                                                                                                                                                                                                                                                              |
| B-tree     | `<`, `<=`, `=`, `>=`, `>`를 사용하는 filter와 `like 'foo%'` 같은 prefix string 비교에 사용할 수 있습니다. `order by` clause의 속도를 높이고, 예를 들어 `select` clause에서 subexpression을 평가하는 대신 index에서 그 값을 가져오는 데도 사용할 수 있습니다.                                                               |
| GIN        | Subset operator에 유용합니다.                                                                                                                                                                                                                                                                                                     |
| BRIN       | 특정 column 기준으로 row가 이미 물리적으로 정렬된 table에 효율적입니다.                                                                                                                                                                                                                                                           |

표준 PostgreSQL syntax로 더 정교한 index를 생성할 수 있습니다.

## Payload query

이 page는 Participant Query Store, PQS에서 payload content를 다루는 query를 최적화할 때의 기법과 고려 사항을 설명합니다.

다음 page를 사전 지식으로 이미 이해했다고 가정합니다.

- `pqs-how-to-query-contracts-and-transactions-using-sql`
- `pqs-references-sql-api`

### Metadata index

PQS data retrieval function에는 특정 Ledger offset에서 생성된 Contract query나 Contract ID로 Contract 찾기 같은 metadata level query에 효율적으로 access하기 위한 index가 이미 있습니다. 하지만 대부분의 business workflow level query는 실제 Contract payload content를 기준으로 data를 선택해야 합니다. 효율적인 query는 Daml model 세부 구조를 알아야 하므로 PQS default index는 여기에 도움이 되지 않습니다. 즉 각 application team이 data access pattern에 맞는 최적의 성능을 확보하도록 적절한 index를 생성하고 유지할 책임이 있습니다.

### 필요한 tool

PostgreSQL의 `psql`[^1] application과 `EXPLAIN`[^2] SQL command로 query plan을 분석하고 잠재적 성능 bottleneck을 바로잡습니다. 이 tool에 대한 자세한 내용은 page 끝의 reference를 참조하세요.

### Daml model

이 page에서는 Issuer가 생성하고 Holder가 보유한 Token register를 나타내는 단순한 Daml model을 사용합니다. 실제 workflow는 논의와 관련이 없어 전체를 제공하지 않지만, `Token` model이 대응하는 `JSONB` payload 표현으로 변환되는 방식을 보는 것이 유용합니다.

```daml
module DA.Register where

-- basic types
type Quantity = Decimal

data Issue = Issue
  with
    issuer: Party
    label: Text
  deriving (Ord, Eq, Show)

data Wallet = Wallet
  with
    holder: Party
    label: Text
    locks: Set Lock
  deriving (Ord, Eq, Show)

walletSigs w = S.fromList $ w.holder :: map (.notary) (S.toList w.locks)

data Lock = Lock
  with
    notary: Party
    label: Text
  deriving (Ord, Eq, Show)

-- token representing a number of units issued and held in a wallet
template Token
  with
    issue: Issue          -- what
    wallet: Wallet        -- where
    quantity: Quantity    -- how many
    observers: Set Party
  where
    signatory issue.issuer, walletSigs wallet
    ensure quantity /= 0.0
    observer observers
```

PQS가 ingest한 대표적인 Contract는 다음과 같습니다.

        "label": "security:by-issuer-6::1220417ac1a340579278093905c1bdcac152f04d50dbd899ca6ac24740f37a9c534d",
        "issuer": "issuer-6::1220417ac1a340579278093905c1bdcac152f04d50dbd899ca6ac24740f37a9c534d"
    },
    "wallet": {
        "label": "treasury for security:by-holder-82::1220417ac1a340579278093905c1bdcac152f04d50dbd899ca6ac24740f37a9c534d",

### Payload index

### 현재 상태, custom index 없음

이 plan에서 다음 정보를 파악할 수 있습니다.

- `Index Scan`을 사용하지만 default metadata level index 같은 범용 index입니다.
- PostgreSQL이 실행을 parallelize할 수 있었습니다. `Workers Launched: 2`
- Query selectivity는 `rows=9`와 `rows=3972`로 다르지만 PostgreSQL이 estimate를 `rows=976`으로 크게 잘못 예측했으므로 최적 실행에 도움이 되지 않았습니다.
- PostgreSQL이 상당한 작업을 수행한 뒤 버립니다. `Rows Removed by Filter:`

이 문제가 생기는 이유는 developer가 개입하지 않으면 PostgreSQL에 `payload` column이 black box이기 때문입니다. 복잡한 non-scalar 구조인 content에 어떤 가정도 할 수 없어 합리적인 결정에 도움이 되는 의미 있는 statistics를 유지할 수 없습니다. 그 결과 같은 output을 만들기 위해 필요 이상으로 CPU, memory, I/O resource를 사용합니다.

### Targeted index로 성능 개선

```sql
call create_index_for_contract('token_quantity', 'Token', '((payload->>''quantity'')::decimal)', 'btree');
```

이 plan에서 다음 개선 사항을 파악할 수 있습니다.

- PostgreSQL이 row 수를 훨씬 정확히 추정합니다. `rows=14`와 `rows=9`
- `Rows Removed by Filter`가 사라져 낭비한 작업이 없습니다.
- `Workers Launched`가 사라져 parallelize할 필요가 없으므로 다른 workload 처리를 위해 resource를 절약할 수 있습니다.

PostgreSQL query planner는 cost 기반 optimizer입니다. 관련 statistics에 access하면 더 나은 결정을 내리고, 그렇지 않으면 지나치게 넓은 추정에 의존해야 합니다.

### 결론

PostgreSQL에는 `JSONB` column에 저장된 payload content를 다루는 query를 최적화할 모든 tool이 있습니다. 하지만 최적의 query 성능을 보장하도록 적절한 index와 statistics를 생성, 유지, monitor하는 것은 application developer의 책임입니다. 방법은 다음과 같습니다.

- Data access pattern을 반영하는 expression에 custom index 생성
- PostgreSQL이 합리적인 결정을 내릴 관련 statistics에 access하도록 보장
- 필요한 경우 종속 조건을 위한 multivariate statistics 생성
- Data distribution의 세부 차이를 포착하는 데 높은 precision이 필요한 expression의 statistics target 증가

추가 index, 주로 write path와 정기 `VACUUM ANALYZE` 실행 중 statistics를 유지하는 데 비용이 든다는 점도 고려해야 합니다. Query 성능과 유지보수 overhead 사이의 균형이 필요합니다.

Index 추가가 모든 성능 문제의 만능 해결책은 아닙니다. 빠른 query의 핵심은 selectivity 제어입니다. Predicate가 table의 20% 이상과 일치하는 query는 sequential scan이 index scan보다 빠를 가능성이 큽니다. `EXPLAIN` command 사용법을 익혀 성능 bottleneck을 식별하고 제거하세요.

Daml model을 단순하고 flat하게 유지하는 실용적 가치를 간과하지 마세요. 깊이 nested된 구조는 효율적인 indexing과 query가 어렵습니다. Downstream application의 query 성능을 높이는 데 도움이 된다면 Daml model denormalization을 고려하세요.
