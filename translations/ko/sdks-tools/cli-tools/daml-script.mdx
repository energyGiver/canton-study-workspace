Daml Script는 Daml Contract의 주요 testing tool입니다. Daml source file에 test scenario를 `Script ()` value로 작성하고 `dpm test`로 실행합니다. Script는 새 empty Ledger에서 실행되며 Party allocation, command 제출, state query, 예상 결과 assertion을 수행할 수 있습니다.

전체 function/type reference는 [Daml.Script API Reference](/appdev/reference/daml-script/daml-script)를 참조하세요.

## Test Script 작성

Daml Script는 `Script ()`를 반환하는 function입니다. Script는 Contract Package에 dependency를 둔 Test Package에 배치합니다. 깔끔한 deployment를 위해 Template과 test를 별도 Package로 유지하세요.

## Test 실행

### dpm test 사용

현재 Package의 모든 script를 실행합니다.

<DamlSdksToolsCliToolsDpmL56 />

Output은 각 script result, 종료 시점 Active Contract 수, 실행한 transaction 수를 보여줍니다. 마지막 summary에는 test coverage 정보가 포함됩니다.

```
Test Summary

MyTests.daml:testCreateAndTransfer: ok, 1 active contracts, 3 transactions.
```

### VS Code에서 실행

Daml Studio인 `dpm studio`가 설치되어 있으면 각 script definition 위에 "Script results" lens가 표시됩니다. 이를 클릭하면 script가 실행되고 side panel에 result가 표시됩니다. Panel에는 두 view가 있습니다.

- **Table view** -- Script 종료 시 Active Contract와 Party별 visibility입니다.
- **Transaction view** -- 모든 transaction/sub-transaction이며 authorization failure debugging에 유용합니다.

## Test 구성

Contract Package 구조를 반영하도록 Test Package를 구성합니다.

```
project/
  contracts/
    daml/
      Licensing/License.daml
    daml.yaml
  tests/
    daml/
      Licensing/LicenseTests.daml
    daml.yaml          # depends on contracts/
  multi-package.yaml
```

`tests/daml.yaml`은 `contracts` Package dependency를 선언합니다. `tests/` directory에서 `dpm test`를 실행하거나 project root에서 `dpm build --all` 후 `dpm test`를 실행합니다.

## Coverage report

`dpm test`는 script가 exercise한 Template/Choice를 보여주는 coverage report를 생성합니다. Test하지 않은 Contract path를 찾는 데 도움이 됩니다.

```
External templates
  5 defined
  4 ( 80.0%) created in any tests
External template choices
  12 defined
  8 ( 66.7%) exercised in any tests
```

Production에서 실행할 모든 Choice의 높은 coverage를 목표로 하세요. 자세한 walkthrough는 [testing guide](/appdev/modules/m3-testing)를 참조하세요.

## Script 기초

`Script`는 test recipe와 같습니다. 여러 Party가 일련의 transaction을 제출하는 scenario를 만들어 Template이 예상대로 동작하는지 확인할 수 있습니다. Party identity와 Ledger time 같은 external information도 script로 작성할 수 있습니다.

다음은 "Alice"라는 Party의 `Token`을 생성하는 기본 script입니다.

<DamlSdksToolsCliToolsDamlScriptL144 />

`Script`를 top-level variable로 선언하고 `script do`로 시작합니다. `do`는 항상 block을 시작하므로 나머지 script는 indent됩니다.

`Token` Contract를 생성하려면 먼저 Test Ledger에 Party가 있어야 합니다. 위 script는 `allocateParty` function으로 "Alice"라는 Party를 `alice` variable에 넣습니다. 다음 두 가지에 유의하세요.

- `=` 대신 `<-`를 사용합니다.

  `allocateParty`는 Ledger context에서 `Script`가 실행될 때만 수행할 수 있는 `Action`이기 때문입니다. `<-`는 "action을 실행하고 result를 bind"한다는 뜻입니다. Ledger state에 따라 `allocateParty`는 지정한 name의 Party를 반환하거나 이미 같은 Party가 allocate되어 있으면 suffix를 붙입니다. `Action`과 `do` block은 `constraints`에서 자세히 설명합니다.

  아직 이해하기 어렵다면 이 arrow가 Ledger에서 오른쪽 value를 꺼내 왼쪽 variable에 저장한다고 생각할 수 있습니다.

- `allocateParty`의 `"Alice"` argument는 bracket으로 감쌀 필요가 없습니다. Daml function은 `fn arg1 arg2 arg3` syntax로 호출합니다.

`Party` type variable `alice`가 준비되면 `submit` function으로 첫 transaction을 제출할 수 있습니다. `submit`은 `Party`와 `Commands` 두 argument를 받습니다.

`Script`가 test recipe인 것처럼 `Commands`는 transaction recipe입니다. `createCmd Token with owner = alice`는 Ledger에 제출할 command list로 변환되는 `Commands`입니다. 이 command는 transaction을 만들고, transaction은 Alice를 owner로 하는 `Token`을 생성합니다.

`Token with owner = alice` syntax는 `data`에서 자세히 설명합니다.

`submit alice (createCmd Token with owner = alice)`로 작성할 수도 있지만 script처럼 `do` block으로 command를 조립할 수 있습니다. `do` block은 항상 마지막 statement의 value를 취하므로 위 syntax는 같은 result를 내면서 더 읽기 쉽습니다. 다만 한 transaction의 일부로 제출한 command끼리는 서로 의존할 수 없습니다.

## Script 실행

Daml Script를 실행하는 방법은 여러 가지입니다.

- Daml Studio에서 Test Ledger를 대상으로 실행하고 결과 Ledger를 시각화합니다.
- Command line의 `dpm test`로 Test Ledger를 대상으로 실행하며 continuous integration에 유용합니다.
- 실제 Ledger를 대상으로 실행합니다. 자세한 내용은 Daml Script 문서를 참조하세요.

Daml Studio의 `token_test_1 = do` line 바로 위에 "Script results" text가 표시됩니다. 이를 클릭해 script result를 표시합니다.

![images/daml-scripts/scenario_results1.png](./images/daml-scripts/scenario_results1.png)

VS Code의 별도 column에 script view가 열립니다. Default view는 Ledger final state의 table representation입니다.

![images/daml-scripts/tabular_view1.png](./images/daml-scripts/tabular_view1.png)

이 display의 의미는 다음과 같습니다.

- 큰 title `Token_Test:Token`은 아래에 표시된 Contract type을 나타냅니다. `Token_Test`는 Module name이고 `Token`은 Template name입니다.
- 첫 column은 Contract ID를 보여줍니다. 이후 설명합니다.
- 두 번째 column은 `active` 또는 `archived`인 Contract status를 보여줍니다.
- 다음 column group은 Contract argument를 field당 한 column으로 보여줍니다. 여기에는 `owner` field 하나가 있고 value는 `'Alice'`입니다. Single quotation mark는 `Alice`가 Party임을 나타냅니다.
- 세로 label이 있는 나머지 column은 어떤 Party가 어떤 Contract를 아는지 보여줍니다. 이 단순한 script에서는 유일한 Party "Alice"가 자신이 생성한 Contract를 알고 있습니다.

같은 test를 command line에서 실행하려면 Module을 `Token_Test.daml` file에 저장하고 `dpm test --files Token_Test.daml`을 실행합니다. File에 script가 둘 이상이면 모두 실행됩니다.

## Failure test

`contracts`에서 `Token` 생성에는 owner authority가 필요하다고 배웠습니다. 즉 Alice가 Bob 같은 다른 Party의 Token을 생성하거나 그 반대로 수행할 수 없어야 합니다. 다음처럼 test할 수 있습니다.

<DamlSdksToolsCliToolsDamlScriptL201 />

하지만 이 script의 script view를 열면 다음 message가 표시됩니다.

![images/daml-scripts/failure.png](./images/daml-scripts/failure.png)

Script는 예상대로 fail했지만 첫 failure에서 abort됩니다. 따라서 Alice가 Bob의 Token을 생성할 수 없다는 것만 test했고 두 번째 `submit` statement에는 도달하지 않았습니다.

Fail하는 submit을 test하면서 이후 script를 계속 실행하거나 submission이 성공하면 fail하게 하려면 `submitMustFail` function을 사용합니다.

<DamlSdksToolsCliToolsDamlScriptL219 />

`submitMustFail`은 Ledger에 영향을 주지 않으므로 결과 table script view에는 성공한 `submit` statement로 생성된 Token 두 개만 표시됩니다. Bob의 새 column과 visibility에 유의하세요. Alice와 Bob은 서로의 Token을 볼 수 없습니다.

![images/daml-scripts/failuretable.png](./images/daml-scripts/failuretable.png)

## Contract archive

Contract archive는 Contract 생성의 반대 작업입니다. Contract는 immutable하므로 update, 즉 넓은 의미에서 state를 변경하려면 Ledger의 현재 Contract를 archive하고 새 Contract를 생성해야 합니다.

Contract를 archive하려면 `createCmd` 대신 `archiveCmd`를 사용합니다. `createCmd`는 Template instance를 받지만 `archiveCmd`는 생성된 Contract reference를 받습니다. Archive에는 Controller authorization이 필요합니다.

[Consuming Choice](/overview/reference/ledger-model-detailed#choices-in-the-ledger-model)가 exercise될 때도 Contract가 archive됩니다.

<Warning>
Archive Choice는 모든 Template에 존재하며 제거할 수 없습니다.
</Warning>

Contract reference는 `ContractId a` type이며 `a`는 ID가 가리키는 Contract의 Template type을 나타내는 *type parameter*입니다. 예를 들어 `Token` reference는 `ContractId Token`입니다.

Alice가 생성한 Token에 `archiveCmd`를 적용하려면 Contract ID가 필요합니다. `<-` notation으로 Ledger에서 Contract ID를 가져옵니다. 동작 방식은 `constraints`에서 설명합니다.

이 script는 먼저 Bob이 Alice의 Token을 archive할 수 없음을 확인한 다음 Alice가 성공적으로 archive합니다.

<DamlSdksToolsCliToolsDamlScriptL257 />

## Ledger와 history 확인

Contract를 archive하면 Ledger에 남은 Contract가 없어 script view가 비어 있습니다. 해당 state에 도달한 과정 등 Ledger history를 보려면 Ledger view 상단의 "Show archived" box를 선택합니다.

![images/daml-scripts/archived.png](./images/daml-scripts/archived.png)

`Token` Contract가 존재했고 현재 archive되었음을 확인할 수 있습니다. `status` column의 "archived" value와 strikethrough로 표시됩니다.

전체 transaction graph를 보려면 옆의 "Show transaction view" button을 클릭합니다.

![images/daml-scripts/tx_graph.png](./images/daml-scripts/tx_graph.png)

Daml Studio script runner에서 commit된 transaction은 순서대로 번호가 지정됩니다. 위 image에서 `TX`로 시작하는 line은 ID가 `#0`, `#1`, `#2`인 commit transaction 세 개가 있음을 나타냅니다. Script의 세 `submit`/`submitMustFail` statement에 대응합니다.

Transaction `#0`에는 *sub-transaction* `#0:0` 하나가 있으며 arrow는 `Token`의 `create`임을 나타냅니다. Identifier `#X:Y`는 `commit X, sub-transaction Y`를 의미합니다. Script runner의 모든 transaction은 이 format을 사용하지만 testing feature일 뿐입니다. 일반적으로 transaction/Contract ID는 opaque하다고 간주해야 합니다.

`create Token_Test:Token` 위아래 line은 추가 정보를 제공합니다.

- `consumed by: #2:0`은 Contract가 commit `2`의 sub-transaction `0`에서 archive되었음을 나타냅니다.
- `referenced by #2:0`은 Contract가 다른 transaction에서 사용되었음을 나타내고 해당 ID를 나열합니다.
- `disclosed to (since): 'Alice' (#0)`은 Contract를 아는 Party를 나타냅니다. List에 `'Alice'`가 있는 것은 table view의 `x`와 같습니다. `(#0)`은 Alice가 commit `#0`에서 Contract를 알게 되었음을 추가로 보여줍니다.
- `with` 뒤의 모든 내용은 create argument를 보여줍니다.

## Exercises

Script를 더 잘 이해하려면 다음 exercise를 수행하세요.

1.  두 번째 Token type의 Template을 작성합니다.
2.  Party 두 개와 Token type 두 개를 가진 script를 작성합니다. 각 Party에 type별 Token을 하나씩 생성하고 각 Party의 Token 하나를 archive해 final Ledger view에 type별 Token 하나씩 남깁니다.
3.  `archiving`에서 Bob이 Alice의 Token을 archive할 수 없음을 test했습니다. Submit이 fail하는 이유를 추측하고 확인 방법을 찾아보세요.

<Tip>
힌트: `intro_2_failure`에서 fail한 submit의 올바른 error message를 확인한 것을 기억하세요.
</Tip>
